## Azure first

- **Azure Logic Apps** is Azure's workflow service: a **trigger** (the event that starts it) followed by **actions** (steps). Every classic Sentinel playbook *is* a Logic App, so it is a normal Azure resource in a **resource group**, billed per run.
- A **connector** is a Logic Apps building block that talks to one service (Microsoft Sentinel, Outlook, Teams, Entra ID). Do not confuse it with a Sentinel *data* connector, which brings logs in.
- A **managed identity** is an identity Azure creates for a resource, so the playbook can sign in without a stored password. You give it roles like a user.
- **Azure RBAC** roles control who builds, runs and attaches playbooks — and whether Sentinel itself may start them.

New to these? Read the Foundations pages linked above.

## In one sentence

A playbook is a saved Azure Logic Apps workflow that Microsoft Sentinel starts — automatically from an automation rule, or by hand from an incident, alert or entity — to do things in other systems: block a user, isolate a device, post to Teams, open a ticket.

## Why it exists

An automation rule (D1.1.10) can only touch the incident itself: assign, tag, change severity, close. It cannot email anyone, call an API or disable an account. A playbook can. Think of the automation rule as the **dispatcher** and the playbook as the **crew** sent out to act in the world.

Microsoft lists four playbook jobs:

| Use case | Example |
|---|---|
| **Enrichment** | Look up an IP in a threat-intel service and add the result as an incident comment |
| **Bi-directional sync** | Open a ServiceNow ticket for every new incident, and keep it updated |
| **Orchestration** | Post the incident to the SOC's Teams or Slack channel |
| **Response** | Disable a compromised user, isolate a machine, block an IP |

## What actually matters

**1. Triggers decide where a playbook can be used.** The Microsoft Sentinel Logic Apps connector has three triggers:

| Logic Apps trigger | Started by | Typical use |
|---|---|---|
| ==@Microsoft Sentinel incident== | Incident-trigger automation rule, or manual run on an incident | **Recommended for most playbooks.** Gets the whole incident: alerts, entities, comments. |
| ==@Microsoft Sentinel alert== | Alert-trigger automation rule, or manual run on an alert | Alerts from analytics rules that don't create incidents |
| ==@Microsoft Sentinel entity== | **Manual only**, on one entity (account, host, IP, URL, file hash…) | Hunting and investigation. No automation rule can call it. |

An entity playbook run from hunting has no incident. Its **Incident ARM ID** field is null. Add a Condition that checks it is "not equal to null" before any step that updates an incident.

**2. The new Defender portal names.** In the Defender portal, **Microsoft Sentinel > Configuration > Automation > Create > Logic App playbook** now offers:

- ==@Playbook with alert trigger== and ==@Playbook with case trigger== — the new options. Defender calls an incident a **case**. These build on the **Microsoft Defender SOC** connector (triggers **Microsoft Defender SOC alert** / **Microsoft Defender SOC case**). The SOC alert trigger covers both Defender and Sentinel alerts.
- **Playbook with incident trigger (Legacy)**, **Playbook with alert trigger (Legacy)**, **Playbook with entity trigger (Legacy)** — the classic Microsoft Sentinel connector. "Legacy" does not mean broken: existing Sentinel-connector playbooks stay supported on incidents and cases.
- **Blank playbook** — for a **Standard** logic app.

Microsoft's own doc adds a naming twist. When you create a "case trigger" playbook, the matching Microsoft Sentinel connector trigger in Logic Apps is still called **Microsoft Sentinel incident**.

The Defender portal also has **generated playbooks** (Playbook Generator). These are AI-written **Python** code, *not* Logic Apps. They don't need Azure Logic Apps roles. They are new, so expect at most a recognition question. The flow: **Automation > Playbooks tab > Generated playbook** → name + input type (**Alert** or **Incident case**) → describe it in chat (**Plan mode**) → switch to **Act mode** to generate code → approve each file change (or turn on **Auto-approve**) → test → **Save**. A saved generated playbook starts ==!disabled== — activate it before an automation rule can use it.

**3. Consumption vs Standard.**

| | Consumption | Standard |
|---|---|---|
| Hosting | Multitenant, pay per run | Single-tenant plan; many workflows in one logic app |
| Templates | Yes — playbook templates deploy as Consumption | **No template support.** Create the logic app, then a workflow, then pick the trigger. |
| Workflow type | — | Must be **Stateful** (Sentinel does not support stateless) |
| Private networking | — | Private endpoints / VNet integration |

**4. Identity: how the playbook signs in to Sentinel.** The Sentinel connector supports a **managed identity** (Microsoft's recommendation), a **service principal**, or a **Microsoft Entra user** (OAuth sign-in). For a managed identity:

1. Turn on the system-assigned identity on the logic app.
2. On the workspace, **Access control (IAM) > Add role assignment** for that logic app.
3. Choose ==@Microsoft Sentinel Responder== if the playbook updates incidents or watchlists. Choose **Microsoft Sentinel Reader** if it only receives incidents.
4. In the designer, choose **Connect with managed identity**.

Assigning that role needs **Owner** or **User Access Administrator** on the workspace.

**5. Who can do what.** This is the most-tested part.

| Need | Role |
|---|---|
| Create / edit playbooks (Consumption) | ==@Logic App Contributor== (can also run) |
| Enable / disable only | Logic App Operator |
| Run a playbook **manually** | ==@Microsoft Sentinel Playbook Operator== |
| See the incident to run it from | Microsoft Sentinel Responder (does **not** let you run it) |
| **Attach** a playbook to an automation rule | ==@Microsoft Sentinel Contributor== |
| Let **Sentinel** run playbooks (service account) | ==@Microsoft Sentinel Automation Contributor== on the playbook's resource group |
| Grant that service permission | **Owner** or **User Access Administrator** |
| Standard logic apps | Logic Apps Standard Operator / Developer / Contributor |

Defender unified RBAC adds three permissions for Defender SOC Logic Apps and generated playbooks: **Playbooks (manage)** to create and run, **Execute hard actions** to run only, and **Automation rules (manage)**. Either playbook permission is enough to run one.

> **Two Microsoft sources disagree on "who can run".** The Sentinel **roles** article and the manual-run instructions say ==+Microsoft Sentinel Playbook Operator== runs playbooks. The prerequisites section of *Automate threat response with playbooks* (repeated in *Run playbooks*) says that to run playbooks you *"also need the **Logic App Contributor** role on the resource group"*. Logic App Contributor does include run rights, so both work in practice. For the exam, the least-privilege answer for "run only" is **Playbook Operator**; Logic App Contributor is the answer when the person must also **create or edit**.

By default a playbook is usable only in its own subscription. Granting Sentinel permission on its resource group extends that.

**6. Templates.** A playbook template is an **ARM template** containing a Logic Apps workflow and one **API connection** per service it uses. It is not a playbook until you deploy it. Three sources:

- the **Playbook templates** tab on the **Automation** page
- the **Content hub** (inside solutions or as standalone items)
- the Microsoft Sentinel **GitHub** repository (**Deploy to Azure** button)

After deploying, open each **API connection** and **authorize** it, or the playbook fails. When a template gets a new version, active playbooks built from it show an **update available** label. Templates are in preview.

**7. Running it.**

- **Automatically:** only through an **automation rule** with a **Run playbook** action. Incident-trigger playbooks need incident-trigger rules; alert-trigger playbooks need alert-trigger rules. Calling playbooks directly from an analytics rule ("Alert automation (classic)") was deprecated in March 2026.
- **Manually:** in the Defender portal open the incident (or case or alert) > **Run playbook** > pick one > **Run playbook**. The **Runs** tab shows history; **View run** opens the Logic Apps run log. A **Missing permissions** status means *you* lack Playbook Operator. A **Grant permission** status means *Sentinel* lacks Automation Contributor.

## Where it lives

| Task | Path |
|---|---|
| Create playbook (Defender portal) | **Microsoft Sentinel > Configuration > Automation > Create > Logic App playbook** |
| Create playbook (Azure portal) | **Microsoft Sentinel > Configuration > Automation > Create > Playbook with incident / alert / entity trigger** or **Blank playbook** |
| From a template | **Automation > Playbook templates** tab > template > **Create playbook** (Basics, Parameters, Connections, Review) |
| List / enable / disable | **Automation > Active playbooks** (columns: Status, Plan, Trigger kind) |
| Grant Sentinel permission | Defender: **Settings > Sentinel > (workspace) > Playbook permissions > Configure permissions**. Azure: **Sentinel > Settings > Settings > Playbook permissions** |
| Run manually | Incident or case > **Run playbook**; alert page > **Run playbook**; entity > **Run playbook** (Azure portal for classic entity playbooks) |
| Edit logic | The logic app resource > **Logic app designer** (Consumption) or workflow > **Designer** (Standard) |

The Create wizard puts the logic app in the **same region** as the workspace. On the **Connections** tab it defaults to a managed identity connection to Sentinel. You can tick **Enable diagnostics logs in Log Analytics** for run monitoring.

## Exam traps

- "Analysts must run playbooks manually, nothing more." ==+Microsoft Sentinel Playbook Operator==, not ==!Logic App Contributor== (that also lets them edit). Responder alone ==!cannot run== a playbook.
- "Attach a playbook to an automation rule." The user needs ==+Microsoft Sentinel Contributor==. *Sentinel* needs ==+Automation Contributor== on the playbook's resource group. ==!Automation Contributor is never assigned to a person.==
- "Playbook is greyed out in the automation rule." ==+Grant Sentinel permission on the playbook's resource group== (Owner needed). It is not a Logic Apps licence issue.
- "Run a playbook on an IP while hunting, no incident." ==+Entity trigger==, run manually. An ==!automation rule cannot call an entity playbook==.
- "Playbook must update incidents using a managed identity." Give the logic app ==+Microsoft Sentinel Responder== on the workspace. ==!Reader== only lets it receive incidents.
- "Attach the playbook directly to the analytics rule." ==!Deprecated== (Alert automation classic). ==+Use an alert-trigger automation rule.==
- "Need a playbook that reaches a private VNet resource." ==+Standard== logic app. But Standard ==!has no template support== and must be ==+Stateful==.
- Logic Apps **connector** ≠ Sentinel **data connector**. The training module's knowledge check tests exactly this.
