## Azure first

- **Case management** is a feature of the **Microsoft Defender portal** (`security.microsoft.com`). It does **not** exist in Microsoft Sentinel in the Azure portal.
- **Unified RBAC** is the Defender portal's own permission system (separate from Azure RBAC on the Sentinel workspace). Its permissions have names like **Security Data Read**, **Security Data Manage** and **Alerts (manage)**. Sentinel roles (Reader, Responder, Contributor) also grant access to generic cases.
- **Log Analytics workspace:** the database behind Microsoft Sentinel. When a **primary Sentinel workspace** is connected to the Defender portal, every case change is copied to a table called `SecurityCaseEvent` in it, so you can report on cases with KQL (the query language).
- **Lab access:** an Azure-only learner can connect a Sentinel workspace to the Defender portal and use cases — no E5 needed. This bullet has **no training unit**; this page is written from product documentation. Incident cases are **in preview** (November 2026) — expect screens to move.

New to these? Read the Foundations pages linked above.

## In one sentence

A **case** is a SOC work item in the Defender portal's **Cases** page — an **incident case** wraps one correlated incident, a **generic case** tracks any other SecOps work — with owner, status, tasks, comments, attachments, custom fields and SLA timers, all audited.

## Why it exists

A hospital has patients (incidents) and a separate admin system for the work around them: who is on shift, which tests are due, when the deadline is, what the notes say. Until now the SOC tracked that admin work in an outside ticketing tool. Case management puts the ticket next to the evidence, so an analyst never copies an incident into ServiceNow to remember a deadline.

## What actually matters

**1. Two case types.** **Incident cases** (preview) are created automatically from correlated incident activity. They are now the **recommended** way to manage incidents in the Defender portal; the **legacy incident experience** stays available during the preview. **Generic cases** are created by hand for work that isn't one incident — chasing a threat-intel lead, tracking a follow-up. Generic cases link **Incidents**, **Indicators** (preview) and **Recommendations** under **Linked objects**. Linking indicators replaces the deprecated *Projects* in Defender Threat Intelligence. (Docs also name a third type, **exposure cases**, from Exposure Management — not this bullet.)

**2. Prioritise with the priority score.** The incident case list has a **Priority score**: **Top priority** above **85**, **Medium** between **15 and 85**, **Low** below **15**. Select a row to read the **priority assessment** — why it scored that way (severity, threat signals, assets, MITRE techniques).

**3. Manage case pane = triage + closure.** Three-dot menu > **Manage case**: **Assigned to**, **Severity**, **Status**, **Classification** (and determination), **Tags**, **Due date / Due time**, **custom fields**, then **Save**. Changes on an incident case **sync to the related incident**: ownership, status, tags, classification, determination and closing notes are stored on both. Existing incident **email notification rules** fire on case changes too.

**4. Closing an incident case does not close its alerts.** In the case experience, ==related alerts keep their own status==. That is a change from the legacy page, where resolving an incident resolves all its active alerts. Defender's classifications are **True positive**, **Informational, expected activity** and **False positive**, each with determinations (D2.1.7 has the full list).

**5. Collaborate and record.** **Tasks** break the work into items with owner, status, priority, due date, category, description and **closing notes**. **Comments & Attachments** holds comments (with formatting and attached files) and an **Attachments** tab. **Activities** is the audit trail: creation, assignment, status, severity, classification, task, comment and automation changes. **Agentic sessions** let you **Run agentic playbook** from a case and follow the agent's status — only for tenants in *Project Perception*. Tasks created in **Sentinel in the Azure portal** (by hand, by an automation rule, a playbook or the Incident Tasks API) ==sync one way== into the Defender portal. Tasks made in Defender do not flow back, and the Defender portal ==!cannot create tasks automatically== yet.

**6. Fix the scope: merge or move.** **Merge** (from the Cases list or the case's three-dot menu) when several cases are one attack: one case ID is kept, the data is consolidated, the other IDs go away. You must type a **comment** and pick at least one **reason** (same actor, same campaign, shared indicators, lateral movement path …). **Resolved cases can't be merged**, and you need **Security Data Manage** on all of them. **Move an alert** (**Artifacts > Alerts** > select alert > **Move alert to another incident**) when it was correlated to the wrong case. A comment is required, and you can send Microsoft feedback on the wrong correlation. Every alert must belong to a case.

**7. Admins shape the process with case templates.** **Cases > Case management settings** > pick **Incidents** or **Generic**:

| Template feature | What it does |
|---|---|
| **Custom fields** | Your own fields (name, type, required, default value) |
| **Custom statuses** | Extra statuses grouped under **New**, **Open**, **Closed**. Default statuses can't be deleted; a status in use can't be deleted |
| **SLA management** | Timers: start and end criteria, pause criteria, **exceeded** and **at risk** limits, and a **Recalculate** rule (Don't recalculate / Recalculate and carry on / Recalculate and reset) |

An **SLA** (service-level agreement) is a promised response time, such as "acknowledge a high-severity case within 30 minutes". Each case's SLA timer shows a state: **Active**, **At Risk** (only if an at-risk limit is set), **Breached**, **Paused**, **Completed (Met)** or **Completed (Breached)**. A negative timer means the target has passed. To email people when a timer changes state, build an **automation rule** with the **Case updated** trigger and an **SLA Policies** condition. During preview, SLA policies work only in a ==!single-tenant== Defender portal, not the multitenant view.

**8. Audit and retention.** Defender keeps case history for **180 days**. With a connected **primary Sentinel workspace**, every change to cases, tasks, comments, attachments (metadata only) and links is synced to `SecurityCaseEvent` automatically. You cannot turn the sync off. Query it in **Advanced hunting**, Sentinel or Log Analytics, and keep it longer by changing the table's retention. Ready-made queries sit in the Log Analytics **Queries hub** (filter **Resource type: Case Management**) and in Advanced hunting under **Community queries > Microsoft Sentinel**.

### Permissions

| Action | Defender unified RBAC | Sentinel role |
|---|---|---|
| View incident cases | **Security Data Read** | — |
| View + manage incident cases (incl. merge, move alert) | **Security Data Manage** | — |
| View / manage **incident case tasks** | **Security data basics (read)** / **Response (manage)** | — |
| View generic cases, tasks, comments, audits | Security operations > **Security data basics (read)** | **Microsoft Sentinel Reader** |
| Create / manage generic cases and tasks | Security operations > **Alerts (manage)** | **Microsoft Sentinel Responder** |
| Case templates, custom fields, SLA policies | Authorization and settings > **Core security settings (manage)** | **Microsoft Sentinel Contributor** |

## Where it lives

**Defender portal only.** Not available in Sentinel in the Azure portal.

| Task | Path |
|---|---|
| Incident cases | **Cases > Incident** |
| Generic cases | **Cases > Generic** > **Create** |
| Investigate | Open a case > **Overview > Summary by Copilot / Attack graph**; **Artifacts > Alerts / Assets / Investigations / Evidence / Activities / Similar cases** |
| Manage | Case > three-dot menu > **Manage case** |
| Comments and files | Case > **Comments & Attachments** |
| Merge | **Cases > Incident** > select cases > **Merge cases** |
| Templates, SLA | **Cases > Case management settings** > **Incidents** or **Generic** |
| Legacy incident page | **Investigation & response > Incidents & alerts > Incidents** |

```kql
// Who changed what on cases in the last week (audit table in the primary Sentinel workspace)
SecurityCaseEvent
| where TimeGenerated > ago(7d)
| project EventTime, ModifiedBy, EntityType, OperationName, PropertyNames, PreviousValues, NewValues, ParentEntityId
| order by EventTime desc
```

`EntityType` says what changed (Case, CaseTask, Comment, Attachment, CaseRelation). `OperationName` is Create, Update, Delete, Link or Unlink.

## Exam traps

- ==!Case management is in the Azure portal's Sentinel.== No — ==+Defender portal only==.
- ==!Closing an incident case resolves its alerts.== No — in cases, ==+alerts keep their own status==. On the legacy page, resolving the incident does resolve its active alerts. Watch which experience the question describes.
- ==!A resolved incident case can be merged.== It can't. Merging keeps ==+one case ID== and removes the others.
- Generic vs incident: **generic** cases are created by hand and have **Priority**; **incident** cases come from correlation and have **Severity** and a **Priority score**.
- Priority score bands: ==@above 85== top, ==@15–85== medium, ==@below 15== low.
- Template permissions: ==@Core security settings (manage)== in unified RBAC = ==@Microsoft Sentinel Contributor==. Creating generic cases = ==@Alerts (manage)== = ==@Microsoft Sentinel Responder==.
- Custom statuses must live under **New**, **Open** or **Closed**; default statuses can't be deleted.
- ==!Incident case tasks need Alerts (manage).== Generic case tasks do; ==+incident case tasks need Response (manage)==.
- ==!Defender can auto-create case tasks.== It can't yet. Sentinel task automation rules / playbooks in Azure create them, and they ==+sync one way== into Defender.
- ==!Case audit sync must be switched on.== It is ==+automatic and can't be turned off== once a primary Sentinel workspace is connected; it lands in `SecurityCaseEvent`.
- Don't confuse with **Microsoft Purview Insider Risk Management cases** (D2.1.2) — a different product with its own "cases".
