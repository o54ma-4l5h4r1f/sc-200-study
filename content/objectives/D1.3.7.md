## Azure first

- A **Log Analytics workspace** stores data in **tables**. Microsoft ships **Azure tables** with fixed columns (`SecurityEvent`, `Syslog`…). You can add your own **custom tables**.
- A **data collection rule (DCR)** describes the shape of incoming data, an optional KQL **transformation**, and which table receives it.
- A **data collection endpoint (DCE)** is an optional regional URL that receives data. Newer DCRs have their own endpoint, so you often don't need one.
- An **app registration** in Microsoft Entra ID gives a script or app an identity (application ID + secret) to send data.
- Two Azure RBAC roles matter: **Log Analytics Contributor** (manage tables) and **Monitoring Metrics Publisher** (allowed to send data through a DCR).

New to these? Read the Foundations pages linked above.

## In one sentence

A **custom table** is a table you define in the workspace — its name always ends in **`_CL`** — and you create it together with a **DCR** that tells Azure Monitor how incoming JSON maps onto it, usually so an app or script can send data with the **Logs Ingestion API**.

## Why it exists

The filing cabinet comes with labelled drawers for common paperwork. When a new kind of paperwork arrives — a line-of-business app's audit log, a SaaS product with no connector — you add a drawer and print its label yourself. The DCR is the clerk's instruction card: "these forms go in drawer `AppAudit_CL`, copy the date into the date box, drop the debug lines".

No training unit covers this bullet. This page is written from the Azure Monitor product documentation.

## What actually matters

**1. Naming.** Custom tables end in **`_CL`**. The portal adds it for you; CLI, PowerShell, REST, ARM and Bicep do not — type it yourself. In the DCR the stream is **`Custom-MyTable_CL`** (built-in tables use `Microsoft-` plus the table name). Custom *columns* added to an **Azure** table end in **`_CF`**. Table names appear on bills, so keep secrets out of them.

**2. Every table needs `TimeGenerated`.** If your sample data lacks it, the portal adds it to the DCR transformation for you.

**3. The portal route (the one to know).** **Log Analytics workspace > Tables > Create > New custom log (DCR-based)**:

1. Name (no `_CL`), optional description, **table plan**: **Analytics** (default), **Basic** or **Auxiliary / Lake**.
2. Pick an existing **DCR** or create one; pick a **DCE** if needed.
3. **Browse for files** — upload a **JSON sample** of your data.
4. Optional **Transformation editor**: a KQL query over the virtual table `source`, e.g. parse a field, filter rows. **Run**, then **Apply**.
5. **Create**. The portal builds the table *and* the DCR with its transformation.

**4. Sending data with the Logs Ingestion API.**

| Piece | Why |
|---|---|
| **App registration + client secret** | The sender's identity |
| **The table** | Must exist first |
| **DCR** | Shape, transformation, target table |
| **Role assignment** | **Monitoring Metrics Publisher** for the app, **on the DCR** (grants `Microsoft.Insights/Telemetry/Write`). Up to **30 minutes** to take effect; before that you get **HTTP 403** |
| **Endpoint** | The DCR's own **logs ingestion endpoint** (DCRs created with `"kind": "Direct"`, available since 31 March 2024) or a **DCE** — a DCE is needed only for **private link** or older DCRs |

The call: `POST https://{endpoint}/dataCollectionRules/{dcrImmutableId}/streams/{streamName}?api-version=...` with a bearer token for scope `https://monitor.azure.com`, `Content-Type: application/json`, body = a **JSON array**. The **immutable ID** is on the DCR's Overview / JSON view. From **1 March 2026** the API requires **TLS 1.2+**. Each call accepts up to **1 MB** of data (the old Data Collector API took 30 MB) — send more as parallel calls. DCR, workspace and DCE must be in the **same region**.

**5. Changing and deleting.**

- Add or remove columns: **Tables > … > Edit schema**. Custom tables: any column. Azure tables: only your `_CF` columns.
- Column names: start with a letter, letters/digits/underscores only, **up to 45 characters**; reserved names (`id`, `TenantId`, `Type`, `_ResourceId`…) not allowed.
- ==!Azure Monitor doesn't update the DCR when you change the table.== Update the DCR yourself.
- You can **delete custom tables**; you ==!can't delete Azure tables==.

**6. Permissions.** Manage a table: `Microsoft.OperationalInsights/workspaces/*` — e.g. **Log Analytics Contributor**. Create a DCR: `Microsoft.Insights/dataCollectionRules/write` — e.g. **Monitoring Contributor**.

**7. The Sentinel connection.** Custom tables are where non-standard data lands: the **Custom logs via AMA** connector (text or JSON files on Windows/Linux into tables you created, such as `ApacheHTTPServer_CL`), **Codeless Connector Framework** connectors, and your own Logs Ingestion API code. The old **HTTP Data Collector API** (workspace ID + shared key, no DCR, no transformation) ==!reached end of support on 14 September 2026==. Ingestion still works for TLS 1.2+ clients, but there are no fixes or SLA — migrate to the Logs Ingestion API. Old Data Collector API tables ("classic" custom tables) can be converted with a one-way **migrate** operation that turns on DCR-based features; it can't be rolled back.

## Where it lives

**Azure portal > Log Analytics workspaces > (workspace) > Tables > Create > New custom log (DCR-based)**. You create the table in the **Azure portal** on the workspace itself, even when you run Sentinel in the Defender portal (whose Sentinel settings live under **System > Settings > Microsoft Sentinel**).

Assign the sender role: **Azure portal > Monitor > Data Collection Rules > (DCR) > Access control (IAM) > Add role assignment > Monitoring Metrics Publisher**.

```bash
az monitor log-analytics workspace table create \
  --resource-group rg-sentinel --workspace-name law-sentinel \
  --name AppAudit_CL --plan Analytics \
  --columns TimeGenerated=datetime RawData=string

az monitor data-collection rule create --resource-group rg-sentinel \
  --name dcr-appaudit --rule-file my-dcr.json
```

```powershell
New-AzOperationalInsightsTable -ResourceGroupName rg-sentinel -WorkspaceName law-sentinel `
  -TableName AppAudit_CL -Plan Analytics -RetentionInDays 31 -TotalRetentionInDays 365 `
  -Column @{'TimeGenerated'='DateTime'; 'RawData'='String'}
```

```kql
AppAudit_CL
| where TimeGenerated > ago(1h)
| take 10
```

## Exam traps

- "Name the table `AppAudit` in the REST call." ==!The API won't add the suffix.== ==+`AppAudit_CL`.== Only the portal adds `_CL`.
- "Add a column `Region` to `SecurityEvent`." Custom columns on Azure tables must be ==+`Region_CF`==.
- "App gets 403 when posting." ==+Monitoring Metrics Publisher on the DCR== — and wait up to 30 minutes. ==!Log Analytics Contributor on the workspace== is the wrong role for sending.
- "A DCE is always required." ==!No== — only for private link or DCRs without their own endpoint.
- "Changed the table schema; DCR follows automatically." ==!False.==
- "Use the HTTP Data Collector API." ==!End of support since 14 September 2026== (ingestion still flows for TLS 1.2+ clients, but unsupported) — ==+use the Logs Ingestion API with a DCR==.
- "Delete the `Syslog` table." ==!Azure tables can't be deleted.==

- **Skip** the full REST, ARM and Bicep JSON bodies for tables and DCRs. Know the parts: `streamDeclarations`, `destinations`, `dataFlows` with `transformKql` and `outputStream`.
- **Skip** the tutorial's PowerShell `LogGenerator.ps1` sample-data script and the client-library list (.NET, Go, Java, JavaScript, Python).
- **Skip** Auxiliary-plan datetime precision rules and the `guid`-stored-as-string note. Table plans and retention are D1.2.
- **Skip** search-job (`_SRCH`) and restore (`_RST`) tables — different table types, not this bullet.
