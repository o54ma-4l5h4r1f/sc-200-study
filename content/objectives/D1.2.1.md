## Azure first

- **Azure RBAC** gives a person, group or app a **role** at a **scope**: subscription, resource group or single resource. Roles add up; the scope flows downward.
- A **resource group** is a folder for Azure resources. Sentinel's workspace, its workbooks and its playbooks usually share one. That is the scope Microsoft recommends for Sentinel roles.
- **Microsoft Entra roles** (Security Administrator, Security Reader, Global Administrator…) are a *different* system. They control the directory and Microsoft 365 portals, not Azure resources.
- **Defender unified RBAC (URBAC)** is a third system, managed inside the Defender portal. It can take over Sentinel permissions once you switch it on per workspace.

New to these? Read the Foundations pages linked above.

## In one sentence

Microsoft Sentinel uses five built-in Azure roles — **Reader**, **Responder**, **Contributor**, **Playbook Operator** and **Automation Contributor** — plus a few helper roles, and you pick the smallest one that lets each person do their job.

## Why it exists

A building has a guard who watches the cameras, a supervisor who can open and close incident reports, and an engineer who rewires the cameras. You don't give the guard the engineer's keys. Sentinel works the same way. Viewing data, handling incidents and changing the detection setup are three different levels of trust.

## What actually matters

**1. The five Sentinel roles, by what they let you do.**

| Role | Run playbooks | Create/edit playbooks | Create/edit analytics rules, workbooks | Manage incidents | View data, incidents, workbooks | Manage Content hub |
|---|---|---|---|---|---|---|
| ==@Microsoft Sentinel Reader== | — | — | —\* | — | ✓ | — |
| ==@Microsoft Sentinel Responder== | — | — | —\* | ✓ | ✓ | — |
| ==@Microsoft Sentinel Contributor== | — | — | ✓ | ✓ | ✓ | ✓ |
| ==@Microsoft Sentinel Playbook Operator== | ✓ | — | — | — | — | — |
| Logic App Contributor | ✓ | ✓ | — | — | — | — |

\*Possible with **Workbook Contributor** added (workbooks only).

**Microsoft Sentinel Automation Contributor** is not in that table. It lets Microsoft Sentinel itself run playbooks from automation rules. ==!It is not used for user accounts.==

**2. Assign at the resource group.** Microsoft recommends assigning Sentinel roles on the **resource group that holds the workspace**. That covers the workbooks, playbooks and other resources in it. If you assign on the workspace alone, you must also assign the same role on the **SecurityInsights solution resource**, and keep chasing other resources.

**3. Extra roles for specific jobs.**

| Task | What's needed |
|---|---|
| Connect data sources | **Write** permission on the workspace (plus whatever each connector demands) |
| Manage Content hub | Microsoft Sentinel Contributor at resource group level |
| Create/edit playbooks | Logic App Contributor |
| Let Sentinel run playbooks | Its service account gets **Automation Contributor** on the playbook resource group; you need **Owner** or **User Access Administrator** to grant it (the roles article says Owner; the playbook articles say Owner or User Access Administrator) |
| Guest user assigns incidents | Microsoft Sentinel Responder **+ Directory Reader** (an Entra role members get by default; guests don't) |
| Create/delete workbooks | Microsoft Sentinel Contributor, **or** a lesser Sentinel role **+ Workbook Contributor** |

**4. Roles add up, and broad roles leak in.** Azure **Owner**, **Contributor** and **Reader**, and **Log Analytics Contributor** / **Log Analytics Reader**, all reach the workspace too. Microsoft's own warning: a user with both **Microsoft Sentinel Reader** and the generic Azure **Contributor** role "may have more permissions than intended". To really limit someone, remove those broad roles as well.

**5. The data lake adds Entra roles.** Sentinel SIEM uses Azure RBAC. The **Microsoft Sentinel data lake** grants *tenant-wide* access through **Microsoft Entra** roles. Read access across all workspaces: **Global Reader**, **Security Reader**, **Security Operator**, **Security Administrator** or **Global Administrator**. Writing to lake tables and managing KQL jobs: **Security Operator**, **Security Administrator** or **Global Administrator**. ==!It is not Entra-only:== a user with an Azure role on one workspace (Sentinel Reader/Contributor, Log Analytics Reader/Contributor, Reader, Contributor, Owner) can read *that* workspace's lake data too.

**6. The Defender portal and unified RBAC.**

- After you connect Sentinel to the Defender portal, your **Azure RBAC roles keep working** there. By default you keep managing them in the Azure portal.
- You *may* activate **Defender unified RBAC** for Sentinel, **per workspace**. After that, URBAC is the source of truth and you manage roles in the Defender portal. Azure-portal changes can cause sync errors. ==!Azure roles still count:== Sentinel pages in the Defender portal keep honouring Azure (ARM) roles too, so a user with more in Azure than in URBAC can still see more.
- Activating needs **Security Administrator** (Entra) **plus** either subscription **Owner**, or **User Access Administrator** + **Sentinel Contributor**.
- **Not supported in URBAC**, so these stay in Azure: **Playbook Operator**, **Automation Contributor**, **Workbook Contributor**. Service principals can't be assigned in URBAC either. If you need a service principal, keep that workspace on Azure RBAC.
- In URBAC, a **Global Administrator** gets no automatic workspace access. They can still assign it, even to themselves.

| Sentinel Azure role | URBAC equivalent | URBAC permissions |
|---|---|---|
| Sentinel Reader | Defender Unified RBAC Reader | Security data basics (read) |
| Sentinel Responder | Defender Unified RBAC Responder | + Alerts (manage), Response (manage) |
| Sentinel Contributor | Contributor and Responder | + Detection tuning (manage) |
| — | Scoped Reader | Security data basics (read), only for assignments with a Sentinel scope applied |
| — | Data Manager | Data operations \ Data (manage) |

**7. Narrower than a workspace.** **Resource-context RBAC** lets a team see only the log rows from Azure resources they already have access to, without any workspace role. **Table-level RBAC** limits access to certain tables. Use either when a team needs some data but not all. In the Defender portal, once Sentinel is active in URBAC, **Microsoft Sentinel scoping** (row-level RBAC) does the same job with reusable scope tags inside one shared workspace.

**8. The Azure portal is going away for Sentinel.** After ==@March 31, 2027== Sentinel is supported only in the Defender portal. Role *assignment* for the SIEM stays Azure RBAC (or URBAC if you switch it on).

**Picking a role — the three questions.** First, *what must they change?* Nothing means **Reader**. Incidents only means **Responder**. Rules, workbooks or solutions means **Contributor**. Second, *do they touch playbooks?* Running them means add **Playbook Operator**. Building them means add **Logic App Contributor**. Third, *where?* Assign on the Sentinel resource group. If playbooks live in another resource group, assign the playbook roles there too. This order of questions solves most "least privilege" exam scenarios.

**Recommended setup:** analysts get **Responder** (+ **Playbook Operator**). Engineers get **Contributor** (+ **Logic App Contributor**). An automation service principal gets **Contributor**.

## Where it lives

| Task | Path |
|---|---|
| Assign an Azure role | **Azure portal > Resource groups > (Sentinel RG) > Access control (IAM) > Add > Add role assignment** |
| Same, from Sentinel | Azure portal: **Microsoft Sentinel > Settings > Workspace settings > Access control (IAM)** |
| Activate URBAC for Sentinel | **Defender portal > System > Permissions > Microsoft Defender XDR > Roles > Activate workloads** (or **Workload settings**) > **View Workspaces** |
| Alternative activation path | **Defender portal > System > Settings > Microsoft Defender XDR > Permissions and roles** |
| Grant Sentinel playbook permissions | Defender: **Settings > Sentinel > (workspace) > Playbook permissions** |

```bash
az role assignment create --assignee analyst@contoso.com \
  --role "Microsoft Sentinel Responder" \
  --scope /subscriptions/<sub-id>/resourceGroups/<sentinel-rg>
```

## Exam traps

- "Analyst must assign and close incidents but not create rules." ==+Responder==. Not ==!Contributor== (too much), not ==!Reader== (can't change incidents).
- "Analyst must also run playbooks by hand." Add ==+Playbook Operator==. ==!Responder alone cannot run playbooks.==
- "User must save a workbook but must not edit analytics rules." ==+Sentinel Reader (or Responder) + Workbook Contributor==, not Sentinel Contributor.
- "Guest user from a partner can't assign incidents." Add the Entra role ==+Directory Reader== to their Responder role.
- "Least privilege for Sentinel to run playbooks from automation rules." ==+Automation Contributor on the playbook's resource group, for Sentinel's service account.== ==!Giving users Automation Contributor== is the distractor.
- "Where to assign for least maintenance?" ==+The resource group containing the workspace.== Workspace-only scope also needs the SecurityInsights solution resource.
- "User with Sentinel Reader edits a rule — how?" They also hold ==!Azure Contributor== or Owner. Roles add up.
- "Manage Playbook Operator in Defender unified RBAC." ==!Not supported== — it stays in Azure.

## Skip

- **Skip:** unit 2–4 and 6 of the workspace module (workspace design, Azure Lighthouse, Sentinel settings). Off-blueprint for this bullet; Lighthouse is MSSP work, not exam material.
- **Skip:** the full URBAC permission catalogue (Live response, Exposure Management, Defender for Cloud Apps mappings). Know the three Sentinel rows of the mapping table and the three roles that stay in Azure.
- **Skip:** GDAP and multitenant URBAC notes. They are in flux and MSSP plumbing. The docs contradict each other: *Activate URBAC* says assigning to a GDAP user group is ==!not supported==; the *Manage RBAC* overview says it is. If asked, the activation article (the procedure page) is the safer bet.
- **Skip:** Sentinel scoping (row-level RBAC) setup — scope tags, table tagging, DCR permissions. Know the name and that it needs URBAC.
- **Skip:** the data lake custom-role specifics (`microsoft.operationalinsights/workspaces/tables/write` and friends). Know the split: SIEM = Azure RBAC, data lake = Entra roles.
- **Skip:** Table-level RBAC implementation. Know the name and the purpose only.
