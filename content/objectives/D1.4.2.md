## Azure first

- **Custom detection rule** — a saved Advanced hunting query that runs on a timer and raises alerts (built in D1.4.1).
- **Incident** — a case file in the Defender portal that groups related alerts. Defender's **correlation engine** decides which alerts land in the same incident.
- **Analytics rule** — Microsoft Sentinel's own detection rule (D1.4.3). If Sentinel is onboarded to the Defender portal, both rule kinds show up in one list.
- **Permissions** — to manage a rule you need the same rights you need to create it: Defender *Security settings (manage)* or Entra **Security Administrator** for Defender data (Entra **Security Operator** also works, but only if Defender for Endpoint RBAC is off — otherwise it also needs *Manage security settings*), Azure **Microsoft Sentinel Contributor** for Sentinel data. A rule querying several products needs rights on all of them.
- **Licence:** custom detections need Defender services. With an Azure subscription only, this is a portal tour.

New to these? Read the Foundations pages linked above.

## In one sentence

Managing custom detections means using one list in the Defender portal to see when each rule last ran and whether it worked, then running, editing, turning off, deleting or un-correlating rules, and reviewing the alerts and actions each one triggered.

## Why it exists

A smoke alarm you never test is worse than none — you trust it while it is silent. Detection rules are the same. Queries break when a table changes. A noisy rule buries real alerts. A rule that isolates laptops can do damage if it misfires. You need one place to check every alarm's health, read its log and switch it off.

## What actually matters

1. **One list for both rule kinds.** `Hunting > Custom detection rules` shows custom detections and, once Sentinel is onboarded to the Defender portal, Sentinel **analytics rules** too. **+ Create detection rule** opens the creation wizard (D1.4.1) from the same list. Filter with **Add filter**, search by **rule name or rule ID**, and filter multi-workspace setups by **Workspace ID** or **Workspace name**.
2. **Four run columns.** **Last run**, **Last run status** (custom detections only), **Next run** and **Status** (on/off). A failing rule shows here first. Through the Graph API a rule's status can also read ==@autoDisabled==.
3. **Rule details page actions.**
   - **Run** — runs now and ==@resets the interval== to the next run. Custom detections only.
   - **Edit** opens the full wizard. **Modify query** opens just the query in Advanced hunting.
   - **Turn off** keeps the rule. **Delete** turns it off and ==!removes it permanently==. Prefer Turn off while unsure.
   - **Open detection rule page** — custom detections only.
4. **Triggered alerts** tab — set an alert's status and classification (true or false alert), link it to an incident, or rerun the query that fired it. **Triggered actions** tab — what the rule actually did to devices, files, users or mail.
5. **Correlation switch.** The correlation engine merges alerts into bigger "attack story" incidents.
   - **Custom detections:** **Include or exclude from correlation** per rule (public preview). Included by default. No tenant-wide setting.
   - **Sentinel analytics rules:** a tenant default at `System > Settings > Microsoft Defender XDR > Rules > Incident correlation`. ==@It is off by default==, so analytics rules start excluded. Override one rule by putting `#INC_CORR#` or `#DONT_CORR#` at the **start** of its description (case-insensitive). The wizard's **Incident correlation** dropdown (Tenant default / Enabled / Disabled) writes the tag for you.
   - **Alert-grouping rules** still have the final say. Changing correlation does not touch alerts already created.
6. **What you can't do yet.** Custom detections can't rerun over a past time window, and have no health workbooks or `SentinelHealth`-style health table (planned). Rule audit events appear in `CloudAppEvents` for Defender for Cloud Apps users.

## Where it lives

**Portal: Microsoft Defender portal** (`security.microsoft.com`).

| Task | Path |
|---|---|
| List, filter, search rules | `Investigation & response > Hunting > Custom detection rules` |
| Rule actions, triggered alerts and actions | Select the rule name → details page |
| Analytics-rule correlation default | `System > Settings > Microsoft Defender XDR > Rules > Incident correlation` |
| API | Microsoft Graph `security/rules/detectionRules` (status: `enabled`, `disabled`, `autoDisabled`) |

Microsoft's own pages name the list three ways: *Custom detection rules*, *Custom detections* and *Detection rules*. They are the same page.

## Exam traps

- ==!Delete is reversible.== ==+Delete is permanent; Turn off keeps the rule.==
- ==!Run waits for the next scheduled slot.== ==+Run executes now and resets the interval.==
- ==!Analytics rules join Defender correlation by default.== ==+Tenant default is off; use `#INC_CORR#` to include one rule.==
- ==!Custom detections are excluded from correlation by default.== ==+They are included by default; exclusion is per rule (preview).==
- ==!The tag can go anywhere in the description.== ==+It must be at the very start.==
- ==!Excluding a rule regroups its old incidents.== ==+Only new alerts are affected.==
- ==!You can rerun a custom detection over last Tuesday.== ==+Not supported yet; that's an analytics-rule feature.==
