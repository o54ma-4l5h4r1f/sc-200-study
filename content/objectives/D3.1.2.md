## Azure first

- **KQL** (Kusto Query Language) is the read-only language for every log table in Sentinel, Log Analytics and Defender advanced hunting. The **KQL basics** Foundation covers `where`, `project`, `extend`, `summarize`, `bin`, `top`, `let`, `union`, `join` and `has` vs `contains`. This page builds on it — it does not repeat it.
- A **Log Analytics workspace** is the Azure database that Sentinel tables live in. Its time column is `TimeGenerated`.
- **Defender XDR tables** in advanced hunting use `Timestamp` instead (see D3.1.1).
- **Threat hunting** means *you* go looking for an attacker that no alert has caught yet. You start with a guess ("someone is spraying passwords") and write a query to prove or kill it.
- **Practise free:** every query on this page marked *demo* runs in the Log Analytics demo environment — no subscription needed. Queries marked *Defender* need advanced hunting.

New to these? Read the Foundations pages linked above.

## In one sentence

Hunting with KQL means turning a suspicion into a query — filter to the right rows, reshape them, correlate them with other tables, and count until the odd thing stands out — and the exam tests whether you can **read** such a query and say what it returns as much as whether you can write one.

## Why it exists

Alerts only fire for attacks someone already wrote a rule for. A hunter asks the questions no rule asks yet. "Which account failed 30 times and then got in?" "Which program ran on only one laptop in the whole company?" "Did anyone sign in from a country they have never used before?"

Think of a detective with a filing cabinet of CCTV logs. The detective does not watch every tape. They pull the tapes for one door, one night (filter), list who walked through (project), count visits per person (summarize), and compare with last month's list (join). Whoever is new and unusual gets a closer look. That is a hunting query.

## Mental model

Data flows **left to right through the pipe** (`|`): everything left of a pipe runs first, and its output table becomes the input of the next line.

![Diagram of K Q L Statement showing data, condition, and evidence.](https://learn.microsoft.com/en-us/training/wwl-sci/construct-kusto-query-language-statements/media/kql-pipe.png){One statement: a table (data), piped through filters (condition), out to a result (evidence)}

Almost every hunting query is the same five-station funnel. When you **read** a query, find each station. When you **write** one, fill them in order.

## What actually matters

### 1. Reading a query — the skill the exam rewards most

Most SC-200 KQL items show a query and ask what it returns, or ask you to pick the missing line. Use this four-question drill on every query:

1. **Which table, which time window?** (first line, first `where`)
2. **Which rows survive?** (each `where`, in order)
3. **What is one output row?** (look at the *last* `summarize … by` — the `by` columns are the row key)
4. **Which columns come out?** (the last `project`, or the `summarize` columns)

Try it on the two statements from the training module. They use the same lines in a different order.

```kql
// Statement 1 (demo)
SecurityEvent
| summarize arg_max(TimeGenerated, *) by Account
| where EventID == 4624
```

```kql
// Statement 2 (demo)
SecurityEvent
| where EventID == 4624
| summarize arg_max(TimeGenerated, *) by Account
```

`arg_max(TimeGenerated, *)` keeps the **whole most recent row** per group. Statement 1 returns accounts whose **very last event was a logon**. Statement 2 returns **every account's most recent logon**, whatever happened after it. Same operators, different answers. ==!The order of the pipe changes the result.==

### 2. Filter, shape and sort — the parts beyond the basics

| Operator | What it does | Note |
|---|---|---|
| `search "term"` | Looks for a term in **every column of every table** | Easy but slow. Prefer `search in (SecurityEvent, SigninLogs) "term"` or, better, `where` on one column |
| `where … between (a .. b)` | Keeps values in a range | Works on times: `between (ago(2d) .. ago(1d))` |
| `has_any (list)` / `in~ (list)` | Matches any of several terms / values | `in~` ignores case |
| `=~` / `!=` / `!in` | Case-insensitive equals / not equals / not in a list | `AccountType =~ "user"` |
| `project-away` | Drops the columns you name | Opposite of `project` |
| `project-keep` / `project-rename` / `project-reorder` | Keep by name / rename / reorder | `project` can do all three at once |
| `order by` / `sort by` | Same operator, two names | Default is **descending** |
| `distinct A, B` | One row per unique combination | Same as `summarize by A, B` with no function |

```kql
// demo — logons with a calculated column, sorted, unneeded column dropped
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID in (4624, 4625)
| extend Outcome = iff(EventID == 4624, "Success", "Failure")
| project-away SourceSystem
| order by TimeGenerated desc
```

### 3. Aggregating — `summarize` and its functions

`summarize` collapses many rows into one row per group. The functions you will meet:

| Function | Returns |
|---|---|
| `count()`, `countif(cond)` | Rows per group / rows matching a condition |
| `dcount(col)`, `dcountif()` | **Distinct** values per group (an estimate) |
| `min()`, `max()`, `minif()`, `maxif()`, `avg()`, `sum()`, `percentile()` | The usual maths |
| `arg_max(col, *)` / `arg_min(col, *)` | The whole row with the largest / smallest value — "latest event per user" |
| `make_set(col)` | A JSON array of the **distinct** values |
| `make_list(col)` | A JSON array of **all** values, duplicates kept |
| `take_any(col)` | Any one value — handy for an example |

Name your result columns (`Failures = count()`). Unnamed, `count()` becomes `count_`.

```kql
// demo — brute force that succeeded: 10+ failures then a success, same account and computer, same hour
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID in (4624, 4625)
| summarize Failures = countif(EventID == 4625),
            Successes = countif(EventID == 4624),
            FirstFail = minif(TimeGenerated, EventID == 4625),
            LastSuccess = maxif(TimeGenerated, EventID == 4624)
            by Account, Computer, bin(TimeGenerated, 1h)
| where Failures >= 10 and Successes > 0 and LastSuccess > FirstFail
```

Read it out loud: *per account, computer and hour, count failures and successes, note the first failure and the last success; keep hours with 10+ failures followed by a success.* No `join` needed — `countif` and `minif` did the correlation inside one table.

`render` turns the result into a chart: `timechart`, `barchart`, `columnchart`, `piechart`, `areachart`, `scatterchart`.

### 4. Correlating — `union`, `join` and the default-join trap

`union` **stacks** rows from tables that hold similar things. Add `withsource=` to learn which table each row came from (every Log Analytics row also carries a `Type` column with its table name). Wildcards work. Watch the pipe: `SecurityEvent | union SigninLogs | summarize count()` returns **one** number for both tables, but `SecurityEvent | union (SigninLogs | summarize count())` returns every SecurityEvent row **plus one** count row — the summarize only ran inside the brackets.

```kql
// demo — row counts for every table whose name starts with Security
union withsource = SourceTable Security*
| where TimeGenerated > ago(1d)
| summarize count() by SourceTable
```

`join` **lines up** two tables side by side on a shared column. The first table is the **left**, the one in brackets is the **right**. When the key column has different names, write `on $left.Account == $right.TargetAccount`.

==!The default join kind is `innerunique`==, which **de-duplicates the left side** by the key first. If one attachment hash was sent in five emails, the default join can show only one of them. ==+Write `kind=inner` when you want every match.== For hunting "what is new", use `kind=leftanti` — left rows with **no** match on the right. All the flavours:

| `kind=` | Output |
|---|---|
| *(none)* / `innerunique` | Left de-duplicated on the key, then one row per match with the right |
| `inner` | One row for **every** matching left–right combination |
| `leftouter` / `rightouter` | Every left (right) row; unmatched cells from the other side are null |
| `fullouter` | Every row from both sides; nulls where no match |
| `leftsemi` / `rightsemi` | Left (right) rows that **have** a match — that side's columns only |
| `leftanti` / `rightanti` (also `leftantisemi`, `rightantisemi`) | Left (right) rows with **no** match |

![Diagram of Example join types, showing where how joins work.](https://learn.microsoft.com/en-us/training/wwl-sci/build-multi-table-statements-kusto-query-language/media/kusto-query-language-m03-01.png){Join flavours: which rows survive from the left (blue) and the right side}

```kql
// demo — successful sign-ins from a country this user has not used in the previous 14 days
let known = SigninLogs
    | where TimeGenerated between (ago(14d) .. ago(1d))
    | where ResultType == "0"
    | extend Country = tostring(LocationDetails.countryOrRegion)
    | distinct UserPrincipalName, Country;
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == "0"
| extend Country = tostring(LocationDetails.countryOrRegion)
| join kind=leftanti known on UserPrincipalName, Country
| project TimeGenerated, UserPrincipalName, Country, IPAddress, AppDisplayName
```

Events close in time: join, then check the gap (Microsoft's best-practices pattern):

```kql
// Defender — a logon within 30 minutes of receiving a malware email
EmailEvents
| where Timestamp > ago(7d)
| where ThreatTypes has "Malware"
| project EmailReceivedTime = Timestamp, Subject, SenderFromAddress,
          AccountName = tostring(split(RecipientEmailAddress, "@")[0])
| join (
    DeviceLogonEvents
    | where Timestamp > ago(7d)
    | project LogonTime = Timestamp, AccountName, DeviceName
  ) on AccountName
| where (LogonTime - EmailReceivedTime) between (0min .. 30min)
```

Join hygiene from the same page: **smaller table on the left**, **time filters on both sides**, **project only needed columns** before joining.

### 5. `let`, `materialize` and functions — name things once

`let` binds a name to a value, a list, or a whole sub-query. It ends with a semicolon. `datatable` builds a small table inline; `dynamic([…])` builds a list.

```kql
// Defender — sweep several tables for known-bad hashes (an IOC sweep)
let badHashes = dynamic(["<sha256-1>", "<sha256-2>"]);
union withsource = SourceTable DeviceFileEvents, DeviceProcessEvents, EmailAttachmentInfo
| where Timestamp > ago(30d)
| where SHA256 in (badHashes)
| project Timestamp, SourceTable, DeviceName, FileName, SHA256
```

When a `let` sub-query is used **more than once**, KQL normally runs it each time. Wrap it in ==@`materialize()`== to run it once and cache the result for the rest of the query (cache limit **5 GB** per cluster node).

```kql
// demo — password spray: one IP failing against many users; compute failures once, use twice
let failed = materialize(
    SigninLogs
    | where TimeGenerated > ago(1d)
    | where ResultType != "0"
    | project UserPrincipalName, IPAddress);
let sprayIPs = failed
    | summarize Users = dcount(UserPrincipalName) by IPAddress
    | where Users >= 5
    | project IPAddress;
failed
| where IPAddress in (sprayIPs)
| summarize Attempts = count() by IPAddress, UserPrincipalName
```

A **function** is a saved query you call by name like a table. Save from the Logs page with **Save > Save as function**. Add **parameters** and call it like `AzureActivityByCategory("Administrative", ago(7d))`. Sentinel's ASIM parsers are parameterized functions.

### 6. Getting values out of text — `extract`, `parse`, `parse_json`, `mv-expand`

Logs often hide the useful bit inside a string. Four tools:

| Tool | Use when | Cost |
|---|---|---|
| `parse` | The text has a fixed shape: literal words between the values | Cheap — ==+prefer it== |
| `extract(regex, group, text)` | The shape varies; you need a regular expression | Slower |
| `parse_json()` / dot notation | The column is JSON (type `dynamic`) | `Col.key` or `Col["key"]` |
| `mv-expand` | A column holds an **array**; you want one row per element | Copies the other columns onto each new row |

`parse` has three modes: `simple` (default — strict), `regex`, and `relaxed` (types may partly match). Values that fail to parse come back **null**.

```kql
// demo — pull user and source IP out of sshd failure messages in Syslog
Syslog
| where TimeGenerated > ago(7d)
| where ProcessName == "sshd" and SyslogMessage has "Failed password"
| parse SyslogMessage with * "Failed password for " User " from " SrcIP " port " SrcPort:int *
| summarize Attempts = count() by SrcIP, User
| top 10 by Attempts
```

```kql
// demo — dot notation into dynamic columns, then one row per authentication step
SigninLogs
| where TimeGenerated > ago(1d)
| extend OS = tostring(DeviceDetail.operatingSystem),
         ErrorCode = tostring(Status.errorCode)
| mv-expand AuthStep = parse_json(AuthenticationDetails)
| extend Method = tostring(AuthStep.authenticationMethod)
| summarize count() by Method, OS
```

Why Syslog needs this: the Syslog collector dumps the whole message into one string column, `SyslogMessage`. CEF data lands in `CommonSecurityLog` **already split into columns**. Save your parse query as a **function** (a "parser") and later queries call it by name instead of re-parsing.

`extract` returns capture group `1`, `2`… (`0` = the whole match) and **null** when nothing matches. The `*` in `parse` means "skip anything here". `mv-apply` runs a small sub-query on each array element. `externaldata` reads a CSV from a storage URL into a table (not available in the demo).

### 7. Time series — spot the spike automatically

```kql
// demo — hourly failed Windows logons, with anomalies flagged
SecurityEvent
| where TimeGenerated > ago(14d)
| where EventID == 4625
| make-series Failures = count() default = 0 on TimeGenerated from ago(14d) to now() step 1h
| extend (Anomalies, Score, Baseline) = series_decompose_anomalies(Failures, 1.5)
| mv-expand TimeGenerated to typeof(datetime), Failures to typeof(long), Anomalies to typeof(int)
| where Anomalies != 0
| project TimeGenerated, Failures
```

Read it: *build a 14-day hourly series of failures; decompose it into baseline + noise; expand the arrays back into rows; keep only flagged hours.* The threshold `1.5` is the default ("mild or stronger"); raise it (for example `2.5`) to flag only big spikes. ### 8. Threat-intelligence lookups — the table name changed

==!The training unit still queries `ThreatIntelligenceIndicator`.== The product docs say Sentinel ==!stopped ingesting into that legacy table after 31 July 2025==. ==+Current tables: `ThreatIntelIndicators` (indicators such as IPs, domains, hashes) and `ThreatIntelObjects` (other STIX objects — threat actors, attack patterns, relationships).== Product docs win. Both new tables use `TimeGenerated`. The indicator value sits in `ObservableValue`, its type in `ObservableKey` (for example `ipv4-addr:value`). Each indicator is re-published every 7–10 days, so take the latest row per `Id`.

```kql
// Sentinel — active IP indicators matched against today's sign-ins
let iocIPs = ThreatIntelIndicators
    | where TimeGenerated > ago(14d)
    | summarize arg_max(TimeGenerated, *) by Id
    | where IsActive == true and IsDeleted == false
    | where ObservableKey == "ipv4-addr:value"
    | project IPAddress = ObservableValue, Confidence;
SigninLogs
| where TimeGenerated > ago(1d)
| join kind=inner iocIPs on IPAddress
| project TimeGenerated, UserPrincipalName, IPAddress, Confidence
```

### 9. Five hunting patterns worth knowing by shape

| Pattern | Shape of the query |
|---|---|
| **Brute force → success** | `countif` failures and successes per account per `bin()`; keep both > 0 |
| **Password spray** | `dcount(UserPrincipalName) by IPAddress` over failures; high count = spray |
| **First seen / new** | Build a baseline with `let`, then `join kind=leftanti` the recent window against it |
| **Rare = suspicious** | `dcount(DeviceId) by FileName, SHA256`; keep files seen on 1–2 devices |
| **IOC sweep** | `let` a list of hashes/IPs/domains; `union` the tables; `where … in (list)` |

```kql
// Defender — rare processes: binaries seen on two devices or fewer this week
DeviceProcessEvents
| where Timestamp > ago(7d)
| summarize Devices = dcount(DeviceId), Example = take_any(ProcessCommandLine) by FileName, SHA256
| where Devices <= 2
| sort by Devices asc
```

### 10. Reading practice — say what it returns before you run it

Cover the answer, run the four-question drill, then check.

```kql
// demo — Query A
AzureActivity
| where TimeGenerated > ago(7d)
| where OperationNameValue endswith "/DELETE"
| where ActivityStatusValue == "Success"
| summarize Deletes = count(), Resources = make_set(_ResourceId) by Caller
| where Deletes > 5
```

**Answer A:** one row per **person or app** (`Caller`) that successfully deleted **more than five** Azure resources in the last week, with the list of distinct resource IDs they deleted. It does **not** show individual delete events — the `summarize` collapsed them.

```kql
// demo — Query B
SigninLogs
| where TimeGenerated > ago(1d)
| summarize Countries = dcount(tostring(LocationDetails.countryOrRegion)) by UserPrincipalName
| where Countries > 1
```

**Answer B:** users who signed in (successfully **or not** — there is no `ResultType` filter) from **two or more** countries today. Adding `| where ResultType == "0"` before the `summarize` would make it "successful sign-ins only". Spotting the *missing* filter is a classic exam question.

### 11. Write it so it runs fast

From Microsoft's advanced hunting best practices: **filter on time first**; **`has` beats `contains`**; look in a **specific column**, not `search *`; prefer **case-sensitive** operators (`==`, `has_cs`) when you can; **parse, don't extract** (regex is expensive); terms of **three characters or fewer** are not indexed. After a run, advanced hunting shows **resource usage** as Low, Medium or High.

## Exam traps

- ==!"`join` with no `kind` returns every match."== ==+Default is `innerunique`== — left side de-duplicated first. Use `kind=inner` for all pairs.
- ==!"`make_list` returns unique values."== ==+`make_set` is unique==; `make_list` keeps duplicates.
- **`arg_max(TimeGenerated, *)`** = the latest whole row per group. It is not "the max time only".
- **`where` before vs after `summarize`** gives different answers (Statement 1 vs 2 above).
- ==!`search` is the fast way to look everywhere.== It is the slowest. Scope it with `search in (…)` or use `where`.
- **`dcount` is an estimate.** Fine for hunting thresholds; do not expect an exact census.
- **`parse` failures return null**, not an error. A column full of blanks means your literal text did not match.
- **`mv-expand` multiplies rows.** Every other column is copied onto each new row.
- **`summarize … by bin()` leaves gaps** where nothing happened; **`make-series` fills them** with `default` — that is why anomaly functions need `make-series`.
- **`materialize()` only pays off** when the same `let` result is used more than once.
- **`order by` and `sort by` are the same operator**, default descending.
- ==!"Query threat indicators in `ThreatIntelligenceIndicator`."== ==+Use `ThreatIntelIndicators` / `ThreatIntelObjects`== — the legacy table stopped receiving data after 31 July 2025.
- **Query explorer vs Queries:** your saved queries vs Microsoft's predefined ones. **Microsoft Sentinel alert** (not Azure Monitor alert) creates an analytics rule.
- **`union` then `summarize`** counts everything; **`summarize` inside the union's brackets** counts only that table.
