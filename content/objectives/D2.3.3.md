## Azure first

- **Microsoft Graph** is the single web API (`https://graph.microsoft.com`) behind almost everything in Microsoft 365 and Entra ID: reading mail, listing users, adding app permissions. Outlook, Teams, the admin portals, scripts and attacker tools all call it.
- An **app registration / service principal** is how a program gets its own identity in Entra ID, with **scopes** (delegated permissions) or **roles** (application permissions).
- **Diagnostic settings** are the "send a copy of these logs somewhere" switch. Entra ID has its own, in the **Entra admin center**.
- A **Log Analytics workspace** is the Azure database where those logs land as tables, queried with **KQL** (Kusto). Microsoft Sentinel reads the same workspace.
- Licence: Graph activity logs need **Microsoft Entra ID P1 or P2**. A free Entra tenant (what an Azure-only subscription gives you) can't produce them.

New to these? Read the Foundations pages linked above.

## In one sentence

**Microsoft Graph activity logs** record **every HTTP request** the Microsoft Graph API receives for your tenant — who or what called (user, app, service principal), from which IP, which URL, which method, and the result code — and you collect them by sending the **MicrosoftGraphActivityLogs** category from Entra **diagnostic settings** to a Log Analytics workspace (or storage / Event Hubs) and querying the `MicrosoftGraphActivityLogs` table.

## Why it exists

Entra **sign-in logs** tell you someone got a token — the badge was issued at reception. Entra **audit logs** and Purview Audit tell you about certain *changes*. Neither shows the quiet **reading**: an attacker's tool calling `GET /users` ten thousand times to map your directory, or a malicious OAuth app reading mailboxes through the API.

Graph activity logs are the **CCTV in the corridors**. Every door the token opened is on tape. You join the tape to the reception log with a shared token ID to prove "this sign-in led to these API calls".

## What actually matters

**1. Prerequisites.**

| Need | Detail |
|---|---|
| Licence | ==@Microsoft Entra ID P1 or P2== (the Entra licensing table lists Graph activity logs as **No** for Free) |
| Role | **Security Administrator** — the least-privileged role that can create the diagnostic setting |
| Destination | An Azure subscription with a **Log Analytics workspace**, a **Storage account** (you need List Keys), or an **Event Hubs** namespace — created first |

The Sentinel Entra ID connector page says any Entra licence is enough for non-sign-in log types. The Graph and Entra licensing pages say P1/P2 for this log. Go with **P1/P2**.

**2. Turning it on.** Entra admin center > **Entra ID** > **Monitoring & health** > **Diagnostic settings** > **Add diagnostic setting** > tick **MicrosoftGraphActivityLogs** > choose the destination > **Save**. Or tick the *Microsoft Graph activity logs* log type in Sentinel's **Microsoft Entra ID** data connector, which streams the same category into the Sentinel workspace. Facts:

- **No filtering** in the diagnostic setting — all requests or nothing. Cut cost with a **workspace transformation** (drop rows/columns) or the **Basic** table plan.
- Events usually arrive within **30 minutes**, sometimes up to **2 hours**. A brand-new diagnostic setting can take up to **three days** to start.
- Only the **resource tenant's** traffic — you can't see what a multitenant app does in *another* tenant.
- Volume is big: Microsoft estimates about **15 GiB/month** of Azure Monitor logs for **1,000 users**.

**3. The columns you hunt with.**

| Column | Use |
|---|---|
| `UserId` / `ServicePrincipalId` / `AppId` | Who called — a user, an app identity, which client app |
| `IPAddress`, `UserAgent` | From where, with what tool (`Location` is only the Microsoft region that served the request) |
| `RequestMethod`, `RequestUri` | What: `GET` = read, `POST`/`PATCH`/`DELETE` = change; the resource path |
| `ResponseStatusCode` | `200` worked, `401`/`403` denied, `429` throttled |
| `Scopes`, `Roles`, `Wids` | Permissions in the token; `Wids` = the user's Entra directory roles |
| `SignInActivityId`, `UniqueTokenId`, `SessionId` | Join keys to sign-in logs |
| `ClientAuthMethod` | `0` public client, `1` client secret, `2` certificate |
| `ResponseSizeBytes`, `DurationMs` | How much data came back and how long it took — big responses hint at bulk reading |
| `ConditionalAccessStatus`, `DeviceId`, `TokenIssuedAt` | CA result recorded for the request, the device the auth came from, when the token was minted |
| `OperationId` | Same value for every request in one `$batch` call; unique otherwise |

Requests from the **Microsoft MCP Server for Enterprise** have `/enterprise` in `RequestUri`.

**4. What investigations it answers.** Everything a **compromised user** did through the API; every call by an app you consented to; unexpected **privileged application-permission assignments**; extreme call volumes; AI clients using Graph; and correlation to sign-ins.

**5. Two tables, two portals.** In a Log Analytics workspace / Sentinel the table is `MicrosoftGraphActivityLogs` (`TimeGenerated`, `UserId`, `IPAddress`). In the **Defender portal advanced hunting** a similar table is `GraphAPIAuditEvents` with different column names (`Timestamp`, `AccountObjectId`, `ApplicationId`, `IpAddress`, `TargetWorkload`). Read the question for which one it means. Two gotchas in the Defender table: the join key to sign-ins is `UniqueTokenIdentifier`, and `ResponseStatusCode` is a **string**, so compare to `"403"`, not `403`.

```kql
GraphAPIAuditEvents
| where Timestamp > ago(7d)
| where ResponseStatusCode in ("401", "403")
| summarize Failures = count() by AccountObjectId, ApplicationId, IpAddress, TargetWorkload
| sort by Failures desc
```

## Where it lives

| Task | Portal / tool | Path |
|---|---|---|
| Create the diagnostic setting | Microsoft Entra admin center (`entra.microsoft.com`) | **Entra ID** > **Monitoring & health** > **Diagnostic settings** |
| Same, via Sentinel | Microsoft Sentinel (Defender portal or Azure portal) | **Data connectors** > **Microsoft Entra ID** > log type *Microsoft Graph activity logs* (needs Sentinel Contributor + Security Administrator) |
| Query | Azure portal > workspace > **Logs** (or Entra admin center > **Entra ID** > **Monitoring & health** > **Log Analytics**); Defender portal > **Advanced hunting** only when that Sentinel workspace is connected to the Defender portal | table `MicrosoftGraphActivityLogs` |
| Defender-native table | Defender portal > **Advanced hunting** | table `GraphAPIAuditEvents` |

Top callers failing on groups (authorization errors):

```kql
MicrosoftGraphActivityLogs
| where TimeGenerated >= ago(3d)
| where ResponseStatusCode == 401 or ResponseStatusCode == 403
| where RequestUri contains "/groups"
| summarize UniqueRequests = count_distinct(RequestId) by AppId, ServicePrincipalId, UserId
| sort by UniqueRequests desc
| limit 20
```

What a risky user touched (needs Entra ID Protection's `AADRiskyUsers`):

```kql
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(30d)
| join AADRiskyUsers on $left.UserId == $right.Id
| extend resourcePath = replace_string(replace_string(replace_regex(tostring(parse_url(RequestUri).Path), @'(\/)+','/'),'v1.0/',''),'beta/','')
| summarize RequestCount = dcount(RequestId) by UserId, RiskState, resourcePath, RequestMethod, ResponseStatusCode
```

Tie API calls to the sign-in that issued the token:

```kql
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(7d)
| join kind=leftouter (union SigninLogs, AADNonInteractiveUserSignInLogs, AADServicePrincipalSignInLogs, AADManagedIdentitySignInLogs, ADFSSignInLogs
    | where TimeGenerated > ago(7d))
    on $left.SignInActivityId == $right.UniqueTokenIdentifier
```

Microsoft warns that calls from Microsoft's own apps might not all have a matching sign-in row, so expect some empty right-hand sides.

Throttled apps (`429`) — a sign of scripted enumeration:

```kql
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(3d)
| where ResponseStatusCode == 429
| summarize RateLimitedCount = count() by AppId, RequestMethod
| sort by RateLimitedCount desc
```

## Exam traps

- ==!Graph activity logs are on by default in Entra.== ==+You must create a diagnostic setting for the MicrosoftGraphActivityLogs category.==
- ==!Entra ID Free is enough.== ==+P1 or P2 is required.==
- ==!Global Administrator is the minimum role.== ==+Security Administrator is the least-privileged role.==
- ==!Filter the noisy requests in the diagnostic setting.== ==+You can't; use a workspace transformation or the Basic plan.==
- ==!Sign-in logs show what the attacker read.== Sign-in logs show the token being issued. **Graph activity logs** show each API call made with it.
- ==!Purview Audit already records every Graph read.== Audit records specific audited activities; Graph activity logs record **every HTTP request** to Graph.
- Join key: `SignInActivityId` ↔ `UniqueTokenIdentifier` (in `GraphAPIAuditEvents` the column is already called `UniqueTokenIdentifier`).
- `429` = throttled, `401/403` = denied — classic hunting filters.
- `MicrosoftGraphActivityLogs` (Log Analytics/Sentinel) vs `GraphAPIAuditEvents` (Defender advanced hunting).

## Skip

- **Skip:** the long `extract_all` URI-segment parsing in Microsoft's throttling query and the timechart query. Know the `429` filter.
- **Skip:** the warning about secrets leaking into request URIs (good hygiene, not tested).
- **Skip:** the 100,000-user cost row, Storage/Event Hubs pricing and national cloud availability.
- **Skip:** `ATContent`, `ATContentH`, `ATContentP` (reserved), `_BilledSize`, `_IsBillable`, `SourceSystem` columns.
- **Skip:** ARM template / `diagnosticSettings` REST setup. The portal path is what's tested.
- **Skip:** the other Entra log categories in the same picker (provisioning, network access, remote network health). They are D1 connector material.
