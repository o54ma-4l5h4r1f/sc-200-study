## Azure first

- **Advanced hunting** is the KQL query page in the Defender portal (`security.microsoft.com`). It holds two families of tables side by side: tables written by the **Defender products** and tables from your **Microsoft Sentinel workspace**.
- **Defender XDR tables** (`Device*`, `Email*`, `Identity*`, `CloudAppEvents`, `Alert*`) are filled by Defender for Endpoint, Office 365, Identity and Cloud Apps. They need those product licences. You do not create them.
- **Sentinel tables** (`SigninLogs`, `SecurityEvent`, `AzureActivity`, `Syslog` …) live in a **Log Analytics workspace** — an Azure database you create and pay for. Data connectors fill them.
- Every row has a **time column**. Defender tables call it `Timestamp`. Sentinel / Log Analytics tables call it `TimeGenerated`.
- With an Azure subscription only, you can practise the **Sentinel** half live (and in the free Log Analytics demo). The Defender half is a portal tour.

New to these? Read the Foundations pages linked above.

## In one sentence

Before you write a single `where`, you must name the **table** that holds the evidence — and in Microsoft's world the table name tells you which product recorded it, what kind of thing happened, and which time column to filter on.

## Why it exists

Think of a hospital records room. X-rays are in one cabinet, blood tests in another, admissions in a third. A doctor who asks "did this patient break a bone?" walks to the X-ray cabinet, not the blood-test one. Asking the wrong cabinet returns nothing, and "nothing" looks exactly like "no problem".

KQL is the same. `DeviceProcessEvents | where FileName == "mimikatz.exe"` returns zero rows. That is great news — unless the attacker ran it on a server that only sends `SecurityEvent` to Sentinel. The exam tests exactly this: given a question, **which table** answers it.

## Mental model

The table name is a sentence: **who recorded it** (prefix) + **what happened** (middle) + **event or snapshot** (suffix).

- `Device` + `Process` + `Events` → Defender for Endpoint saw a process start.
- `Email` + `Attachment` + `Info` → Defender for Office 365 describes an attachment (a fact, not an action).
- `Identity` + `Logon` + `Events` → Defender for Identity saw an authentication.

`*Events` tables are **things that happened** (a stream, one row per action). `*Info` tables are **descriptions of things** (a snapshot that is refreshed, one row per entity per refresh).

## What actually matters

### 1. The Defender XDR table families

These are the tables the exam names most. Learn the family, then the handful of members.

| Family | Tables you must know | Answers… |
|---|---|---|
| **Device** (Defender for Endpoint) | `DeviceProcessEvents`, `DeviceNetworkEvents`, `DeviceFileEvents`, `DeviceRegistryEvents`, `DeviceLogonEvents`, `DeviceImageLoadEvents` (DLL loads), `DeviceEvents` (everything else — antivirus, exploit protection), `DeviceInfo`, `DeviceNetworkInfo`, `DeviceFileCertificateInfo` | What ran, connected, wrote, changed, signed in **on a device** |
| **Device TVM** (Vulnerability Management) | `DeviceTvmSoftwareInventory`, `DeviceTvmSoftwareVulnerabilities`, `DeviceTvmSecureConfigurationAssessment` (+ `KB` tables) | What is installed and vulnerable — posture, not attacks |
| **Email** (Defender for Office 365) | `EmailEvents`, `EmailAttachmentInfo`, `EmailUrlInfo`, `EmailPostDeliveryEvents`, `UrlClickEvents` | Who got which mail, what was attached or linked, what happened after delivery (ZAP), who clicked |
| **Teams messages** | `MessageEvents`, `MessagePostDeliveryEvents`, `MessageUrlInfo` | The same questions for Teams chats |
| **Identity** (Defender for Identity + Entra) | `IdentityLogonEvents`, `IdentityQueryEvents`, `IdentityDirectoryEvents`, `IdentityInfo`, `IdentityAccountInfo`, `EntraIdSignInEvents`, `EntraIdSpnSignInEvents` | AD authentications, LDAP/DNS queries against DCs, directory changes, who an account is |
| **Cloud apps** (Defender for Cloud Apps) | `CloudAppEvents` | Activity inside Office 365 and other SaaS apps — mailbox rules, file sharing, admin actions |
| **Alerts** | `AlertInfo`, `AlertEvidence` | Alerts from every Defender product; join them on `AlertId` |
| **Behaviors** (preview) | `BehaviorInfo`, `BehaviorEntities` | Behaviors from Defender for Cloud Apps and UEBA |
| **Exposure graph** | `ExposureGraphNodes`, `ExposureGraphEdges` | Assets and the relationships between them — the raw data behind attack paths and hunting graphs |

Two naming changes catch people. The beta sign-in tables `AADSignInEventsBeta` and `AADSpnSignInEventsBeta` are replaced by ==@`EntraIdSignInEvents`== and `EntraIdSpnSignInEvents`; queries using the old names are migrated automatically. (The table pages give 19 October 2026 as the cut-over; the schema-changes log gives 9 December 2025. Either way, today the new names are the right answer.) Both need a **Microsoft Entra ID P2** licence to collect data. In Sentinel, the threat-intelligence table `ThreatIntelligenceIndicator` stopped receiving data on 31 July 2025; its replacements are `ThreatIntelIndicators` and `ThreatIntelObjects`.

### 2. Events vs Info — read the suffix

An `*Events` table answers **"what happened, when?"** An `*Info` table answers **"what is this thing?"** You almost always join one to the other.

Freshness differs too. **Event data** (processes, logons, mail) arrives almost as soon as the sensor sends it. **Entity data** (`DeviceInfo`, `IdentityInfo` …) is refreshed on a schedule with one new row per entity. ==!Sources disagree on the schedule:== the product article says tables are updated ==+every hour==; the older training unit says every 15 minutes. The product docs win.

```kql
// What did the sender attach? Events table (the mail) joined to an Info table (the attachment)
EmailEvents
| where Timestamp > ago(7d)
| where ThreatTypes has "Malware"
| join kind=inner EmailAttachmentInfo on NetworkMessageId
| project Timestamp, SenderFromAddress, RecipientEmailAddress, FileName, SHA256
```

Read it out loud: *mail from the last 7 days flagged as malware, matched to its attachments by the message ID, showing who sent what file to whom.* `NetworkMessageId` is the key that ties all `Email*` tables together. `AlertId` ties `AlertInfo` to `AlertEvidence`. `DeviceId` ties the `Device*` tables.

```kql
// Alerts from the last day and the devices / users they touched
AlertInfo
| where Timestamp > ago(1d)
| join kind=inner AlertEvidence on AlertId
| summarize Evidence = make_set(EntityType) by AlertId, Title, Severity, ServiceSource
```

### 3. Sentinel tables in the same page

When a Sentinel workspace is connected to the Defender portal, its tables appear in the **Schema** tab of advanced hunting, grouped by solution, **after** the Defender tables. You need at least **Microsoft Sentinel Reader** to query them there.

| Sentinel table | Holds | Typical question |
|---|---|---|
| `SigninLogs` | Microsoft Entra interactive sign-ins | Who failed MFA from a new country? |
| `AuditLogs` | Entra directory changes (users, groups, apps) | Who added themselves to a privileged group? |
| `AzureActivity` | Azure control-plane operations (subscription Activity log) | Who deleted the VM? |
| `OfficeActivity` | Office 365 audit (Exchange, SharePoint, Teams) | Who created an inbox forwarding rule? |
| `SecurityEvent` | Windows Security event log via the agent (4624, 4625, 4688 …) | Which servers saw failed logons? |
| `Event` | Other Windows event logs (for example Sysmon) | Sysmon process or network events |
| `Syslog` | Linux syslog messages | sshd failures on Linux |
| `CommonSecurityLog` | Firewalls / appliances sending CEF | What did the firewall block? |
| `AzureDiagnostics` | Resource logs from Azure services in diagnostics mode | Key Vault secret reads |
| `SecurityAlert` / `SecurityIncident` | Sentinel's own alerts and incidents | What did my analytics rules fire? |
| `ThreatIntelIndicators` / `ThreatIntelObjects` | Threat-intelligence indicators (STIX) | Is this IP on a TI list? |
| `Watchlist` | Imported watchlist rows (query with `_GetWatchlist()`) | Is this account on the VIP list? |

You can run these live, free, in the **Log Analytics demo** workspace:

```kql
// Runs in the Log Analytics demo — which tables actually have data, and how much?
union withsource = TableName *
| where TimeGenerated > ago(1d)
| summarize Rows = count() by TableName
| sort by Rows desc
```

```kql
// Failed Windows logons (event 4625) per computer — SecurityEvent, TimeGenerated
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4625
| summarize Failures = count() by Computer, Account
| top 10 by Failures
```

```kql
// Same idea for cloud identities — SigninLogs, ResultType "0" means success
SigninLogs
| where TimeGenerated > ago(7d)
| where ResultType != "0"
| summarize Failures = count() by UserPrincipalName, IPAddress
| top 10 by Failures
```

### 4. `Timestamp` vs `TimeGenerated`

| | `Timestamp` | `TimeGenerated` |
|---|---|---|
| Found in | Defender XDR tables in advanced hunting | Every Log Analytics / Sentinel table |
| Means | When the **event happened** | When the row was **generated/ingested** into the workspace |
| Retention in advanced hunting | **30 days** of native Defender data | Whatever **analytics-tier retention** the workspace has |

When Defender tables are **streamed into Sentinel**, they carry **both** columns. If a row reaches Log Analytics more than **48 hours** late, ingestion overwrites `TimeGenerated` with `now()`. So ==+for the real event time, use `Timestamp`==. Streaming Defender tables to Sentinel with a longer retention is also how you hunt **beyond 30 days** in advanced hunting.

```kql
// Defender table: filter on Timestamp
DeviceProcessEvents
| where Timestamp > ago(1d)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine has_any ("DownloadString", "EncodedCommand", "-enc")
| project Timestamp, DeviceName, AccountName, ProcessCommandLine
```

### 5. Which tier the table is in

In the unified portal, the schema pane shows each table's **schema type**: an **advanced** (analytics-tier) table supports full KQL; a **basic** or **Lake/Auxiliary** table does not. Advanced hunting reads only the **analytics** retention period. Older data kept only in the **data lake tier** is reached with **Data lake exploration > KQL queries** or a search job, not advanced hunting. Example from the docs: `SigninLogs` with 90 days analytics retention and two years total → advanced hunting sees only the latest 90 days.

==!Two Microsoft articles disagree on lake-only tables.== The advanced hunting overview says data stored *only* in the data lake "isn't available in advanced hunting". The Sentinel-in-Defender article's known issues say *new* Sentinel customers can query Analytics **and** Lake-tier tables there, and that lake tables may wrongly show **Advanced table** as their schema type (they should show **Lake / Auxiliary logs table** with a gold icon). For the exam, use the safe rule: ==+long-term lake data → Data lake exploration or a search job==.

### 6. Read the schema before guessing

Every table has a reference card: description, columns, the possible `ActionType` values and a sample query. Use it on exam day too — the Learn pane shows the same reference. `ActionType` is the column that tells you *which kind* of event a row is (for example `ConnectionSuccess`, `LogonFailed`, `FileCreated`).

```kql
// What event types does this table hold?
DeviceNetworkEvents
| where Timestamp > ago(1d)
| summarize count() by ActionType
```

## Exam traps

- ==!"Search `SigninLogs` in advanced hunting with `Timestamp`."== Sentinel tables use `TimeGenerated`. ==+Defender tables use `Timestamp`==; streamed copies in Sentinel have both.
- ==!`DeviceLogonEvents` for domain-controller authentication.== That is endpoint sign-ins. ==+AD authentications seen by Defender for Identity are in `IdentityLogonEvents`==; LDAP/DNS queries against DCs are `IdentityQueryEvents`.
- ==!`EmailEvents` for who clicked a link.== ==+Clicks are `UrlClickEvents`==; links inside the mail are `EmailUrlInfo`; ZAP and moves after delivery are `EmailPostDeliveryEvents`.
- ==!`CloudAppEvents` is the same as `OfficeActivity`.== One is the Defender for Cloud Apps table in advanced hunting; the other is Sentinel's Office 365 connector table. Similar data, different products and column names.
- ==!"Advanced hunting keeps Defender data for 90 days."== ==+30 days== for native Defender data; longer only via Sentinel analytics-tier retention.
- **`AlertInfo` vs `AlertEvidence`:** the alert's title/severity vs the entities it touched. Join on `AlertId`.
- **`SecurityEvent` vs `DeviceEvents`:** Windows event log collected by the Sentinel agent vs Defender for Endpoint sensor telemetry. Different source, different columns.
- **`ThreatIntelligenceIndicator`** in older training material is stale — current tables are `ThreatIntelIndicators` and `ThreatIntelObjects`.

## Skip

- **Skip:** memorising every column. The schema reference and the exam's Learn pane list them. Know the *key* columns: `Timestamp`, `DeviceId`/`DeviceName`, `AccountName`/`AccountUpn`, `ActionType`, `NetworkMessageId`, `AlertId`, `SHA256`, `ReportId`.
- **Skip:** the long tail of preview tables in the schema list (`CloudKeyVaultEvents`, `CloudStorageAggregatedEvents`, `CloudPolicyEnforcementEvents`, `DeviceBaselineCompliance*`, `DataSecurity*`, `AgentsInfo`, `CallActivityEvents`, `GraphAPIAuditEvents`, `FileMaliciousContentInfo`, `OAuthAppInfo`, `DisruptionAndResponseEvents`). Recognise the prefix; do not learn their columns.
- **Skip:** the `DeviceTvm*KB` knowledge-base tables. They describe vulnerabilities and configurations, not attacks — vulnerability management is off-blueprint for this exam.
- **Skip:** the query-logs module's table descriptions that still say "Azure Active Directory", "Azure Security Center" and "Log Analytics agent" (unit 4). The tables are right; the product names are old.
- **Skip:** `McasShadowItReporting` and `WindowsFirewall` from the same unit — rarely hunted, not tested.
- **Skip:** GCC-Moderate limitations on mixing Sentinel and Defender tables. Government-cloud detail.
