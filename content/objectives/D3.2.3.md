## Azure first

- A **Log Analytics workspace** stores data in **tables**. Each table has a **plan** or tier: **Analytics** (full KQL, rules, expensive), **Basic** and **Auxiliary** (cheap, limited queries), or the Sentinel **Data lake tier** (D1.2.2).
- A **custom log table** is a table you create. Its name always ends in `_CL`.
- An **analytics rule** is a scheduled detection in Sentinel. It can only read **Analytics**-tier tables.
- A **diagnostic setting** tells an Azure resource to send its own operational logs somewhere. Here it sends the workspace's summary-rule run log to the `LASummaryLogs` table.
- **Content hub** is Sentinel's store of installable content, including summary rule **templates**.

New to these? Read the Foundations pages linked above.

## In one sentence

A **summary rule** is a KQL query that the workspace runs **automatically every 20 minutes to 24 hours** over the latest slice of data (one **bin**), and writes the much smaller aggregated result into a **custom `_CL` table on the Analytics plan**, so you can query, alert and report on it fast and cheaply.

## Why it exists

Imagine a shop that gets 10,000 till receipts an hour. Nobody reads them all. Every hour a clerk writes one line per product: "coffee, 412 sold, first at 09:02, last at 09:58". The receipts go to cheap boxed storage. The managers read only the clerk's sheet.

Network and firewall logs are the receipts: terabytes a day of noisy, low-value rows. Keep the raw rows in a cheap tier (Basic, Auxiliary or data lake). A summary rule is the clerk. Its sheet is an **Analytics** table, so analytics rules, workbooks and hunting queries run on it at full speed.

Microsoft gives three reasons:

- **Analysis and reports** over big ranges, where raw queries time out.
- **Cost savings**: raw data stays cheap; only the summary pays Analytics prices.
- **Privacy**: the summary can drop or mask personal fields. Then you lock down the raw table.

The rule is a conveyor. Every bin it takes one slice of fresh raw data, shrinks it, and drops the result in a hot table. It never goes back in time.

## What actually matters

**1. Where and who.** Defender portal: **Microsoft Sentinel > Configuration > Summary rules**. Azure portal: **Microsoft Sentinel > Configuration > Summary rules**. The same feature also lives in Azure Monitor: **Log Analytics workspace > Settings > Rules > Summary rules** tab. In Sentinel you need **Microsoft Sentinel Contributor**. Under the hood the rule needs `Microsoft.OperationalInsights/workspaces/summaryLogs/write` and `.../tables/write`. ==@Log Analytics Contributor== has both. To use the Defender portal, the workspace must be onboarded to it.

**2. The wizard.** **+ Create**, then:

| Field | Meaning |
|---|---|
| **Name**, **Description** | free text |
| **Destination table** | **Existing custom log table** or **New custom log table**. Name ends ==@_CL== |
| **SummaryLogs** diagnostic setting | Recommended. It logs each run to `LASummaryLogs`. ==!It costs extra.== |
| **Set summary logic** | your KQL; **Preview results** |
| **Query scheduling** | how often it runs (the **bin size**), an optional **delay** in minutes, and the start time |
| **Review + create** | **Save** |

The table schema is built from your query. Extra standard columns are added: `_RuleName`, `_RuleLastModifiedTime`, `_BinSize`, `_BinStartTime`. If your output uses a reserved name such as `TimeGenerated` or `Type`, the original gets an `_Original` prefix.

**3. Bin size is the key setting.** Allowed values are **20, 30, 60, 120, 180, 360, 720 or 1440 minutes**. The bin is both how often the rule runs and the time slice it reads. ==!Don't put a time filter in the query==; it would intersect with the bin. The first run starts shortly after the next whole hour. By default each bin waits **3.5 minutes up to 10% of the bin size** for late data. You can set `binDelay` (up to 1,440 minutes) and `binStartTime` to control timing. ==!A summary rule can't process historical data==: it covers the recent past, up to **24 hours**.

```kql
// Summary rule query (bin = 60 min). No time filter: the bin supplies it.
CommonSecurityLog
| where DeviceAction in ("deny", "drop")
| summarize Attempts = count(), Ports = make_set(DestinationPort, 20),
            FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
    by SourceIP, DestinationIP, DeviceVendor
```

```kql
// Then hunt or alert on the small table, over months, in seconds
FirewallDenySummary_CL
| where TimeGenerated > ago(90d)
| where SourceIP == "203.0.113.50" or DestinationIP == "203.0.113.50"
| summarize TotalAttempts = sum(Attempts) by bin(_BinStartTime, 1d), _RuleName
```

**4. Query rules depend on the source table's plan.**

- **Analytics** source: almost all KQL works. Not allowed: cross-resource `workspaces()`, `app()`, `resource()`; cross-service `ADX()`, `ARG()`; and schema-reshaping plugins (`bag_unpack`, `narrow`, `pivot`).
- **Basic** source: single table, but you can `lookup` up to **five** Analytics tables.
- **User-defined functions** aren't supported. Microsoft's system functions are.
- ==!`union *` and `isfuzzy=true` are not supported.==
- ==!Federated tables can't be queried== by a summary rule (a KQL job can).
- Aim for a result of **0.01% or less** of the source volume, and a record size under **1 MB**.

**5. Managing rules.** Each row on the **Summary rules** page has a menu: view current data in **Logs**, **run history**, **Disable/Enable**, **Edit**. ==!Delete is irreversible.== A workspace allows ==@100 active rules==. To create a 101st, stop or delete one first. In Azure Monitor you can **Stop** and **Start** a rule. Failed bins are retried **10 times within 8 hours**, then skipped. After **8 consecutive** failed bin retries the rule is put on hold (`isActive: false`). You can **rerun a failed bin** from the portal. If someone deletes the destination table, the rule is **suspended** and a message lands in `LASummaryLogs`. Removing a field from the query doesn't remove the column. You can't add a **workspace transformation** to the destination table. Summary rules exist only in the **public cloud**, and not across tenants via **Azure Lighthouse**.

```kql
// Monitor runs (needs the Summary Logs diagnostic setting)
LASummaryLogs
| where Status == "Failed"
| project TimeGenerated, RuleName, BinStartTime, Status, Message

// Bins close to the 10-minute query limit
LASummaryLogs
| where QueryDurationMs > 0.9 * 600000
```

**6. Templates.** Install ready-made summary rules from **Content hub** (filter **Content type = Summary rules**). They then appear on the **Templates** tab of the Summary rules page. Select one and choose **Create**; the wizard opens prefilled.

**7. Price.** The rule itself is free. You pay for what it reads and writes:

| Source table plan | Query cost | Result cost |
|---|---|---|
| Analytics | none | Analytics ingestion of the results |
| Basic / Auxiliary | data scanned | Analytics ingestion of the results |

**8. Two Sentinel scenarios worth knowing.** (a) **Hunt a malicious IP over 90+ days**: a daily summary of every IP seen in `CommonSecurityLog`. Then a quick analytics rule on the summary finds when the IP appeared, even beyond raw retention. (b) **TI matching on noisy logs**: summarize an **Auxiliary** firewall table with a `lookup` against active threat indicators into a table such as `MaliciousIPDetection`. An analytics rule then alerts on that table. Microsoft's sample joins the legacy `ThreatIntelligenceIndicator` table; ==@ThreatIntelIndicators== is the current TI table, so write new rules against that.

**9. Summary rule vs KQL job vs search job.** Three look-alikes that all write results into a new table. Microsoft's own comparison:

| | Summary rule | KQL job (D3.2.2) | Search job (D1.2.2) |
|---|---|---|---|
| Source | Analytics, Basic, Auxiliary, data lake (not System tables) | data lake only | one table: Analytics, lake; or Basic/Auxiliary/archive without the lake |
| Needs data lake onboarding | ==+No== | ==!Yes== | No |
| Tables per query | several (Basic source: `lookup` up to 5 Analytics tables) | several, full joins/unions | ==!one== |
| Federated tables | No | Yes | No |
| Schedule | every 20 min to 24 h | on demand or scheduled (by minute, hourly, daily, weekly, monthly — see D3.2.2) | on demand |
| Look-back | ==!up to 1 day== | up to 12 years | up to 12 years (1-year span) |
| Timeout | 10 minutes | 1 hour | 24 hours |
| Max results | 500,000 records | depends on timeout | 100 million records |
| Price | free on Analytics source; data scan on Basic/Auxiliary; plus Analytics ingestion | GB analyzed | GB analyzed |
| Templates / health | ==+Content hub templates; `LASummaryLogs`== | template gallery (per the how-to; the comparison article says none — see D3.2.2) | none |

Rule of thumb: **frequent, recent, shrink it** → summary rule. **History, joins, lake** → KQL job. **One big table, hydrate it** → search job.

**Sources disagree on scope.** The comparison article says summary rules work in "any Microsoft Sentinel workspace connected to Microsoft Defender". The Sentinel article and the Azure Monitor article still show them in the Azure portal and in any Log Analytics workspace. The product wins: both portals work today. The Azure portal for Sentinel retires after **31 March 2027**, so expect Defender-portal wording on newer questions.

## Where it lives

| Task | Path |
|---|---|
| Sentinel summary rules | Defender: **Microsoft Sentinel > Configuration > Summary rules**. Azure: **Microsoft Sentinel > Configuration > Summary rules** |
| Azure Monitor view | **Log Analytics workspace > Settings > Rules > Summary rules** |
| Templates | **Content hub** > Content type **Summary rules** > Install; then Summary rules > **Templates** |
| Run log | workspace **Diagnostic settings** > category **Summary Logs** > table `LASummaryLogs` |
| API / IaC | REST `.../workspaces/{ws}/summaryLogs/{rule}` (PUT, GET, DELETE; POST `/stop`, `/start`, `/retrybin` to rerun a failed bin), `az rest`, `Invoke-AzRestMethod`, Bicep/ARM `Microsoft.OperationalInsights/workspaces/summaryLogs` |

```powershell
# Create a 30-minute summary rule via REST from PowerShell
$body = @{ properties = @{ ruleType = "User"; description = "Blob ops per account"
  ruleDefinition = @{ query = "StorageBlobLogs | summarize count() by AccountName"
                      binSize = 30; destinationTable = "BlobOpsSummary_CL" } } } | ConvertTo-Json -Depth 10
Invoke-AzRestMethod -Method PUT -Payload $body -Uri "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.OperationalInsights/workspaces/<ws>/summaryLogs/BlobOps?api-version=<api>"
```

## Exam traps

- "Keep 1 TB/day of firewall logs cheaply but alert on them every hour." ==+Raw data in a low-cost tier; summary rule (bin 60) into an Analytics `_CL` table; analytics rule on that table.==
- "Summary rule to backfill last year." ==!Impossible== — it only processes the recent past (up to 24 h). ==+Use a KQL job== (data lake) or a search job.
- "Valid bin size of 15 minutes?" ==!No.== ==+20, 30, 60, 120, 180, 360, 720, 1440.==
- "Destination table name `FwSummary`." ==!Must end in `_CL`.==
- "What plan is the destination table on?" ==+Analytics==, always.
- "Where do you see failed runs?" ==+`LASummaryLogs`==, after enabling the **Summary Logs** diagnostic setting.
- "Query has `| where TimeGenerated > ago(1h)` and returns too little." ==+Remove the time filter== — it intersects with the bin.
- "101st rule fails to save." ==+Limit is 100 active rules per workspace.== Stop or delete one.
- "Role to create summary rules in Sentinel." ==+Microsoft Sentinel Contributor.==
- "Deleted a summary rule by mistake — restore it?" ==!Deletion is irreversible.==
- "Need summarization every 20 minutes on a workspace not onboarded to the data lake." ==+Summary rule==, not a KQL job.
- "Pull one huge table's old archived data into an Analytics table for a forensic case." ==!Not a summary rule== (1-day look-back). ==+Search job.==
- "Summary rule over a federated table." ==!Not supported.== ==+KQL job.==

## Skip

- **Skip:** the full aggregation-timing tables (`binStartTime` and `binDelay` worked examples). Know the default delay rule and that you can change start time and delay.
- **Skip:** the CLI / PowerShell / REST / Bicep / ARM tab walkthroughs. Know that an API and templates exist. The portal wizard is what gets tested.
- **Skip:** customer-managed-key encryption of summary queries, data export rules, `retryBinStartTime` formats and waiting for `provisioningState` = `Succeeded` between API changes. Edge cases.
- **Skip:** the `ContainerLogV2` container example. It shows the idea; the Sentinel scenarios (IP hunting, TI matching) are the exam-shaped ones.
- **Skip:** cost formulas per bin. Know only "free rule; pay for scan (Basic/Auxiliary) and for Analytics ingestion of results".
- **Note:** the old Sentinel tutorial *Summarize insights from raw data in an Auxiliary table* now redirects to the KQL jobs article. Microsoft steers lake-scale summarizing towards KQL jobs.
- **No training unit covers this bullet.** It is written entirely from product documentation.
