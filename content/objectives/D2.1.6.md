## Azure first

- **Active Directory (AD)** is the *on-premises* user directory most companies still run on their own Windows servers. The servers that hold it are **domain controllers (DCs)**. Every Windows sign-in at the office is checked by a DC. This is not the same thing as **Microsoft Entra ID**, the cloud directory — many companies sync one to the other.
- **Kerberos** and **NTLM** are the two ways Windows proves who you are to a DC. Attackers steal the *tickets* (Kerberos) and *password hashes* (NTLM) these produce, then replay them. That is what most Defender for Identity alerts are about.
- **Microsoft Defender for Identity (MDI)** — formerly *Azure Advanced Threat Protection (Azure ATP)* — is a small program — a **sensor** — on each DC that watches that traffic and reports to the cloud. Its alerts show up in the **Microsoft Defender portal** (`security.microsoft.com`).
- **Licence:** MDI needs a Microsoft 365 E5 / E5 Security or standalone MDI licence *and* real domain controllers. An Azure-only learner has neither, so this lesson is a **portal tour**: the screenshots below are the lab.

New to these? Read the Foundations pages linked above.

## In one sentence

Defender for Identity puts a sensor on every domain controller, raises an alert when someone uses Active Directory the way an attacker does, and lets you **disable the account, force a password change or revoke sessions** straight from the Defender portal.

## Why it exists

Think of an office building where every door badge is checked at one front desk. A thief who copies a badge looks like a normal employee to every door. Only the front desk sees that "Alice" just badged in on floor 2 and floor 9 in the same minute.

The DC is that front desk. Endpoint antivirus sees one laptop. It cannot see that a stolen Kerberos ticket is being replayed across ten servers. MDI watches the desk itself, so it catches **credential theft, lateral movement** (hopping from machine to machine with stolen credentials) and **domain dominance** (the attacker owning AD itself).

## What actually matters

**1. Sensors: where they go, which version.** The sensor runs on **domain controllers**, and also on **AD FS**, **AD CS** and **Microsoft Entra Connect** servers. **Sensor v3.x** is for Windows Server 2019 or later. On a server already onboarded to Defender for Endpoint you just *activate* it; otherwise you run the v3.x onboarding package. **Sensor v2.x** is a separate install for Windows Server 2016 or earlier (and for VPN integration or syslog, which v3.x lacks). Both can live in one workspace. A preview restriction means workspaces created from **October 2026** allow v2.x only on Windows Server 2016 or earlier.

**Scope has grown.** The training unit still says MDI uses *on-premises AD* signals. The current product docs say MDI monitors **on-premises AD, Microsoft Entra ID and other identity providers such as Okta** (through **API connectors**), and 2026 brought a run of new Entra ID alerts (for example *Possible use of a stolen session cookie*). Two Microsoft sources disagree; ==+the product docs win==. The sensor itself is still only for on-premises servers.

![Diagram of sensor deployment: use sensor v3.x on supported servers running Windows Server 2019 or later, and v2.x on earlier versions](https://learn.microsoft.com/en-us/defender-for-identity/deploy/media/deploy-defender-identity/sensor-deployment-decision.png){Which sensor goes where: v3.x on Windows Server 2019+, v2.x on older servers}

**2. Alert categories follow the attack chain.** MDI groups alerts by the phase of an attack. Know the names — questions ask "which category is this alert in?". The current *classic* categories are **Reconnaissance and discovery**, **Persistence and privilege escalation**, **Credential access**, **Lateral movement** and **Other**. Alerts in the newer **Defender format** use the ten MITRE-style categories instead (Credential Access, Lateral Movement, Discovery and so on). The **Detection source** field on an alert tells you which format you are looking at.

| Phase | What the attacker does | Example MDI alert |
|---|---|---|
| Reconnaissance / discovery | Maps users, groups, IPs | User and IP address reconnaissance (SMB); Network mapping reconnaissance (DNS) |
| Credential access | Steals or guesses passwords | Suspected brute-force attack |
| Lateral movement | Replays stolen tickets or hashes on other machines | Suspected pass-the-ticket; Suspected overpass-the-hash |
| Domain dominance | Owns AD itself | Remote code execution on a DC; DCShadow; Golden Ticket |

**3. The alert page.** Open from **Incidents & alerts > Alerts**. Top: the **Accounts**, **Source Host** and **Destination Host**. Then the **Alert story** (**What happened** + **Alert graph**), **Important information**, **Activity details**, and a right-hand **details pane** for Manage alert, Export, Move alert to another incident and Classify. The alert queue shows the **last seven days** by default. **Export** downloads an Excel report — classic-format alerts only.

**4. Classify every alert.** **True positive (TP)** = malicious. **Benign true positive (B-TP)** = real but harmless, such as a penetration test. **False positive (FP)** = it did not happen. Classifying tunes MDI. To quieten a noisy-but-benign alert, use **Settings > Identities > Excluded entities** for classic alerts, or an **alert tuning rule** for Defender-format alerts.

**5. The identity page is where you investigate.** One person can own several accounts (AD, Entra ID, Okta…). Defender joins them into one **identity**. The tabs: **Overview**, **Incidents and alerts**, **Observed in organization** (devices, locations, groups — the blast radius), **Risk score** (0–100 likelihood of compromise, preview), **Timeline**, **Security recommendations**, **Attack paths** (possible **lateral movement paths** to or from this identity), **Policies**, **Identity Explorer** (preview, needs a Sentinel data lake licence) and **Microsoft Sentinel events**. The **Timeline** merges AD, Entra ID sign-ins, cloud app and device logon events for every linked account into one list.

**6. Remediate from the identity.** **Actions** menu on the identity page, the identity side panel, an **advanced hunting** result or the **Action center**. The five actions:

| Action | Works on | What it does |
|---|---|---|
| **Disable** | AD, Entra ID, Okta, CyberArk, SailPoint, some SaaS apps | Blocks sign-in until re-enabled. Deletes nothing. |
| **Enable** | AD, Entra ID, Okta, CyberArk, SailPoint, Salesforce | Undoes Disable |
| **Revoke session** | Entra ID, Okta | Kills active sessions |
| **Mark as compromised** | Entra ID | Sets user risk in Entra ID Protection |
| **Force password change** | AD, Entra ID | User must change password at next sign-in |

For AD accounts the action is carried out by the **sensor on a domain controller**, using the DC's **local system account**. Turn on **Automatically use the sensor's local system account** under **Settings > Identities > Microsoft Defender for Identity > Manage action accounts** — it is **required** for v3.x sensors. Sensors on AD FS, AD CS or Entra Connect servers never run remediation. For Entra ID accounts, Microsoft uses an enterprise app called **Microsoft Defender for Identity** (older tenants: *Radius Aad Syncer*). You need a Defender unified RBAC role with **Response (manage)**. For Entra ID accounts the Entra role matters too: **Security Operator** or **SOC Identity Responder** can run all five actions; **Mark as compromised** also works for **Security Administrator**. Track the result in the **Action center**. **Automatic attack disruption** can also fire these actions by itself.

## Where it lives

All in the **Microsoft Defender portal** (`security.microsoft.com`). There is no separate MDI portal any more.

| Task | Path |
|---|---|
| Alert queue | **Incidents & alerts > Alerts** (filter **Service sources** = Microsoft Defender for Identity) |
| Identity page | **Assets > Identities** > select the identity |
| Remediate | Identity page > **Actions** (or **Hunting > Advanced hunting** result, or **Actions & submissions > Action center**) |
| Action account setting | **Settings > Identities > Microsoft Defender for Identity > Manage action accounts** |
| Sensors | **Settings > Identities > On-premises > Sensor management** tab (lists deployed sensors and servers eligible for v3.x) |
| Detection exclusions (classic alerts) | **Settings > Identities > Excluded entities** |

In advanced hunting, identity actions need the user's SID (`AccountSid`, `OnPremSid` …) for AD, or `AccountObjectId` for Entra ID. The identity timeline is built from `IdentityLogonEvents`, `IdentityQueryEvents`, `IdentityDirectoryEvents`, `CloudAppEvents`, `DeviceLogonEvents`, `EntraIdSignInEvents`, `GraphAPIAuditEvents` and `AlertInfo`.

```kql
// Everything the sensor saw one account do on the DCs in the last day
IdentityLogonEvents
| where Timestamp > ago(1d)
| where AccountName =~ "alice"
| project Timestamp, ActionType, Protocol, DeviceName, DestinationDeviceName, IPAddress
```

## Exam traps

- "MDI only knows on-premises AD." ==!Outdated== (the training unit's view). Today MDI also takes Entra ID and Okta signals. But the **sensor** goes only on on-premises servers (DC, AD FS, AD CS, Entra Connect), and **user risk / sign-in risk** with risk-based Conditional Access is ==+Entra ID Protection== (D2.1.5).
- MDI's old name was ==@Azure ATP==. An answer naming "Azure Advanced Threat Protection" means MDI.
- "Remediation for an AD account needs a gMSA action account." Old answer. Today ==+the sensor's local system account== is the recommended setting and is **required** for v3.x.
- "Any sensor can disable a user." ==!Only sensors on domain controllers== run remediation. Sensors on AD FS / AD CS / Entra Connect don't.
- ==!Revoke session works on AD accounts== — no, Entra ID and Okta only. ==!Mark as compromised== is Entra ID only.
- **Disable** does not delete the account or its mail and files.
- Benign true positive vs false positive: a pen test **did happen** (==+B-TP==); a false positive means **the activity did not happen**.
- Classic vs Defender-format alerts can show **the same detection under two names**. The ==@Detection source== field tells you which.
- The **Export** to Excel and the **alert story graph** exist only on classic-format alerts.

## Skip

- **Three category lists.** The training module lists Reconnaissance, Compromised credential, Lateral movement, Domain dominance, Exfiltration. The MDI overview article uses similar *attack stages*. The alert catalogue (classic) uses Reconnaissance and discovery / Persistence and privilege escalation / Credential access / Lateral movement / Other, and Defender-format alerts use ten MITRE tactics. The catalogue is what the portal shows, so it wins. Learn the *phases*, not one exact list.
- **Every individual alert's description, MITRE ID and External ID** (the alerts-mdi-classic and alerts-xdr catalogues). Hundreds of rows. The exam asks what phase an attack is in, not detector IDs.
- **Sensor deployment detail** — `m365-threat-safeguard` unit 2 *Configure sensors* is off-blueprint (Npcap, gMSA setup, proxy, v2→v3 migration). Deployment belongs to D1; here you only need "sensor on the DC, v3.x on 2019+".
- **The Excel export's tab-by-tab column list.** Know Export exists for classic alerts; skip its schema.
- **Identity Explorer's ten predefined scenarios.** Preview, needs a Sentinel data lake licence. Know the tab exists and shows lateral movement paths.
- **Okta / CyberArk / SailPoint connector setup.** Know remediation reaches them; skip configuring them.
