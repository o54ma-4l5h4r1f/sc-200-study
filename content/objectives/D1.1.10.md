## Azure first

- An **incident** is the case file a SOC works: one or more **alerts** (single suspicious findings) grouped with the users, devices and IPs involved (**entities**). Automation rules act on incidents and alerts.
- An **analytics rule** is the scheduled query in Microsoft Sentinel that creates alerts (and usually incidents). Automation rules run *after* it.
- A **playbook** is an Azure Logic Apps workflow — a separate Azure resource in a **resource group** — that calls other systems. Automation rules can start one.
- **Azure RBAC roles** decide who can create rules, and whether Sentinel itself may start a playbook. You grant roles on a resource group.
- Sentinel now lives mainly in the **Defender portal** (`security.microsoft.com`). The Azure portal version stops being supported after **31 March 2027**.

New to these? Read the Foundations pages linked above.

## In one sentence

An automation rule is a no-code "if this incident or alert appears (or changes), and it matches these conditions, then do these actions, in this order" rule inside Microsoft Sentinel.

## Why it exists

Think of a hospital triage desk. Every patient who walks in gets a wristband, a colour and a ward before a doctor sees them. Nobody wants a doctor doing that by hand. Automation rules are the triage desk for incidents. They tag, assign, change severity, close known noise, add a checklist of tasks, and hand the hard cases to a playbook.

Before automation rules, each analytics rule had to call its own playbook. That meant the same response wired up 50 times. One automation rule can now cover **many analytics rules at once**, including future ones. Microsoft retired the old method: direct playbook calls from analytics rules ("Alert automation (classic)") can no longer be added to an analytics rule and were deprecated in March 2026.

The key idea: rules are **sequential**. Rule 2 sees the incident *after* Rule 1 changed it. If Rule 1 lowers severity from Medium to Low, a Rule 2 that only fires on Medium-or-higher will **not** run.

## What actually matters

**1. The three triggers (plus two new ones).**

| Trigger | Fires when | Notes |
|---|---|---|
| ==@When incident is created== | A new incident appears | Most common. Triage, assign, tag. |
| ==@When incident is updated== | Status, owner or severity changes; alerts, comments, tags or tactics are added | Escalation, ticket sync, reopen handling |
| ==@When alert is created== | A **Scheduled** or **NRT** analytics rule creates an alert | For rules with incident creation turned off. **Classic action set: Run playbook only.** Exception: Simple Flows (preview, Defender portal) adds **Update Alert** (status, classification, determination, assigned to). |
| **Case created / Case updated** (preview, "Simple Flows") | A case in the Defender portal is created or changed | Defender-portal onboarded workspaces only |

Microsoft recommends **incident-triggered** automation for most work. The incident is the living case file. Use the alert trigger mainly for alerts from analytics rules that **do not create incidents**. In the Defender portal, alert-trigger rules act only on **Microsoft Sentinel** alerts, not Defender XDR alerts. For those, Microsoft points to the **Enhanced Alert Trigger**.

**2. Conditions.** All conditions must be true (**AND**). For "this or that", use **condition groups** (**OR**). Conditions are case-insensitive. You can test incident properties (title, severity, status, tactics, analytic rule name, alert product names, owner), **entity properties** (for example an IP address or account name), tags and **custom details**.

- The **create** trigger checks the *current state*: equals, contains, starts with, ends with (and their "does not" twins).
- The **update** trigger adds *state-change* operators: **Changed**, **Changed from**, **Changed to**, **Added**. It also adds **Updated by** (user, application, playbook, automation rule, alert grouping, and so on). Use it to stop a rule firing on its own changes.
- The **alert** trigger has only one condition: **which analytics rule** made the alert.
- **Tags** have two operator families. **Any individual tag** is true if *at least one* tag matches. **Collection of all tags** judges the whole set. With "does not contain 2024", an incident tagged `2024` and `2023` is **true** for "any individual tag" and **false** for "collection".

**3. Actions** run top to bottom, and you can reorder them with the up and down arrows. Built-in: **Assign owner**, **Change status** (closing needs a classification reason and comment), **Change severity**, **Add tags**, **Add incident tasks** (a checklist on the incident) and **Run playbook**. Simple Flows (preview, Defender portal) adds **Send Case Created Email**, **Send Case Updated Email**, **Update Case**, **Add Task** (max **10 tasks per rule**) and **Update Alert**.

**4. Playbook matching.** Incident-trigger rules can only run **incident-trigger** playbooks. Alert-trigger rules can only run **alert-trigger** playbooks. Sentinel runs the playbook with its own service account. That account needs the **Microsoft Sentinel Automation Contributor** role on the playbook's resource group. To grant it you need **Owner** (or User Access Administrator) on that resource group. Ungranted playbooks appear greyed out. A long playbook does not block forever: after **2 minutes** the rule moves to its next action whether or not the playbook finished.

**5. Order and expiration.**

- Each trigger type has its **own queue**. All create-trigger rules finish before any update-trigger rules run.
- The portal fills the **Order** field with the next free number. API or command-line rules need it set by hand.
- Nothing stops two rules sharing a number. If they do, the engine picks their order **randomly**.
- **Rule expiration** (default *Indefinite*) disables the rule after a date and time. The classic use is closing noise during a planned penetration test.

**6. Three places to create a rule.** The **Automation** page (widest options; use it for many analytics rules or Defender XDR incidents). The **Automated response** tab of the analytics rule wizard (the rule is locked to that analytics rule). The **Incidents** page (pre-fills a suppression rule from one noisy incident: same name, that analytics rule, its entities as conditions, a **close** action and a suggested **expiration date**).

## Where it lives

| Task | Defender portal | Azure portal |
|---|---|---|
| Create / reorder / enable rules | **Microsoft Sentinel > Configuration > Automation > Automation rules** tab > **Create > Automation rule** | **Microsoft Sentinel > Configuration > Automation** > **Create > Automation rule** |
| Rule for one analytics rule | **Microsoft Sentinel > Configuration > Analytics** > rule > **Edit** > **Automated response** > **+ Add new** | Same path |
| Grant Sentinel playbook permissions | **Manage playbook permissions** link in the rule, or **Settings > Sentinel > (workspace) > Playbook permissions** | **Settings > Settings > Playbook permissions > Configure permissions** |
| Export / import as ARM JSON | Automation page > select rule > **Export** / **Import** | Same |

## Exam traps

- "Close all incidents from the pen-test scanner for the next two weeks with no code." ==+Automation rule with a close action and an expiration date==, not ==!a playbook==, and not ==!disabling the analytics rule== (that would blind you to real attacks).
- "An alert-trigger automation rule should also change severity." ==!Not possible== — ==+Run playbook is the classic alert-trigger action==. The preview Simple Flows **Update Alert** action can set status, classification, determination and owner — ==!not severity==.
- "Run a playbook on Defender XDR alerts using an alert-trigger rule in the Defender portal." ==!Alert-trigger rules only see Microsoft Sentinel alerts there.== Use incident triggers, or the Enhanced Alert Trigger.
- Order puzzles: Rule 1 lowers severity, Rule 2 needs Medium+. Rule 2 ==+does not run==. Rules with ==!the same order number do not run in parallel== — they run in ==+random sequence==, one at a time.
- "Which role lets Sentinel run the playbook?" ==+Microsoft Sentinel Automation Contributor, assigned to Sentinel's service account== on the playbook's resource group. ==!It is not for user accounts.== The *user* who attaches the playbook needs **Microsoft Sentinel Contributor**. The one who grants the role needs **Owner**.
- An incident-trigger rule ==!cannot run an alert-trigger playbook== (and vice versa).
- "Avoid a loop when a rule updates an incident." Use the update trigger's ==@Updated by== condition, and exclude "Automation rule".
- After onboarding to Defender, ==!the Incident provider condition is gone== and the `SecurityIncident` table has no **Description** field. Rules using either break. Use **Analytic rule name** instead.
