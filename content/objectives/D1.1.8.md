## Azure first

- **Defender XDR** joins signals from **Defender for Endpoint** (devices), **Defender for Identity** (on-premises Active Directory), **Defender for Office 365** (email) and **Defender for Cloud Apps** (cloud apps) into one **incident** — one attack story.
- **Microsoft Entra ID** is the cloud directory of user accounts. Disabling or suspending a user there stops their cloud sign-ins. **Active Directory** is the older on-premises directory; Defender for Identity can disable accounts there.
- **Containing** a device or user means every *other* onboarded device refuses to talk to it. **Isolating** a device means cutting that device off the network itself.
- **Device groups** in Defender for Endpoint carry an **automation level**. Attack disruption reads that level (see D1.1.9).

New to these? Read the Foundations pages linked above.

## Docs-only objective

No SC-200 training unit teaches this bullet. The training unit *Automate, investigate, and remediate* covers email AIR, not attack disruption. Everything below comes from the product documentation listed in the frontmatter.

## In one sentence

**Automatic attack disruption** is Defender XDR's emergency brake: when it is very sure an attack such as human-operated ransomware is in progress, it automatically **contains devices, disables or contains users and blocks IPs** so the attacker cannot spread — and leaves the clean-up and release to your team.

## Why it exists

AIR (D1.1.7) handles one alert at a time: quarantine this file, stop that process. Human-operated ransomware moves faster than a person can triage. An attacker with a stolen admin password can jump to fifty servers in minutes.

Attack disruption looks at the **whole incident**, not one alert. When the combined signals reach high confidence, it acts on the attacker's assets everywhere at once. Think of a fire door that closes itself when the building's sensors agree a fire is spreading. It does not put out the fire. It stops it reaching the next floor, and the fire brigade opens the door again afterwards.

## What actually matters

**1. What triggers it.** Not a single alert and not a rule you write. Defender correlates signals from many products into **one high-confidence incident**, identifies the assets the attacker controls, then acts. Microsoft keeps containment detectors at **99% or higher** confidence. The documented attack types are **human-operated ransomware**, **business email compromise (BEC)** and **adversary-in-the-middle (AiTM)** phishing. You cannot add your own disruption logic — that is what Sentinel automation is for.

**2. The response actions.** Each action is carried out by a specific product, so that product must be deployed.

| Action | Done by | What it does |
|---|---|---|
| ==@Contain device== | Defender for Endpoint | All onboarded devices block communication from the suspicious device. Works on **unmanaged** devices too. |
| ==@Contain IP== | Defender for Endpoint | Blocks an IP of an undiscovered / not-onboarded device. |
| Isolate device (preview) | Defender for Endpoint | Cuts an onboarded **workstation** off the network, except Defender services. Undone automatically after a set time window. |
| ==@Contain user== | Defender for Endpoint | All onboarded devices block the user's communication: sign-ins, file access, network paths. Limits lateral movement and remote encryption. |
| ==@Disable user== | Defender for Identity | Disables the account in Active Directory (and in Entra ID if synced). |
| Revoke user session | Microsoft Entra ID | Kills active sessions. |
| Suspend user in Entra | Microsoft Entra ID | Suspends the cloud account. |
| OAuth app compromise | Defender for Cloud Apps | Protective action on a compromised OAuth app. |
| Deny policy on AWS user / Suspend Okta user (preview) | Microsoft Sentinel connectors | Same idea on AWS IAM and Okta. |

**Disable user** depends on where the account lives. AD-only: done by Defender for Identity on a domain controller running its sensor. AD synced to Entra: done on the DC **and** in Entra. Cloud-only: done in Entra through a Microsoft-managed enterprise app called **Microsoft Defender for Identity** (older tenants: *Radius Aad Syncer*). Disabling in Entra does **not** need Defender for Identity deployed.

**Predictive shielding** is a sibling. It uses the same engine but acts *before* the attack spreads: **Safeboot hardening**, **GPO hardening**, **proactive user containment**. Its actions also show under **Performed by: AttackDisruption**. Do not confuse the two: disruption responds to an active attack, shielding anticipates the next step.

**3. "Configure" really means "meet the prerequisites".** There is no switch to turn it on. Meet these and it works:

| Area | Requirement |
|---|---|
| Licence | One of: Microsoft 365 E5/A5; M365 E3 + Microsoft Defender Suite; M365 E3 + EMS E5; M365 A3 + A5 Security; Windows 10/11 Enterprise E5/A5; EMS E5/A5; Office 365 E5/A5; or a standalone Defender for Endpoint Plan 2, Defender for Identity, Defender for Cloud Apps, Defender for Office 365 Plan 2 or Defender for Business. |
| Deployment | Deploy the Defender products. Wider deployment = more scenarios covered. Each action needs its product. |
| Defender for Endpoint | **Device discovery** set to **Standard discovery** (for *Contain device*). Sense agent **v10.8470** or later (for *Contain user*). Device-group **automation level** not set to *No automated response*. Works whatever the Defender Antivirus state (Active, Passive or EDR block mode). |
| Defender for Identity | Audit policies on domain controllers. **Action account** with rights to disable users (default: the DC's **LocalSystem**). Sensor on the DC that holds the account. |
| Defender for Cloud Apps | **Microsoft 365 connector** with **all** checkboxes, including Entra ID apps. |
| Defender for Office 365 | Mailboxes in **Exchange Online**. Mailbox auditing for at least `MailItemsAccessed`, `UpdateInboxRules`, `MoveToDeletedItems`, `SoftDelete`, `HardDelete`. |
| Okta / AWS (preview) | Sentinel workspace connected to the Defender portal with the provider connector. |
| Permissions to configure | Entra: Global Administrator, Security Administrator, User Administrator, Authentication Administrator, Privileged Authentication Administrator, Directory Writers, Helpdesk Administrator or Security Operator. |

**Automation level and disruption.** ==+Any *Semi* level still lets disruption act without manual approval.== ==!*No automated response* excludes that device group from automatic containment== — and also from AIR. Use it for very few devices.

Watch your own automation too. A script that re-enables every active employee's account can quietly undo a disruption.

**4. Exclusions.** Microsoft warns that excluding assets weakens protection. Where you need them:

| Exclusion | Where | Use for |
|---|---|---|
| User accounts | **Settings** > **Microsoft Defender XDR** > **Automated response** > **Identities** > **Add user exclusion** | Break-glass admins, service accounts |
| Device groups | … > **Devices** > **Device groups** tab > pick group > automation level | Critical servers, legacy systems |
| IP addresses / ranges / subnets | … > **Devices** > **Exclude IP** | Critical infrastructure ranges |
| Policy application (preview) | … > **Devices** > **Policy application** > **Create rule** on a device **tag** | Keep disruption on but switch off specific controls for tagged devices |

Identity exclusions affect both Defender for Identity and Defender for Endpoint actions. Permissions: with unified RBAC **off**, Security Administrator or Global Administrator. With unified RBAC **on**, **Security Operator** or higher, or **Core security settings (manage)**. A **Security Reader** can view exclusions but not change them.

**Opting out completely** is not a toggle. You open a **support case** titled *Attack disruption opt-out*. You still get the alerts; only the actions stop.

**5. Seeing that it happened.**

- Incident queue: an **Attack Disruption** tag.
- Incident page: the tag plus the threat type (for example *ransomware*), a **yellow banner** under the title, contained assets labelled in the **incident graph**, and an **attack disruption summary card** (**View activities**, **View related assets**).
- **Activities** tab: filter **Performed by: AttackDisruption**. The **Policy status** column (preview) shows **Active**, **Inactive**, **Not applicable** or **No status**.
- **Action center**: every disruption action, with **Undo**.
- API: incident titles that end with **(attack disruption)**.
- Advanced hunting: `DisruptionAndResponseEvents` for all actions; `DeviceEvents` rows with `ContainedDevice` / `ContainedUser` for traffic blocked *because of* containment.

```kql
DisruptionAndResponseEvents
| where Timestamp > ago(30d)
| project Timestamp, ActionType, AttackDisruptionCategory, DeviceName, AccountUpn, RemoteIP
| order by Timestamp desc
```

**6. Releasing.** After investigation, select the contained asset in the incident and choose **Release from containment** (device) or **Enable user** (account), or **Undo** in the Action center. Release too early and the attacker resumes.

## Exam traps

- ==!You must enable attack disruption in Settings.== ==+It is built in; meeting the prerequisites is the configuration.== Full opt-out needs a support case.
- ==!Attack disruption acts on single high-severity alerts.== It acts at the **incident** level on correlated, high-confidence signals.
- ==!Contain device and isolate device are the same.== **Contain** makes *other* devices refuse traffic from it (works on unmanaged devices). **Isolate** cuts an onboarded workstation off the network.
- ==!Disable user always needs Defender for Identity.== Cloud-only accounts are disabled in Entra without it. AD accounts do need the MDI sensor on a DC.
- ==!Semi-automation blocks disruption until approved.== ==+Semi levels still allow automatic disruption.== Only **No automated response** excludes the group.
- ==!Disruption needs Defender Antivirus in active mode.== It works in Active, Passive or EDR block mode.
- "Contain device does nothing on unmanaged devices" → check **device discovery = Standard discovery**.
- "Contain user fails" → Sense agent older than **v10.8470**.
- "Protect the break-glass admin from being disabled" → **user exclusion** under **Automated response > Identities**.
- "Mailbox auditing" on a disruption question → the five events: `MailItemsAccessed`, `UpdateInboxRules`, `MoveToDeletedItems`, `SoftDelete`, `HardDelete`.
- Where is disruption seen? Tag, yellow banner, graph labels, summary card, Activities tab, Action center — ==!not== a separate "Disruption" page.

## Skip

- **Skip:** the "how attack disruption uses AI" section (graph models, boosted decision trees, small language models). Know only: built-in, Microsoft-tuned, 99%+ confidence.
- **Skip:** the long advanced-hunting query that finds disabled accounts via domain controllers on port 88. Know that `DisruptionAndResponseEvents` exists.
- **Skip:** the PowerShell registry commands that read the Sense version. Know the minimum version **v10.8470** and why it matters.
- **Skip:** Okta and AWS setup detail. Know that preview support exists through Sentinel connectors.
- **Skip:** the enterprise-app ID `60ca1954-…`. Know the app's name only if asked why a cloud-only user was disabled without MDI.
- **Skip:** Defender for Business attack disruption — same idea, fewer options, no exclusion detail on the exam.
- **Skip:** the predictive shielding management pages. Know the three actions and that they are pre-emptive.
