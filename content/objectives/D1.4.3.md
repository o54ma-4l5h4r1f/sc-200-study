## Azure first

- **Log Analytics workspace** — the Azure database Sentinel sits on. Every analytics rule is a query against its tables (`SecurityEvent`, `SigninLogs`, `AzureActivity`...).
- **Microsoft Sentinel** — Microsoft's cloud SIEM, switched on over one workspace. You can use it in the **Azure portal** or the **Defender portal**. After **31 March 2027** the Azure portal stops being supported; tenants that first onboarded from July 2025 are usually in the Defender portal already.
- **Azure RBAC** — the role **Microsoft Sentinel Contributor** (or anything with write rights on the workspace and its resource group) is needed to create or edit rules.
- **KQL** — rules are KQL queries, so you need to read `Table | where ... | summarize ...`.
- **Licence:** this is fully lab-able with an Azure subscription. Keep a daily cap on the workspace.

New to these? Read the Foundations pages linked above.

## In one sentence

An **analytics rule** is Sentinel's alarm: a query (or a Microsoft-built model) that keeps checking your workspace and, when it matches, creates **alerts** and usually **incidents**; Sentinel has several rule *types* that differ in who writes the logic and how much you can change.

## Why it exists

Collecting logs is like installing CCTV in every room. Nobody watches 400 screens. Analytics rules are the motion sensors that ring the guard desk. Some sensors you set yourself (scheduled, NRT). Some come sealed from the factory (Fusion, ML behaviour analytics, threat intelligence matching). One kind just forwards alarms other systems already rang (Microsoft security rules).

Microsoft now recommends **custom detections** (D1.4.1) for brand-new rules. Analytics rules still work, still run in the Defender portal, and are what the exam bullet names.

## What actually matters

### 1. The rule types — know which you can customise

| Type | Who writes the logic | Customise? | Notes |
|---|---|---|---|
| **Scheduled** | You (KQL) | Fully | Interval and lookback 5 min–14 days |
| **NRT** (near-real-time) | You (KQL) | Mostly | Runs every minute |
| **Microsoft security** | Microsoft source products | Filters only | Creates incidents from alerts of connected Microsoft security products (Defender for Cloud, Defender for Endpoint, Defender for Identity, Defender for Cloud Apps, Entra ID Protection...) — one template per product |
| **Threat intelligence** | Microsoft | No | One rule; matches Microsoft indicators |
| **Fusion** ("Advanced multistage attack detection") | Microsoft ML | Only source signals/exclusions | One rule, enabled by default |
| **ML behavior analytics** | Microsoft ML | No | Preview; anomalous SSH and RDP sign-ins |
| **Anomaly** | Microsoft ML | Thresholds via a duplicate | Writes to the `Anomalies` table — see D1.4.5 |

**Rule count limits** (Service limits page): scheduled rules **512 enabled / 1,024 total** (1,024 / 2,048 with a dedicated cluster, by support ticket); NRT counted separately.

Rules come from **templates**. Templates arrive with **solutions** you install from the **Content hub**. On the Analytics page: **Active rules** tab, **Rule templates** tab, **Anomalies** tab.

### 2. Scheduled rules — the wizard, tab by tab

**General.** Name (unique per workspace), Description, **Severity** (Informational, Low, Medium, High), **MITRE ATT&CK** tactics and techniques (multiple allowed; they flow into alerts, incidents and the MITRE page — D1.4.4), **Status** (Enabled by default).

**Set rule logic.**

- **Rule query.** 1–10,000 characters. No `search *` or `union *`. Return `TimeGenerated` — the lookback is measured on it. Microsoft suggests ASIM parsers over raw tables.
- **Alert enhancement.** Three parts:
  - **Entity mapping** — tell Sentinel which column is the user, host, IP and so on. Up to ==@10 entity mappings== per rule, up to **3 identifiers** each, at least one *required* identifier. Up to **500 entities** per alert, split across mappings. Entities land in the alert's `Entities` field (64 KB cap).
  - **Custom details** — surface extra columns in the alert (`ExtendedProperties`). Up to **20** per rule.
  - **Alert details** — dynamic alert name, description, severity or tactics taken from columns.
- **Query scheduling.** **Run query every** (interval) and **Lookup data from the last** (lookback): both ==@5 minutes to 14 days==. Interval must be ≤ lookback. **Start running**: *Automatically* or *At specific time* (preview, 10 minutes–30 days ahead). Scheduled rules run on a built-in **5-minute delay** for ingestion lag.
- **Alert threshold.** Alert when results are greater than / fewer than / equal to / not equal to a number. Applies per run. Enter `0` for no threshold.
- **Event grouping.** **Group all events into a single alert** (default) or **Trigger an alert for each event**. Max **150 alerts** per run: with per-event alerts, events 1–149 get their own alert and the 150th summarises the rest.
- **Suppression.** **Stop running query after alert is generated** → stop for up to **24 hours**.
- **Results simulation.** **Test with current data** replays the rule **50 times** over current data and graphs the results.

**Incident settings.**

- **Create incidents from alerts triggered by this analytics rule** — **Enabled** by default; one incident per alert. Set Disabled for "collect only" rules. ==!In the Defender portal, leave it Enabled== — Defender XDR creates the incident but reads this setting.
- **Alert grouping** — group up to **150 alerts** per incident within a time frame (**default 5 hours**, range 5 minutes–7 days). Three choices: *all entities match* (recommended), *all alerts from this rule*, or *selected entities and details match*. **Re-open closed matching incidents** — ==!not available in the Defender portal==. In the Defender portal, grouping is only a first suggestion; the correlation engine may regroup. A per-rule **Incident correlation** setting appears there too (D1.4.2).

### 3. NRT rules

NRT rules are hard-coded to run **every minute** with only a **two-minute delay**. They query on **ingestion time**, not `TimeGenerated`, so late data isn't missed. Same enrichment, grouping, suppression and automation as scheduled rules. Limits: ==@50 NRT rules== (the NRT article says "per customer"; the *Service limits* page says **50 enabled, 100 in total** including disabled — the limits page is the more precise one); at most **30 alerts** per run (29 single + 1 summary); only for sources with under **12 hours** ingestion delay. Queries may use several tables, watchlists and workspaces. In the wizard, ==!Query scheduling and Alert threshold are missing== — the schedule is fixed and every match alerts.

### 4. Microsoft security rules

Alerts from Microsoft products arrive in the `SecurityAlert` table but ==!don't create Sentinel incidents on their own==. A Microsoft security rule does that. Filters: **Microsoft security service**, **Filter by severity**, **Include specific alerts** / **Exclude specific alerts** by text in the alert name. Create from a template, or `+ Create > Microsoft incident creation rule`. Or tick **Create incidents – Recommended** on the connector.

==!Not available== if you enabled **Defender XDR incident integration** or onboarded Sentinel to the Defender portal. Existing ones are auto-disabled; Defender XDR makes the incidents.

### 5. Threat intelligence matching

Enable the **Microsoft Defender Threat Intelligence Analytics** rule (older pages call it *Microsoft Threat Intelligence Analytics*): `Analytics > Rule templates` → search "threat intelligence" → **Create rule** → **Review > Create**. It's read-only and needs no MDTI premium licence. It matches Microsoft domain, IPv4 and URL indicators against CEF (`CommonSecurityLog`), Windows DNS (`DnsEvents`), Syslog, `OfficeActivity`, `AzureActivity` and ASIM DNS/network session data. Alerts for the same indicator within 24 hours share one incident. Matched indicators are published to the workspace's threat-intelligence table and show on the **Threat intelligence** page with source *Microsoft Threat Intelligence Analytics*. ==!The matching-analytics article is inconsistent==: its text says `ThreatIntelligenceIndicators`, its screenshot shows the legacy `ThreatIntelligenceIndicator` (no new data since 31 July 2025). Current TI tables are `ThreatIntelIndicators` and `ThreatIntelObjects` — see [D1.3.6](D1.3.6.html).

### 6. Machine learning: Fusion and ML behavior analytics

**Fusion** = the **Advanced Multistage Attack Detection** rule. It correlates low-fidelity alerts and anomalies across products into a few high-severity incidents. **Enabled by default**, one rule only, logic hidden. You can edit only its **source signals** (exclude a provider or severity) and **excluded detection patterns** (matching incidents still form but are auto-closed with the tag `ExcludedFusionDetectionPattern`). It trains on 30 days of data. For your scheduled rules to feed Fusion they need **entity mapping and tactics**. ==!In the Defender portal Fusion isn't available== — the Defender XDR correlation engine does this job.

**ML behavior analytics** (preview): **Anomalous SSH Login Detection** (Syslog) and **Anomalous RDP Login Detection** (Windows Security Event ID 4624). Not customisable — only enabled or disabled. Needs **30 days** of data to baseline.

### 7. Managing rules

On **Active rules**: **Edit**, **Disable** (keeps config — use it during maintenance), **Duplicate** (copy named with "Copy"), **Delete** (permanent, no undo). Templates show **In use**; a template update shows an **Update** tag and you can revert to the template. A rule carries its own access token, so it keeps working if its creator leaves. ==!Exception:== rules that query workspaces in **other subscriptions or tenants** (the MSSP case) use the creator's own credentials. If that person loses access, the rule fails ("insufficient access to resource" health message) and is **auto-disabled** after repeated failures. Rules export and import as **ARM templates** (preview).

**Template versions.** A rule built from a template remembers it. When Microsoft updates the template, the rule shows an **Update** badge; the details pane offers **Compare with template**, then an **Update template** or **Revert to template** tab. A rule with only an **Edit** button was built from scratch.

## Exam traps

- ==!Fusion can be customised like a scheduled rule.== ==+Only source signals and exclusions; one rule only.==
- ==!Microsoft security rules work in the Defender portal.== ==+Unavailable there; Defender XDR creates incidents.==
- ==!Lookback can be 30 days.== ==+Scheduled interval and lookback: 5 minutes–14 days.==
- ==!Interval longer than lookback is fine.== ==+Validation blocks it; interval ≤ lookback.==
- ==!Suppression can last a week.== ==+Up to 24 hours.==
- ==!Alert grouping window maxes at 24 hours.== ==+Default 5 hours, up to 7 days.==
- ==!NRT rules are unlimited.== ==+50 enabled (100 total), 30 alerts per run.==
- ==!You set an NRT rule's threshold and schedule.== ==+Neither exists — it runs every minute and every match alerts.==
- ==!Disabling incident creation in the Defender portal stops noise.== ==+Leave it Enabled there.==
- ==!Delete to pause a rule.== ==+Disable — delete has no undo.==
- **Which rule makes incidents from all Defender for Cloud alerts?** Microsoft security. **Which lets you write KQL?** Scheduled (and NRT).
