## Azure first

- The **Activity log** is Azure's record of who changed what in a **subscription**: created a VM, deleted a key vault, changed a role assignment. Azure keeps it for **90 days** automatically, but Sentinel can't see it until you export it.
- **Resource logs** are what happens *inside* a resource — a secret read from a key vault, a firewall rule hit. They aren't collected at all until you switch them on.
- A **diagnostic setting** is the export switch. It's attached to one subscription (for the Activity log) or one resource (for resource logs) and sends the logs to a destination such as the Sentinel workspace.
- **Azure Policy** is Azure's rule engine. A *deployIfNotExists* policy can create a missing diagnostic setting on every matching resource. A **remediation task** fixes resources that existed before the policy.
- Assigning a policy needs the **Owner** role (or equivalent) at the scope you assign it.

New to these? Read the Foundations pages linked above.

## In one sentence

Azure activity and resource logs reach Sentinel through **diagnostic settings** — created by hand per resource (a *standalone* connector) or stamped out at scale by an **Azure Policy assignment** launched from the connector page (a *Policy-managed* connector) — and the Activity log lands in the **`AzureActivity`** table.

## Why it exists

Azure already records everything, like a building's door-badge system that keeps 90 days of swipes in its own box. Sentinel is the security desk across the road. Nothing crosses the road until someone runs a cable: the diagnostic setting.

One cable for one subscription is easy. Hundreds of key vaults, each needing its own setting, is where Azure Policy helps. Write the rule once — "every key vault must send its logs to workspace X" — and Policy adds the setting to every vault, including ones created next year.

## What actually matters

**1. Activity log vs resource logs.**

| | Activity log | Resource logs |
|---|---|---|
| Records | **Control plane** — management actions on resources (create, delete, configure) | **Data plane** — actions inside a resource (read a secret, query a database) |
| Scope | Subscription (also management group and tenant views) | Each resource |
| Collected by default? | Yes, kept **90 days**, free | ==!No== — nothing until a diagnostic setting exists |
| Sentinel table | `AzureActivity` | `AzureDiagnostics` or a resource-specific table |

The Activity log is ==!not== a sign-in audit. Requests rejected during authentication or authorization never create an entry. Sign-ins are in Entra ID's logs.

Activity log categories you can filter on in `AzureActivity` include Administrative, Service Health, Resource Health, Alert, Autoscale, Recommendation, Security and Policy. There are **no ingestion charges** for Activity log data; you pay only for keeping it longer than 90 days (up to 12 years).

**2. Diagnostic setting rules.**

- One setting per resource **per destination set**. A resource can have **up to five** diagnostic settings.
- Each setting can have at most **one** destination of each type. Two workspaces = two settings.
- Destinations: **Log Analytics workspace**, **Storage account**, **Event Hubs** (to stream to a non-Microsoft SIEM), **partner solutions**. The destination must already exist. For storage and event hubs it must be in the same region as a regional resource.
- **Category groups** save ticking boxes: `allLogs` (everything) and `audit` (customer interactions with data or settings). If you use a group you can't also pick single categories.
- **AllMetrics** sends platform metrics too.
- Delete a resource's diagnostic settings when you delete, rename or move it. Otherwise a re-created resource of the same name can pick the old setting up.

**3. The two Sentinel connector styles.**

- **Standalone** diagnostic-settings connectors: the connector page links you to the resource; you add the diagnostic setting yourself. Needs read and write on the workspace.
- **Policy-managed** connectors: **Launch Azure Policy Assignment wizard** from the connector page. **Basics:** choose the **Scope** (subscription, optionally a resource group). **Parameters:** clear "Only show parameters that require input", pick the **Log Analytics workspace**, leave the log types you want as **True**. **Remediation:** tick **Create a remediation task** — ==@without it the policy only covers resources created from now on==. Needs **Owner** at the policy assignment scope.
- Status quirk: a Policy-managed connector shows **connected** only if data arrived in the **past 14 days**.
- The wizard just assigns a **built-in policy definition**. For the Activity log it is ==@Configure Azure Activity logs to stream to specified Log Analytics workspace== (effect **DeployIfNotExists**). For resource logs the built-ins are named like **Enable logging by category group for (resource type) to Log Analytics** (DeployIfNotExists / AuditIfNotExists). You can assign the same definitions yourself from **Azure portal > Policy > Definitions** — same result as the connector button.
- A DeployIfNotExists assignment gets a **managed identity** (an Azure-owned service account). The remediation task uses that identity to create the diagnostic settings, so the identity needs rights on the target resources — the wizard grants them, which is one reason you need Owner.

**4. The Azure Activity connector specifically.** It now uses the **diagnostic settings pipeline**. Prerequisites shown on the connector: workspace read/write, **Owner** on the policy assignment scope, **Owner** on the subscription. If subscriptions still use the old (pre-diagnostic-settings) method, step 1 on the page is **Disconnect All**. Step 2 launches the Policy wizard. The `AzureActivity` table does ==!not== support DCR transformations (connector reference: DCR support **No**, "Not currently supported"; lake-only ingestion also **No**).

**5. Two Microsoft pages disagree — show both, trust the product.** The Sentinel article *Connect … by using diagnostic settings-based connections* lists Azure Activity in its prerequisites table and says to continue with the **standalone** instructions. The training unit and the live connector page say **Launch Azure Policy Assignment wizard**. The screenshot below is the connector page itself: under "Connect your subscriptions through diagnostic settings new pipeline" it uses the **Policy wizard**. ==+The product UI wins: Azure Activity is Policy-managed.== Either way the outcome is the same — a **subscription-level diagnostic setting** that sends the Activity log to `AzureActivity`.

## Where it lives

**Sentinel connector (Defender portal):** **Microsoft Sentinel > Content management > Content hub** > install **Azure Activity**, then **Microsoft Sentinel > Configuration > Data connectors > Azure Activity > Open connector page > Launch Azure Policy Assignment wizard**. Same path under **Microsoft Sentinel** in the Azure portal.

**Activity log export by hand (Azure portal):** **Monitor > Activity log > Export Activity Logs > + Add diagnostic setting**. Disable any legacy configuration (log profiles) first.

**Policy by hand (Azure portal):** **Policy > Definitions** > search "Configure Azure Activity logs to stream" > **Assign** > Scope, Parameters (workspace), **Remediation** tab > **Create a remediation task**. Check progress under **Policy > Remediation**.

**Resource logs by hand (Azure portal):** open the resource > **Monitoring > Diagnostic settings > + Add diagnostic setting** > tick categories or a category group > **Send to Log Analytics workspace** > Save. Or **Monitor > Settings > Diagnostic settings** and pick the resource.

Command line:

```bash
# Activity log = SUBSCRIPTION-scope setting
az monitor diagnostic-settings subscription create --name to-sentinel \
  --workspace <workspace-resource-id> \
  --logs '[{"category":"Administrative","enabled":true},{"category":"Security","enabled":true},{"category":"Policy","enabled":true}]'

# Resource logs = resource-scope setting
az monitor diagnostic-settings create --name kv-to-sentinel \
  --resource <key-vault-resource-id> --workspace <workspace-resource-id> \
  --logs '[{"categoryGroup":"allLogs","enabled":true}]'
```

```powershell
# Resource-scope only. New-AzDiagnosticSetting can NOT export the Activity log.
$log = New-AzDiagnosticSettingLogSettingsObject -Enabled $true -CategoryGroup allLogs
New-AzDiagnosticSetting -Name 'KeyVault-Diagnostics' -ResourceId $KV.ResourceId -WorkspaceId $Law.ResourceId -Log $log
```

Check:

```kql
AzureActivity
| where TimeGenerated > ago(1d)
| summarize count() by CategoryValue
```

Use case-insensitive operators (`=~`, `has`) on `AzureActivity` — values can differ in case.

## Exam traps

- "Collect Activity log from 40 subscriptions, including future ones, with least effort." ==+Azure Activity connector → Policy assignment at a management group or subscriptions scope + remediation task.== Not 40 hand-made settings.
- "Policy assigned, but existing resources still send nothing." ==+Create a remediation task.== Policy alone only affects new or updated resources.
- "Sentinel Contributor can run the Policy wizard." ==!No== — assigning policy needs ==+Owner== (or equivalent) on the scope.
- "Key vault secret reads appear in AzureActivity." ==!No== — that's a resource (data-plane) log; it needs the key vault's own diagnostic setting.
- "Use `New-AzDiagnosticSetting` for the Activity log." ==!Not supported== — use a subscription-scope setting (`az monitor diagnostic-settings subscription create`, ARM template, or the portal).
- "Send to two workspaces in one diagnostic setting." ==!One destination per type== — make a second setting (max five per resource).
- "Connector shows disconnected though it's configured." Policy-managed connectors go grey after **14 days** with no data.
- "Failed sign-in attempts are in the Activity log." ==!No.==
