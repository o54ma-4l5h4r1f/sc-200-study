## Azure first

- **Microsoft Sentinel** is the SIEM that sits on a **Log Analytics workspace** (the database). Every hunting query reads tables in that workspace, such as `SigninLogs`, `SecurityEvent` or `AzureActivity`.
- **KQL** is the read-only query language. A hunting query is just a saved KQL query plus a description and some labels.
- **MITRE ATT&CK** is a public catalogue of attacker *tactics* (the goal, such as Persistence) and *techniques* (the method, such as a scheduled task). Sentinel files every hunting query under one or more of them.
- An **entity** is a thing a result row is about: an account, host, IP address, URL or file. Sentinel can draw entities on a graph only if you tell it which column holds which entity (**entity mapping**).
- Sentinel runs in two portals today: the **Defender portal** (`security.microsoft.com`, the future) and the **Azure portal** (retired for Sentinel after **31 March 2027**). Paths differ slightly.

New to these? Read the Foundations pages linked above.

## In one sentence

A **hunting query** is a saved KQL query you run *on purpose* to look for attacker behaviour that no detection rule has alerted on yet; Sentinel's **Hunting** page lets you run hundreds of them, watch which ones spike, save interesting rows as **bookmarks**, group the work into a **hunt**, and turn a good query into an **analytics rule**.

## Why it exists

Detection rules are smoke detectors. They ring when a known pattern happens. Hunting is the night-shift guard walking the corridors with a torch. They look for things nobody wired a detector for.

Some activity is too common to alert on, like a rare process on a server. You don't want an incident each time, but you do want to *look* weekly. When a walk finds something real, you install a new smoke detector: you promote the query to an analytics rule.

Training unit 2 draws the line: hunting looks for activity **not previously detected**. Searching for a new bad IP from a threat feed is indicator matching, not hunting. Real hunting starts from a **hypothesis** about attacker *behaviour*.

Three objects, nested. A **query** is the torch. A **bookmark** is a photo of what the torch lit up. A **hunt** is the case folder holding the torches, the photos and your notes.

## What actually matters

**1. The Hunting page and its tabs.** Path: **Microsoft Sentinel > Threat management > Hunting**. The **Queries** tab lists every hunting query: those installed by **Content hub** solutions plus your own. Each shows its data sources, MITRE **tactics** (icons on the **MITRE ATT&CK tactic bar** across the top) and **techniques** (the **Techniques** column). The other tabs are **Bookmarks** and **Hunts (Preview)**.

**2. "Monitor" = run them and read the numbers.** Nothing runs on a timer here. You press **Run all queries** or select some and **Run selected queries**. Then read three columns:

| Column / filter | What it tells you |
|---|---|
| ==@Results== | how many rows matched. **N/A** = the table it needs is not connected (hover the **i** to see which data source) |
| ==@Results delta== | change in results: last 24 hours against the previous 24–48 hours |
| ==@Results delta percentage== | the same change as a percentage. Sort by it to find spikes |

Star a query to make it a **favorite**. ==+Favorites run automatically each time you open the Hunting page.== Microsoft suggests running hunting queries for your ingested data **at least once a week**.

**3. Creating a query.** **Queries** tab > **New query**. Fill in **Name**, **Description**, **Custom query** (KQL), **Entity mapping** (entity type, identifier, column) and **Tactics & techniques** (tactic, technique, sub-technique). You can also **Clone** any query (built-in or custom) and edit the copy. ==!You can only Edit a query whose content source is custom.== A query that came from a Content hub solution or repository must be changed at its source; clone it instead.

```kql
// Custom hunting query from the training exercise: who deleted a VM?
AzureActivity
| where OperationNameValue =~ "Microsoft.Compute/virtualMachines/delete"
| where ActivityStatusValue == "Success" or ActivityStatus == "Accepted"
| project TimeGenerated, Caller, CallerIpAddress, ResourceGroup, _ResourceId
| extend AccountCustomEntity = Caller, IPCustomEntity = CallerIpAddress
```

The `AccountCustomEntity` / `IPCustomEntity` columns are the old in-query way to map entities. The **Entity mapping** fields on the form are the newer way. Both work.

**4. Bookmarks.** In the query results, tick rows and select **Add bookmark**. One bookmark is created **per row**. Each keeps the row, the query and its time range, plus your **tags**, **notes**, **entity mappings** and **MITRE** mappings. Bookmarks inherit the query's entity and MITRE mappings by default. From the **Bookmarks** tab you can **Investigate** (open the investigation graph; ==!needs at least one mapped entity==) or use **Incident actions > Create new incident / Add to existing incident** (the bookmarks article marks adding bookmarks to incidents as ==!Azure portal only==). Every bookmark is also a row in the ==@HuntingBookmark== table. Deleting one writes a new row with `SoftDeleted` = true; nothing is erased. The Bookmarks tab shows up to **1,000** bookmarks; the rest stay queryable in the table. A new bookmark can take minutes to appear on the tab.

```kql
// Latest version of every live bookmark tagged for one campaign
HuntingBookmark
| summarize arg_max(TimeGenerated, *) by BookmarkId
| where SoftDeleted == false
| where Tags has "campaign-x"
| project BookmarkName, EventTime, CreatedBy, Notes, QueryText
```

**5. Portal split for bookmarks (current state).** ==!Bookmarks can be created only in the Azure portal.== In the Defender portal you can **view** existing bookmarks but not add new ones. ==!Advanced hunting has no bookmarks at all.== Microsoft suggests incident tags, saved queries or custom tables there instead. Expect this to change before Sentinel leaves the Azure portal on 31 March 2027.

**6. Hunts (preview).** A case folder around one hypothesis. Select queries > **Hunt actions > Create new hunt**, or **Hunts (Preview) > New Hunt** for a blank one. Queries in a hunt are **clones**, independent of the originals. Tabs: **Queries**, **Bookmarks**, **Entities**, plus **comments**. The **hypothesis** state records whether the guess was validated; the **hunt status** whether the hunt is new, active or closed. A metrics bar counts validated hypotheses, new incidents and new rules. Needs **Microsoft Sentinel Contributor** (or a custom role with `Microsoft.SecurityInsights/hunts` permissions).

**7. Promote to a detection.** Inside a hunt, right-click a query > **Create analytics rule**. The name, description and KQL prefill, and the rule is linked under **Related analytics rules**. From plain query results: **New alert rule > Create Microsoft Sentinel alert** opens the analytics rule wizard.

**8. Livestream is gone.** ==!Livestream sessions are no longer available.== Microsoft points you to **KQL jobs** (D3.2.2), **analytics rules** or **playbooks** instead. The unit slug is still `5-livestream` but now teaches hunts. The *feature availability* table still lists Livestream as GA; the hunting article and the unit say it is gone. ==+The live article wins.==

**9. A good hypothesis** (training unit 3): achievable (you have the data), narrow, **time-bound**, useful (covers a detection gap) and tied to your threat model. Document what, how, why, inputs, outputs and next steps.

## Where it lives

| Task | Defender portal | Azure portal |
|---|---|---|
| Hunting page | **Microsoft Sentinel > Threat management > Hunting** | **Microsoft Sentinel > Threat management > Hunting** |
| New / clone query | Hunting > **Queries** > **New query** / row **...** > **Clone** | same |
| Create bookmark | ==!not available (view only)== | query results in **Logs** > tick rows > **Add bookmark** |
| Hunts | Hunting > **Hunts (Preview)** | same |
| MITRE gap view | **Microsoft Sentinel > Threat management > MITRE ATT&CK** > **Simulated: Hunting queries** | **MITRE ATT&CK (Preview)** |
| Search job (long-range single-table search) | **Microsoft Sentinel > Search** (results under **Search > Saved Searches**) | **Microsoft Sentinel > General > Search** |

Bookmarks only work when the **Logs** pane was opened from inside Sentinel. Open **Logs** straight from Azure Monitor and the **Add bookmark** button is missing.

**Search jobs, briefly.** A hunt sometimes needs one keyword across a year of one table, beyond the 10-minute query timeout. That is a **search job**: asynchronous, one table; the training says up to one year, the current product doc allows any range within the table's total retention (up to 12 years) — product doc wins; results land in a new `_SRCH` Analytics table you can bookmark from. D1.2.2 teaches it with **restore**. Its limits disagree between sources: the training unit says 1 million records, 5 concurrent jobs and 100 runs per day per workspace. The Azure Monitor article says **100 million** records, **10** concurrent, **200** per day (and **200** results tables per workspace, against the unit's 100). Both agree on the **24-hour** timeout. ==+The product article wins.==

## Exam traps

- "Which query language do hunting queries use?" ==+KQL.== Not T-SQL, not JSON.
- "A hunting query should run every time the analyst opens the Hunting page." ==+Mark it as a favorite.== ==!Not a scheduled analytics rule==, and ==!not livestream (retired)==.
- "Find queries whose matches jumped since yesterday." ==+Sort by Results delta / Results delta percentage.== The **N/A** result means a missing data source, not zero hits.
- "Change a built-in Content hub hunting query." ==!Edit is blocked.== ==+Clone it, then edit the clone.==
- "Preserve suspicious rows, with notes, for teammates, and attach them to an incident." ==+Bookmarks.== ==!Not a workbook, not a watchlist.==
- "A bookmark won't open in the investigation graph." ==+Map at least one entity.==
- "Where are bookmarks stored for KQL?" ==+`HuntingBookmark`== in the workspace. Deleted ones remain with `SoftDeleted` = true.
- "Create a bookmark in Advanced hunting." ==!Not possible.== In the Defender portal you can only view bookmarks; creation is Azure portal Sentinel Hunting.
- "Group queries, bookmarks, entities and comments around one hypothesis and track if it was validated." ==+A hunt.==
- "Turn a proven hunting query into automatic alerts." ==+Create analytics rule== (from the hunt query menu, or **New alert rule > Create Microsoft Sentinel alert**).
- "Searching logs for a new bad IP from a TI feed is threat hunting." ==!Strictly no== — it uses a known indicator. Hunting starts from a behavioural hypothesis.
