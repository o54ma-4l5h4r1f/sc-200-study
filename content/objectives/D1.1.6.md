## Azure first

- **Defender for Endpoint (MDE)** is Microsoft's security product for laptops and servers. A small sensor on each device reports to the **Defender portal** (`security.microsoft.com`).
- **Microsoft Defender Antivirus** is the antivirus built into Windows. ASR rules are a feature *of* Defender Antivirus, so it must be the active antivirus.
- **Microsoft Intune** is Microsoft's device-management service. It pushes settings ("policies") to devices. Its **endpoint security** policies are the recommended way to switch ASR rules on.
- **Microsoft Entra ID** holds the device objects and **groups** that policies are assigned to. ASR policies target **device** groups, not user groups.
- **Group Policy (GPO)** is the older, on-premises way Windows domains push settings. It still works for ASR.

New to these? Read the Foundations pages linked above.

## In one sentence

**Attack surface reduction (ASR) rules** are Windows switches that block specific risky behaviours malware relies on — such as Word starting a child process or a script downloading an executable — and you push them to devices as a **security policy** from Intune, the Defender portal, Group Policy or PowerShell.

## Why it exists

Antivirus asks "is this file known to be bad?". Attackers dodge that by using new files or by abusing normal tools: Office macros, PowerShell, PsExec, scripts. ASR asks a different question: "is this *behaviour* something an ordinary user ever needs?". An accountant never needs Excel to launch `powershell.exe`. So you block that behaviour for everyone, good file or bad.

Think of a building. Antivirus is the guard checking faces against a list of known burglars. ASR rules are the **locks on doors nobody uses** — the roof hatch, the loading bay at night. A burglar with a clean record still cannot get through a locked hatch.

The catch: some legitimate business software *does* behave like malware. That is why every rule has an **Audit** mode and an **exclusion** list.

## What actually matters

**1. ASR rules are one part of a bigger "attack surface reduction" family.** The training unit lists eight capabilities. Know the names and one line each:

| Capability | What it does |
|---|---|
| ==@ASR rules== | Block risky behaviours (Office child processes, obfuscated scripts, LSASS credential theft). Needs Defender Antivirus. |
| Hardware-based isolation | Uses virtualization-based security to wall off sensitive parts of Windows, such as credentials. |
| Application control | Apps must earn trust before they run. |
| Exploit protection | Exploit mitigations for the OS and apps. Works with third-party antivirus too. |
| Network protection | Blocks connections to malicious domains and IPs. Needs Defender Antivirus. |
| Web protection | Web threat protection and web content filtering. |
| Controlled folder access | Stops untrusted apps (for example ransomware) changing files in protected folders. Needs Defender Antivirus. |
| Device control | Controls USB drives and other removable media. |

**2. The five modes and their codes.** Every tool except Intune and Configuration Manager names a rule by its GUID and a number:

| Mode | Code | Behaviour |
|---|---|---|
| Off / Disabled | `0` | Rule explicitly off. Can conflict with another policy that turns it on. |
| Block | `1` | Behaviour stopped. User gets a notification. |
| Audit | `2` | Behaviour **allowed**, but logged as if blocked. Use it to test. |
| Not configured | `5` | Same effect as Off, but no conflict risk. |
| Warn | `6` | Blocked, but the user can select **Unblock** for **24 hours**. |

Warn details that get tested: it needs Windows 10 version 1809 or later (older versions just Block). It is **not available in Microsoft Configuration Manager**. Two rules do not support it: *Block credential stealing from the Windows local security authority subsystem* and *Block Office applications from injecting code into other processes*. Since Defender platform **4.18.26060**, **Unblock** needs administrator approval. For a permanent allow, use a per-rule exclusion, not Unblock.

**3. Standard protection rules go straight to Block. Everything else goes to Audit first.** Microsoft names three **standard protection rules** that are safe to Block without long testing:

- Block abuse of exploited vulnerable signed drivers
- Block credential stealing from the Windows local security authority subsystem (LSASS)
- Block persistence through WMI event subscription

One caveat on the third: if **Configuration Manager** manages the device, do not switch *Block persistence through WMI event subscription* to Block or Warn with another tool without long Audit testing — the Configuration Manager client itself uses WMI.

All other rules (for example *Block all Office applications from creating child processes*, *Block execution of potentially obfuscated scripts*, *Use advanced protection against ransomware*) should run in **Audit**, be reviewed, get exclusions, and only then move to Block or Warn.

**4. Requirements.** Defender Antivirus must be in **Active** mode. Passive mode, EDR in block mode, limited periodic scanning or Off all stop ASR rules. **Real-time protection** must be on. **Cloud-delivered protection** is strongly needed. Defender components must be no more than two versions old. ASR rules are **Windows only**. They do not exist on macOS or Linux, even when onboarded to MDE. The rules themselves do **not** need Microsoft 365 E5. The portal report, alerts and advanced hunting do need Defender for Endpoint Plan 2 (or Defender for Business).

**5. Where you configure them — seven methods.**

| Method | Notes |
|---|---|
| ==+Intune endpoint security policy== | **Recommended.** Intune admin center > **Endpoint security** > **Attack surface reduction** > profile **Attack Surface Reduction Rules**. |
| Defender portal endpoint security policy | Same Intune policy engine, created in `security.microsoft.com`. Works on devices **not enrolled in Intune** through **Defender for Endpoint security settings management**. |
| Intune custom profile (OMA-URI) | `./Vendor/MSFT/Policy/Config/Defender/AttackSurfaceReductionRules`, value `GUID=mode`. |
| Any MDM via Policy CSP | Same CSP, `GUID=mode` pairs separated by `pipe` characters. |
| Microsoft Configuration Manager | Exploit Guard policy. No Warn mode. |
| Group Policy | Computer configuration > Administrative templates > Windows components > Microsoft Defender Antivirus > Microsoft Defender Exploit Guard > Attack Surface Reduction. |
| PowerShell | `Set-MpPreference` / `Add-MpPreference` on one device. Lowest precedence. |

**Security settings management** deserves one paragraph. It lets Intune policies reach a device that is onboarded to MDE but **not enrolled in Intune** — for example a server. The device gets an Entra ID registration (a **synthetic registration** if it had none) so it can be put in a group. It checks in every **90 minutes**; **Policy sync** on the device page forces it (about 10 minutes). Such devices show **Managed by: MDE**. Assign these policies to **Entra device groups**, never user groups.

**6. Exclusions — four kinds.**

- **Global ASR exclusions** ("Attack surface reduction only exclusions") — apply to every rule. Every method supports them.
- **Per-rule exclusions** — apply to one rule. Only **Group Policy**, **Intune endpoint security policies** and **Defender portal endpoint security policies** support them.
- **Defender Antivirus exclusions** — honoured by some rules only. All rules honour AV **process** exclusions.
- **Indicators (IoCs)** for files and certificates — honoured by most rules.

Three facts about exclusions: an excluded file runs and **no event is recorded**. Exclusions apply only when the process **starts**, so restart a running service. And if **Disable local admin merge** is on, local and per-rule exclusions made on the device do not apply.

**7. When two tools disagree.** Local PowerShell settings lose to everything. **Group Policy beats MDM (Intune) by default.** The Policy CSP setting **MDMWinsOverGP** = `1` flips that. **Controlled configuration** makes Intune and security settings management ignore conflicting GPO, Configuration Manager and local settings. Avoid setting the same rule in two tools.

**8. Seeing what the rules did.**

| Where | What |
|---|---|
| Windows Event Viewer | Applications and Services Logs > Microsoft > Windows > Windows Defender > Operational. **1121** = block, **1122** = audit, **1129** = user overrode a Warn, **5007** = settings changed. |
| Advanced hunting | Table `DeviceEvents`, ASR rows have an `ActionType` starting with `Asr`. Events are throttled to unique processes per hour. |
| ASR rules report | Defender portal > **Reports** > **Endpoints** tab > **Attack surface reduction rules** (`security.microsoft.com/asr`). Tabs: **Detections**, **Configuration**, **Add exclusions**. |
| Device timeline | The device page shows ASR events in time order. |

```kql
DeviceEvents
| where Timestamp > ago(30d)
| where ActionType startswith "Asr"
| summarize EventCount = count() by ActionType
```

## Where it lives

| Task | Portal | Path |
|---|---|---|
| Create ASR policy (recommended) | Intune admin center | **Endpoint security** > **Attack surface reduction** > **Create policy** > Platform **Windows** > Profile **Attack Surface Reduction Rules** |
| Create ASR policy in Defender | Defender portal | **Endpoints** > **Configuration management** > **Endpoint security policies** (`security.microsoft.com/policy-inventory`) > **Create new policy** > **Windows** > template **Attack surface reduction rules** |
| Turn on security settings management | Defender portal | **System** > **Settings** > **Endpoints** > **Configuration management** > **Enforcement scope** |
| Force a device to pull policy | Defender portal | **Assets** > **Devices** > device > **More actions** > **Policy sync** |
| See policies on a device | Defender portal | device page > **Configuration management** > **Security policies** tab |
| ASR report | Defender portal | **Reports** > **Endpoints** > **Attack surface reduction rules** |

Other templates on the same **Endpoint security policies** page: Microsoft Defender Antivirus, Antivirus exclusions, Firewall, Firewall rules, Endpoint detection and response, Windows Security experience (tamper protection), Device control, Defender update controls. That is what "security policies for Defender for Endpoint" means in the blueprint.

**Permissions to manage those policies in the Defender portal:** unified RBAC **Authorization and settings / Security settings / Core Security settings (manage)**, or Entra **Security Administrator** / **Intune Administrator**. Your role must cover **all devices** — a role scoped to some device groups cannot open the page.

PowerShell on one device (elevated):

```powershell
# Audit one rule (Block Office apps creating child processes)
Add-MpPreference -AttackSurfaceReductionRules_Ids d4f940ab-401b-4efc-aadc-ad5f3c50688a -AttackSurfaceReductionRules_Actions AuditMode
# Global ASR exclusion
Add-MpPreference -AttackSurfaceReductionOnlyExclusions "C:\Data\LOBApp\app1.exe"
# See what is set
(Get-MpPreference).AttackSurfaceReductionRules_Ids
```

`Set-MpPreference` **replaces** the whole list. `Add-MpPreference` appends. `Remove-MpPreference` removes.

## Exam traps

- ==!Audit mode blocks nothing.== It logs event **1122** and lets the behaviour run. ==+Block (code 1) stops it== and logs **1121**.
- ==!"Not configured" (5) and "Off" (0) are not identical in practice.== Same effect, but **Off** can conflict with another policy; **Not configured** cannot.
- ==!Warn is available everywhere.== It is **not** in Configuration Manager and two rules (LSASS credential stealing, Office code injection) do not support it.
- ==!ASR rules work with a third-party antivirus.== They need Defender Antivirus **active**. Passive mode is not enough. (Exploit protection is the family member that works with third-party AV.)
- ==!ASR rules protect Linux and macOS servers.== They are Windows only.
- ==!Assign the policy to a user group.== For security settings management, ==+assign to Entra device groups==.
- ==!Intune always beats Group Policy.== By default ==+Group Policy wins over MDM== unless **MDMWinsOverGP** = 1 (or controlled configuration is used).
- ==!Per-rule exclusions work in every tool.== Only GPO, Intune endpoint security and Defender portal endpoint security policies support them. PowerShell and the CSP give **global** exclusions only.
- ==!`Set-MpPreference` adds a rule.== It **overwrites** the list. ==+`Add-MpPreference` appends.==
- A rule keeps firing on an excluded **service**? It was already running — exclusions apply at process start.
- "Which rules can go straight to Block?" → the three **standard protection rules**.

**Two Microsoft sources disagree.** Training unit 3 says you "can't specify which rules the exclusions apply to" and lists only four modes (Not configured, Block, Audit, Warn). The current product docs add **per-rule exclusions** (GPO, Intune and Defender portal) and a separate **Off = 0** code. The product docs are newer and match the shipping UI — learn those.

## Skip

- **Skip:** the per-rule GUID list. Microsoft lists ~19 rules with GUIDs. The exam does not ask you to recall a GUID. Know that GUIDs exist, that `GUID=mode` is the format, and the names of the three standard protection rules.
- **Skip:** the per-rule exclusion-honouring matrix (which rule honours AV exclusions, certificate IoCs, etc.). Remember only: all rules honour AV *process* exclusions; global and per-rule ASR exclusions work for every rule.
- **Skip:** training unit 3's **Device configuration > Profiles > Endpoint protection** Intune path. That is the old template route. Endpoint security policies replaced it.
