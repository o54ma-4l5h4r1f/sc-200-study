## Azure first

- **The Defender portal** (`security.microsoft.com`) is the one website where Defender XDR alerts, incidents and hunting live. Microsoft Sentinel can be plugged into it too.
- **Advanced hunting** is the query screen inside that portal. You type **KQL** (Kusto Query Language — `Table | where ...`) against tables such as `DeviceProcessEvents` or `EmailEvents`.
- **Defender XDR tables** come from the Defender products (Endpoint, Office 365, Identity, Cloud Apps). They need a Microsoft 365 E5-class licence. **Sentinel tables** live in a Log Analytics workspace you pay for in Azure.
- **Two permission systems** meet here. Entra roles (Security Administrator) or Defender permissions cover Defender data. The Azure role **Microsoft Sentinel Contributor** covers Sentinel data.
- **Licence note:** with an Azure subscription only, you can onboard Sentinel to the Defender portal, but Microsoft lists custom detection rules as ==!limited or unavailable== without Defender services. Treat this page as a portal tour.

New to these? Read the Foundations pages linked above.

## In one sentence

A **custom detection rule** is a saved Advanced hunting query that the Defender portal re-runs on a timer; every time it finds matching rows it raises an **alert** and can automatically **act** on the device, file, user or email it found.

## Why it exists

Think of a shop guard who spots a shoplifting trick on CCTV once. He can keep re-watching the tapes by hand every night. Or he can tell the camera system: "ring the bell whenever you see that move again, and lock the door." Advanced hunting is the guard watching tapes. A custom detection is the instruction to the camera.

Microsoft's built-in detections cover common attacks. Your organisation has its own risks — a rare admin tool, a mailbox that should never forward mail. A custom detection turns *your* hunting query into a permanent alarm.

Microsoft now calls custom detections ==@the unified way to create new detections== across Defender XDR and Sentinel. Sentinel's own **analytics rules** (D1.4.3) still exist. Custom detections can query **both** Defender and Sentinel tables in one rule, and only they can fire Defender response actions.

## What actually matters

### 1. The query must return the right columns

Microsoft **recommends** these columns in the results:

| Column | Why |
|---|---|
| `Timestamp` or `TimeGenerated` | Sets the alert's time. Without it, the time falls back to the lookback window. |
| `DeviceId` + `ReportId` (Defender for Endpoint tables) | Puts the alert in the right device group and builds the process tree. |
| `Timestamp` + `ReportId` (other Defender tables) | Lets Defender find the exact original event. |
| One strong identifier | Auto-maps the impacted asset: device (`DeviceId`, `DeviceName`, `RemoteDeviceName`), mailbox (`RecipientEmailAddress`, `SenderFromAddress`, `SenderMailFromAddress`, `SenderObjectId`, `RecipientObjectId`) or account (`AccountObjectId`, `AccountSid`, `AccountUpn`, `InitiatingProcessAccountSid`, `InitiatingProcessAccountUpn`). |

If you `summarize`, you lose those columns. The fix is `arg_max`, which keeps the newest row's `Timestamp` and `ReportId` per group:

```kql
DeviceEvents
| where ingestion_time() > ago(1d)
| where ActionType == "AntivirusDetection"
| summarize (Timestamp, ReportId)=arg_max(Timestamp, ReportId), count() by DeviceId
| where count_ > 5
```

Do **not** filter on `Timestamp` or `TimeGenerated` to limit the time range. The service already pre-filters by the lookback. For speed, filter on `ingestion_time()` instead, matched to the run frequency — `ago(1d)` covers a daily rule, as in the sample. Each run can raise at most ==@150 alerts==, so tune out normal activity first.

> **Two Microsoft sources disagree.** The training unit says the query **must** return `Timestamp`, `DeviceId` and `ReportId`, and that a rule can raise **100** alerts per run. The current product article says these columns are **recommended** and the cap is **150**. The product article wins. Expect the exam to accept 150.

### 2. Frequency and lookback

When you save, the rule runs at once over the **past 30 days**. After that it repeats on the frequency you pick. With Defender data, the lookback is fixed:

| Frequency | Lookback (Defender data) |
|---|---|
| Every 24 hours | 30 days |
| Every 12 hours | 48 hours |
| Every 3 hours | 12 hours |
| Every hour | 4 hours |
| Continuous (NRT) | events checked as they arrive |
| Custom (Sentinel-only data) | frequency 5 minutes to 14 days; lookback per the rule below |

**Continuous (NRT)** — near real time — works only if the query uses **one table**, no joins, no unions, no `externaldata`, and no comment lines. Only listed tables qualify (for example `DeviceProcessEvents`, `EmailEvents`, `SigninLogs`, `SecurityEvent`). The custom detection rules page has a **Migrate now** button that switches every compatible rule to NRT.

For **Sentinel-only** data you set the lookback yourself. Faster than hourly: under 48 hours. Hourly up to daily: up to 14 days. Daily or slower: up to 30 days. Rules evaluate `ingestion_time()`, so a late-arriving old event can still be caught. Duplicates from overlapping windows are merged into one alert.

The *Advanced hunting in the Defender portal* known-issues list still says NRT isn't available for detections that include Sentinel data. Two newer feature articles beat one known-issues line: expect NRT on Sentinel data to be allowed, and trust what the wizard offers on the day.

### 3. Alert details and enrichment

The wizard asks for: **Detection name**, **Frequency**, **Lookback** (Sentinel only), **Alert title**, **Severity**, **Category**, MITRE ATT&CK **Tactic**, **Techniques** and **Sub-techniques** (D1.4.4), an optional **Threat analytics report** link, **Description** and **Recommended actions**. Title and description are plain text only.

Then three enrichments:

- **Dynamic title/description.** Put a result column in double curly brackets: `User {{AccountName}} unexpectedly signed in from {{Location}}`. Up to **3 columns per field**.
- **Custom details.** Key–value pairs shown in the alert side panel. Up to **20 pairs** and **4 KB** total. Go over 4 KB and the whole set is dropped.
- **Entity mapping.** Tell Defender which column holds the main victim. **Impacted assets** (account, device, mailbox, cloud app, Azure/AWS/GCP resource) versus **Related evidence** (process, file, registry value, IP, OAuth app, DNS, security group, URL, mail cluster, mail message). One column per entity type. For Defender data entities are picked automatically. For Sentinel data you ==@map them by hand==. Entities drive how alerts merge into incidents.

### 4. Automatic actions (Defender data only)

| Target | Actions | Column needed |
|---|---|---|
| Device | Isolate device, Collect investigation package, Run antivirus scan, Initiate investigation, Restrict app execution | `DeviceId` |
| File | Allow/Block (needs *Remediate* permission; applies per device group), Quarantine file | `SHA1`, `InitiatingProcessSHA1`, `SHA256` or `InitiatingProcessSHA256` |
| User | Mark user as compromised (sets Entra risk to high), Disable user, Reset user authentication | `AccountObjectId` etc.; Disable/Reset need a SID column |
| Email | Move to mailbox folder (Junk, Inbox, Deleted items), Delete email (Soft or Hard delete) | `NetworkMessageId` + `RecipientEmailAddress` |

SaaS user actions on Box, Google Workspace and Salesforce identities from `CloudAppEvents` are in **preview**.

![Actions for custom detections](https://learn.microsoft.com/en-us/defender-xdr/media/custom-detection-rules/ah-custom-actions.png){The Actions step — device, file, user and email actions}

### 5. Scope and permissions

**Scope** is **All devices** or **Specific device groups**. The rule only queries, and only acts on, devices in scope. Scope does not affect mailbox- or identity-only rules.

**Who can create rules:**

- Defender data: **Security settings (manage)** Defender permission, or the Entra role **Security Administrator**. **Security Operator** works only if Defender for Endpoint RBAC is off; with RBAC on it also needs **Manage security settings**.
- Per workload: manage rights on Office 365 only lets you query `Email*` tables, not `Identity*`.
- Sentinel data: Azure role **Microsoft Sentinel Contributor** or higher.
- Device scope: you must have rights over every device group in the rule's scope.

### 6. Custom detection vs Sentinel analytics rule

Microsoft's comparison article calls custom detections ==@the best way to create new rules across Sentinel and Defender XDR==. The differences a question can hinge on:

| Capability | Sentinel analytics rule | Custom detection |
|---|---|---|
| Query Defender XDR tables | Not supported | ==+Supported== |
| Query Sentinel Analytics-tier tables | Supported | Supported |
| Native Defender response actions (isolate, quarantine…) | Not supported | ==+Supported== |
| Alerts without incidents | Supported | ==!Not supported== |
| Alert suppression after a run | Supported | ==!Not supported== |
| Customise alert grouping | Supported | Not supported (correlation engine groups) |
| Choose when the first run happens | Supported | Not supported (runs at once over 30 days) |
| Run rule on demand | Not supported | Supported |
| Show on the MITRE ATT&CK page | Supported | Planned |
| Sentinel automation rules (incident / alert trigger) | Supported | Planned |
| Rules health in `SentinelHealth` | Supported | Planned |
| Rule audit log | `SentinelAudit` | `CloudAppEvents` (Defender for Cloud Apps users) |

### 7. Sentinel data in custom detections

In the Defender portal, Advanced hunting **Manage rules** offers two buttons. **Create analytics rule** builds a Sentinel analytics rule (Sentinel data only, D1.4.3). **Create custom detection** builds a custom detection that can mix Defender and Sentinel tables. You don't need to stream Defender data into Sentinel to do this.

Limits to remember:

- Only **Analytics-tier** tables. ==!Basic and Auxiliary logs can't be used.==
- `workspace()` and `adx()` operators are **not supported** in custom detections. `arg()` is not supported in analytics rules.
- With Sentinel scoping, project `SentinelScope_CF` or scoped analysts won't see the alerts.
- See the comparison table above for what custom detections can't do yet.

## Where it lives

**Portal: Microsoft Defender portal** (`security.microsoft.com`).

| Task | Path |
|---|---|
| Build the query first | `Investigation & response > Hunting > Advanced hunting` → run query → **Create detection rule** |
| Start from the rule list | `Investigation & response > Hunting > Custom detection rules` → **+ Create detection rule** |
| Rule with Sentinel tables | Advanced hunting → **Manage rules > Create custom detection** |
| API | Microsoft Graph `POST /security/rules/detectionRules` |

Rules can also be managed as code with the Microsoft Security Bicep extension through Sentinel Repositories (**preview**).

## Exam traps

- ==!"A new rule only looks at data from now on."== ==+The first run checks the past 30 days.==
- ==!Hourly rule looks back 1 hour.== ==+Hourly → 4 h, 3-hourly → 12 h, 12-hourly → 48 h, daily → 30 days.==
- ==!A summarize query can be used as-is.== ==+Return `Timestamp` and `ReportId` with `arg_max`, or the alert loses its anchor event.==
- ==!NRT works with joins if they're small.== ==+NRT: one table, no joins/unions/externaldata, no comments.==
- ==!Security Operator can always create custom detections.== ==+Only with Defender for Endpoint RBAC off — otherwise add Manage security settings.==
- ==!Custom detections can isolate devices found in Sentinel data.== ==+Response actions need Defender data.==
- ==!You must ingest Defender tables into Sentinel to mix them in one rule.== ==+Custom detections query both directly.==
- ==!"Need an alert with no incident, or suppression after it fires — use a custom detection."== ==+That is still a Sentinel analytics rule feature.==
- **Delete email** needs `NetworkMessageId` and `RecipientEmailAddress`; **Disable user** needs a SID column.
- **Block file** needs *Remediate* permission and applies to device groups, not single devices.
