## Azure first

- **Microsoft Sentinel data lake** is one tenant-wide, low-cost store for security data, alongside the **analytics tier** of your Log Analytics workspace. You onboard it once per tenant; it is billed to an **Azure subscription and resource group** you choose.
- **Microsoft Sentinel graph** is built on top of that lake. It stores data as **nodes** (users, devices, files, groups) and **edges** (relationships between them).
- The **Defender portal** is where you use it: under **Microsoft Sentinel > Graphs**, and inside the incident graph and advanced hunting (D3.1.5).
- **Custom graphs** are written in a **Jupyter notebook** (a document that mixes Python code and output) inside **Visual Studio Code** with the Microsoft Sentinel extension.
- **Licence note:** the data lake does **not** need a Defender XDR licence — Sentinel in the Defender portal plus an Azure subscription is enough. Custom graphs cost money (graph meter). Practise only with tiny data, or treat this page as a portal tour.

New to these? Read the Foundations pages linked above.

## In one sentence

Microsoft Sentinel graph is the relationship layer over the Sentinel data lake: it powers Microsoft's built-in graph views (blast radius, hunting graph, Purview data risk graphs) and lets you build your own **custom graphs**, which you query with **GQL** on the **Graphs** page of the Defender portal.

## Why it exists

Some questions are about **connections**: "If this account is compromised, what can it reach?" In tables, every hop is another join. In a graph, a hop is following a line.

Think of a family tree versus a pile of birth certificates. "Who is my third cousin?" is hard from the pile and easy from the tree. Sentinel graph turns the pile (the data lake) into the tree.

## What actually matters

### 1. Built-in experiences vs custom graphs

| | **Built-in (embedded) graphs** | **Custom graphs** (preview) |
|---|---|---|
| Who models nodes and edges | Microsoft | You, in a notebook |
| Where you see them | Incident graph (**blast radius**), advanced hunting (**hunting graph**), Purview **Insider Risk Management** and **Data Security Investigations** (**data risk graph**) | **Microsoft Sentinel > Graphs** in the Defender portal; VS Code notebooks; graph query APIs |
| Setup | Auto-provisioned once the data lake exists | Build + publish a graph job |
| Query language | Scenarios and clicks (or KQL `make-graph` on exposure tables) | **GQL** (Graph Query Language) |
| Cost | No graph charge for hunting graph, blast radius or Purview data risk graphs (reaching them through the **MCP graph tools** does trigger the graph meter) | **Microsoft Sentinel graph meter**, per compute hour: building in a notebook, and every query (notebook, Graphs page, graph query APIs, MCP tools) |

==!Purview data risk graph is being retired.== New onboarding stops 24 September 2026 (Insider Risk Management) and 30 September 2026 (Data Security Investigations); the feature is gone after **24 November 2026** (IRM) and **30 November 2026** (DSI). Expect it to vanish from questions; do not pick it as the answer for new setups.

### 2. Prerequisite: onboard to the data lake and graph

Onboarding the data lake also provisions the graph. Know these requirements:

- **Defender portal and Sentinel configured**; a **primary Sentinel workspace connected to the Defender portal**. ==+A Defender XDR licence is not required.==
- An **Azure subscription and resource group** for billing. You must be the **direct subscription owner** — owner at management-group level is not enough.
- **Read** access to the workspaces to attach. Only Defender-connected workspaces **in the same region as the primary workspace** are attached. The lake is created **in that region**.
- Roles for the onboarding account: **Subscription Owner or Contributor** (billing), **Global Administrator or Security Administrator** (authorize ingestion from Entra, Microsoft 365, Azure).

Onboarding also: loads **Entra**, **Microsoft 365** and **Azure Resource Graph** asset data into lake **System tables**; mirrors analytics-tier data to the lake; moves auxiliary tables into the lake, where they are ==!no longer reachable from advanced hunting==; creates a managed identity named `msg-resources-` plus a GUID with **Reader** on the onboarded subscriptions (do not delete it). Setup itself takes **up to 60 minutes**; once ingestion is enabled, data takes **90–120 minutes** to appear. ==!Customer-managed keys (CMK) are not supported.== Workspaces created **after** onboarding are not added automatically (support ticket). ==!Deleting the billing subscription or resource group suspends the lake; ingestion stops after 3 days.== Offboarding needs a support request.

### 3. Build a custom graph

1. **Model** it in a Jupyter notebook in VS Code (Microsoft Sentinel + Jupyter extensions): pick a Microsoft Sentinel Spark pool as the kernel (the first cell takes about **five minutes** to start the Spark session), read lake tables with **PySpark** (Python for Spark), shape **node** and **edge** data, and build with the `sentinel_graph` library. You can write the code yourself or use **AI-assisted graph authoring**.
2. **Persist** (Microsoft says *materialize*) it with a **graph job** — an interactive-session graph ==!vanishes when the session closes==. **On demand** graphs are kept **30 days**; **scheduled** graphs rebuild on your schedule.
3. **Query and visualize** it on the **Graphs** page. Notebooks can also run graph algorithms (GraphFrames and Sentinel graph traversal functions).

Custom graphs run on Microsoft Fabric under the hood. You only see data you are allowed to read: datasets you cannot access are silently left out of the graph.

Permissions for each step:

| Operation | Needs |
|---|---|
| Model and build a notebook graph | Custom Defender unified RBAC role with **data (manage)** over the Sentinel data collection |
| Persist a graph in the tenant | Entra **Security Operator**, **Security Administrator** or **Global Administrator** |
| Query a persisted graph | Custom unified RBAC role with **security data basics (read)** |

A **Sentinel-scoped** user cannot create custom graphs, and cannot open **Graphs** without Security Reader, Security Operator, Security Administrator or Global Administrator.

### 4. Analyze relationships on the Graphs page

**Microsoft Sentinel > Graphs** lists your published custom graphs as tiles. **Query graph** opens the editor:

- **Schema** shows the node types, edge types and their properties.
- **Getting started** suggests queries; **Visualize any graph** is the starter.
- Highlight a query, **Run GQL query**. Results show on a **graph** tab and a **Table** tab (search, sort, JSON, **export to CSV**).
- **Explore connected assets** (right-click, or **+**) expands one hop. **Filters** by node or edge type; grouping; node details.
- **Share query** copies a link to the query, the code, or the graph results.

GQL reads like a picture of the pattern: `(node)-[edge]->(node)`.

```gql
MATCH (x)-[y]->(z)
RETURN *
LIMIT 100
```

Read it: *find any node x with an edge y pointing to a node z; return them all; stop at 100 matches.* The default `LIMIT` keeps the canvas responsive — raise or remove it to see more.

```gql
MATCH p=(g1:EntraGroup)-[cg]->{1,8}(g2)
WHERE g1.displayName = 'tmplevel3'
RETURN *
```

Read it: *from the Entra group tmplevel3, follow edges one to eight hops — every nested group and member.* In KQL that needs a self-join per level.

For comparison, the KQL graph operators work on the exposure tables in advanced hunting (D3.1.5):

```kql
// Defender advanced hunting — KQL's own graph operators on the exposure graph
ExposureGraphEdges
| where EdgeLabel =~ "member of"   // =~ is case-insensitive equals
| make-graph SourceNodeId --> TargetNodeId with ExposureGraphNodes on NodeId
| graph-match (member)-[e*1..3]->(grp)
    project Member = member.NodeName, Group = grp.NodeName
| take 100
```

### 5. Graphs for AI agents (know it exists)

The **Sentinel MCP server** (Model Context Protocol — the way AI agents call tools; D3.2.4) has a graph tool collection: `find_blastradius`, `find_walkable_paths`, `find_exposure_perimeter`, `find_connected_nodes`, `find_nodes` and `get_graph_context` (a helper that lists the valid node labels and properties the others accept). They reason over the exposure, hunting and blast radius graphs in plain-language prompts. They need the data lake onboarded and at least **Exposure Management read-only**. Installing them is free; ==!using them triggers the graph meter==.

## Exam traps

- ==!"Sentinel graph needs a Defender XDR / E5 licence."== ==+The data lake and graph work with Sentinel in the Defender portal alone==; built-in Defender graphs still need Defender data.
- ==!"An interactive notebook graph is saved."== ==+Only a graph job persists it== — on demand for 30 days, or scheduled.
- ==!"Query custom graphs with KQL."== ==+Custom graphs use GQL== on the Graphs page. KQL's `make-graph`/`graph-match` is for in-query graphs such as the exposure tables.
- ==!"Graphs is in the Azure portal's Sentinel blade."== ==+Defender portal, Microsoft Sentinel > Graphs.==
- **Cost:** ==!"Hunting graph and blast radius are billed on the graph meter."== ==+They are free; custom graphs and MCP graph tools are billed.==
- **Billing:** must be the **direct** subscription owner; lake region = primary workspace region; only same-region, Defender-connected workspaces attach.
- **Custom graph persist permission** is an Entra role (Security Operator / Security Admin / Global Admin); model and query use **unified RBAC** custom roles.
