## Azure first

- An **Azure subscription** is the billing and permission boundary that holds your **resources** (VMs, storage accounts, SQL databases, key vaults). Defender for Cloud works **per subscription**: you switch its plans on per subscription.
- **Microsoft Defender for Cloud** is Azure's own security service. Its free part grades your configuration (posture). Its paid **Defender plans** watch running workloads and raise **security alerts**. No plan, no alerts.
- **Azure RBAC** roles decide who sees and acts. Defender for Cloud adds two of its own: **Security Reader** (look) and **Security Admin** (look, dismiss, change policy).
- A **Logic App** is a no-code workflow in Azure. Defender for Cloud's **workflow automation** fires one when an alert appears — the same idea as a Sentinel playbook.

New to these? Read the Foundations pages linked above.

> **Not licence-blocked — you can lab this.** Turn on a Defender plan (30-day trial for most plans) on a test subscription, then use **Sample alerts** to create fake alerts on simulated resources. Delete the resource group and turn the plan off afterwards.

## In one sentence

Defender for Cloud's paid **workload protection plans** raise **security alerts** (and group related ones into **incidents**) when something attacks your Azure, hybrid or multicloud resources; you triage them by severity, read the alert, then use the **Take action** tab to mitigate, harden, run a **Logic App**, or **suppress** future false positives.

## Why it exists

Think of a block of rented storage units. The landlord's free inspection checks that every door has a lock (that is posture). But a lock does not tell you someone is picking it right now. For that you pay for a guard on each corridor — one who knows what lock-picking on a *storage* unit looks like, another who knows what it looks like on the *vault*. Each Defender plan is a specialist guard for one resource type. When a guard sees something, you get an alert with what happened, which unit, and what to do.

## What actually matters

**1. Alerts come from plans.** Defender for Cloud has two halves. **CSPM** (posture management) gives you secure score and recommendations. **CWP** (cloud workload protection) is the set of paid **Defender plans** that produce alerts. The plans the training covers:

| Plan | Watches | Example alerts |
|---|---|---|
| **Defender for Servers** P1 / P2 | Windows/Linux VMs in Azure, AWS, GCP, on-premises (via Azure Arc). P1 deploys **Defender for Endpoint**; P2 adds everything else, including **DNS threat protection** | Malicious tool (Mimikatz), DNS tunnelling, C2 domains |
| **Defender for Storage** | Blob, Files, Data Lake | Anonymous access, compromised credentials, malicious content |
| **Defender for Databases / SQL** | Azure SQL, SQL on machines, PostgreSQL, MySQL, Cosmos DB | Brute force, anomalous access and query patterns |
| **Defender for App Service** | Web apps on dedicated App Service plans | Widespread scanning, distributed attacks |
| **Defender for Containers** | AKS, other Kubernetes, EKS; container registries | Suspicious activity on cluster control plane or Linux nodes |
| **Defender for Key Vault** | Key vault access | Access from Tor or suspicious IP, unusual secret reads |
| **Defender for Resource Manager** | Every management operation (portal, CLI, API) | Exploitation toolkits (MicroBurst, PowerZure), suspicious extension scripts |
| **Defender for APIs** | APIs | (listed in the module; no alert detail taught) |
| **Defender for AI Services** | Azure AI workloads | Jailbreak attempts, data exposure (newer plan; not in the training module) |

==!There is no separate Defender for DNS plan to enable any more.== Since **1 August 2023**, new subscriptions get DNS alerts as part of **Defender for Servers Plan 2**; only subscriptions that already had the standalone plan kept it, and in July 2026 the plan-enablement API started blocking new onboarding to it. The protection scope did not change: it watches resources that use Azure's default DNS resolvers, with no agent. Network-layer alerts need the VM to have a **public IP** (or sit behind a public load balancer).

**2. Alert anatomy and severity.** Each alert has a severity, status, activity time, description, affected resource (with its Azure **tags** for context), MITRE ATT&CK tactic, and an **Alert details** tab (IPs, files, processes). Severity is how sure Defender is:

| Severity | Meaning |
|---|---|
| **High** | Very likely compromised; look now (e.g. Mimikatz ran) |
| **Medium** | Probably suspicious; often anomaly/ML based (e.g. sign-in from unusual location) |
| **Low** | Might be benign or a blocked attack (e.g. log cleared) |
| **Informational** | Only seen inside an incident or via the API |

Alerts stay **90 days**, even if the resource was deleted. Export options: **Download CSV** (one-off), **continuous export** to a Log Analytics workspace or Event Hub, or a **Sentinel connector**.

**3. Incidents.** A **security incident** is a set of related alerts that Defender for Cloud's correlation joined into one attack story. In the Azure portal it sits in the same **Security alerts** list with a different icon. Its page has an **Alerts** tab and the same **Take action** tab. Some alerts also link a **threat intelligence report** (PDF): **Activity Group**, **Campaign**, or **Threat Summary**.

**4. The Take action tab — the core of remediation.**

| Section | What it gives you |
|---|---|
| **Inspect resource context** | Jumps to the resource's activity logs around the alert |
| **Mitigate the threat** | Manual remediation steps for this alert |
| **Prevent future attacks** | Security recommendations to harden the resource |
| **Trigger automated response** | Run a Logic App now (**Trigger logic app**) |
| **Suppress similar alerts** | **Create suppression rule** for this alert type |

The tab also has **Configure email notification settings** — who gets alert emails for this subscription. When done, change the status. The values are **Active**, **In progress**, **Resolved** and **Dismissed**. A dismissed alert drops out of the main list; filter on *Dismissed* to see it again. You can change status in bulk with the check boxes and **Change status**.

**5. Suppression rules.** A suppression rule auto-dismisses future alerts that match. The alerts are ==@still generated== — their status is just set to **Dismissed**, so they do not notify. Facts:

- Create from **Security alerts > Suppression rules > Create new suppression rule**, or from an alert's **Take action > Suppress similar alerts**.
- Scope: **subscriptions** (portal or REST API) or **management groups** (only through **Azure Policy**).
- ==!Works only for alert types that have fired at least once.==
- Conditions can narrow it by entity (IP, process, user, resource, location). **Simulate** shows how many past alerts would have matched.
- Name: 2–50 characters, letters/numbers, `-` and `_` only.
- Deleting a rule does **not** re-open alerts it already dismissed.
- Expiry: the current docs offer **Custom** (a date) or **None** (runs indefinitely). The training unit says rules "can run for up to six months". ==!The sources disagree== — trust the product docs and portal.

**6. Workflow automation.** On the Defender for Cloud menu, **Workflow automation > Add workflow automation** picks a trigger and a **consumption Logic App**. Triggers: **When a Defender for Cloud Alert is created or triggered** (filterable by severity or text such as "SQL"), **When a Defender for Cloud recommendation is created or triggered**, **When a regulatory compliance assessment is created or triggered**. ==!The legacy trigger "When a response to a Microsoft Defender for Cloud alert is triggered" does not work with workflow automation.== Deploy at scale with the built-in Azure Policy **Deploy Workflow Automation for Microsoft Defender for Cloud alerts** (DeployIfNotExists).

**7. Defender portal integration.** All Defender for Cloud alerts and incidents (except **Informational**) appear in the **Defender portal** queues and correlate with endpoint and identity alerts. Status changes **sync both ways** — except ==!Defender for Endpoint alerts on cloud resources==, which show in both portals but do **not** sync status. Sentinel customers using the Defender XDR incident connector should switch to the **Tenant-based Microsoft Defender for Cloud** connector and disconnect the legacy subscription-based one, to avoid duplicate alerts. Each VM gets its own entity page. Hunting tables include `CloudAuditEvents`, `CloudProcessEvents` and `CloudStorageAggregatedEvents`. Viewing them there needs a Defender **unified RBAC** role for Defender for Cloud, or Entra **Global Administrator / Security Administrator**. Defender for Cloud's own console is also moving in: **Cloud security > Overview** in the Defender portal is in public preview for tenants with a paid plan. The Azure portal pages below still work and are what the training shows.

**8. Who can do what (Azure RBAC).**

| Action | Security Reader / Reader | Security Admin | Contributor (RG) | Contributor / Owner (subscription) |
|---|---|---|---|---|
| View alerts and recommendations | ✔ | ✔ | ✔ | ✔ |
| **Dismiss alerts** | — | ✔ | — | ✔ |
| Apply a recommendation (**Fix**) | — | — | ✔ | ✔ |
| Create / delete **suppression rules** | — | ✔ | — | Owner |
| Create **workflow automation** | — | ✔ (+ write on target, Logic App Contributor to build the app) | — | Owner |
| Create **sample alerts** | — | — | — | Contributor |

## Where it lives

| Task | Portal path |
|---|---|
| Alert list | Azure portal > **Microsoft Defender for Cloud > Security alerts** |
| Alert details | select alert > **View full details** > **Alert details** / **Take action** tabs |
| Suppression rules | **Security alerts > Suppression rules** |
| Sample alerts | **Security alerts > Sample alerts** (toolbar) |
| Workflow automation | **Microsoft Defender for Cloud > Workflow automation** |
| Plans on/off | **Environment settings** > subscription > **Defender plans** |
| Same alerts in Defender | Defender portal > **Incidents & alerts > Alerts / Incidents** (filter *alert subscription ID*) |
| New cloud console (preview) | Defender portal > **Cloud security > Overview** |

```bash
# list alerts in the subscription
az security alert list --output table
# set one alert's status: dismiss | activate | resolve | inprogress
az security alert update --location centralus --name <alertName> --status dismiss
```

```powershell
Set-AzSecurityAlert -Location "centralus" -ResourceGroupName "RSG" -Name "<alertName>" -ActionType Dismiss
```

**Lab tip.** Sample alerts are the safe route: no real attack, simulated resources. The docs also show how to make *real* test alerts — an EICAR file on a VM with Defender for Endpoint, browsing `https://YOUR-APP.azurewebsites.net/This_Will_Generate_ASC_Alert` on App Service (alert within 2–4 hours), or opening a storage SAS URL from the Tor browser. Use only throwaway resources.

### Responding to specific plans (training unit 6)

| Plan | Contact step | Immediate mitigation | Then |
|---|---|---|---|
| **Key Vault** | Was the traffic from inside your tenant? Ask the user/app owner | Unknown IP → turn on the **Key Vault firewall**. Unknown app/user → remove its **role assignment** (Azure RBAC) or access policy (legacy) | List what was read; **rotate** those secrets, keys, certificates |
| **DNS** (Servers P2) | Ask the resource owner; expected → dismiss | **Isolate** the resource, full antimalware scan, remove unknown software, restore to a known-good state | Fix the machine's recommendations |
| **Resource Manager** | Ask the resource owner; expected → dismiss | Delete unfamiliar accounts / change credentials; remove unknown runbooks, IAM permissions and resources; reimage VMs | Review the **Activity log** for everything the account did |

## Exam traps

- ==!Enabling Defender for Cloud gives you threat alerts.== ==+Alerts need a paid Defender plan for that resource type.== The free tier is posture only.
- ==!A suppression rule stops the alert from being generated.== ==+It is generated and auto-set to Dismissed.==
- ==!You can suppress an alert type before it ever fires.== ==+Only types already triggered at least once.==
- **Suppress across a management group** → ==+Azure Policy==, not the portal page.
- ==!Security Reader can dismiss alerts.== ==+Security Admin (or Contributor/Owner at subscription) can.==
- **Automatically email someone / open a ticket when an alert fires** → ==+workflow automation (Logic App)==. **Stop alerts about a known scanner** → ==+suppression rule==. **Harden the VM so it does not happen again** → ==+Prevent future attacks (recommendations)==.
- ==!Informational Defender for Cloud alerts show up in the Defender portal.== ==+They are not integrated.==
- **Defender for DNS** questions: the standalone plan is deprecated; ==@Defender for Servers Plan 2== provides DNS threat protection.
- Alerts are kept ==@90 days== even after the resource is deleted.
- ==!Changing an MDE alert's status in Defender for Cloud also closes it in the Defender portal.== ==+Only Defender for Cloud's own alerts sync status; MDE alerts on cloud resources don't.==
- **No network-layer alerts on a VM?** ==+It needs a public IP (or a public load balancer)== and egress not blocked by an external IDS.
- Workflow automation uses **consumption** Logic Apps. To *run* an existing one you need **Logic App Operator**; to *create* one, **Logic App Contributor**.
