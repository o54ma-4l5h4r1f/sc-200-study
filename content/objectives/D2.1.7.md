## Azure first

- **Microsoft Sentinel** is Microsoft's SIEM: it sits on top of a **Log Analytics workspace** (the database of your logs) and runs **analytics rules** (saved KQL queries) on a schedule. A rule that finds something raises an **alert**; alerts are grouped into an **incident** — the case file an analyst works.
- **Two portals.** Sentinel can be used in the **Azure portal** (`portal.azure.com`) or inside the **Microsoft Defender portal** (`security.microsoft.com`). Since **1 July 2025** most brand-new Sentinel tenants are onboarded straight into the Defender portal, and after **31 March 2027** the Azure portal experience is no longer supported. The exam still shows both, so this page names both paths.
- **Azure RBAC role** to work incidents: **Microsoft Sentinel Responder** on the workspace. Reader can only look. Contributor can also delete comments and edit rules.
- **Lab access:** Sentinel runs on your own Azure subscription — this objective is **not** licence-blocked. Sentinel in the Defender portal works without E5.

New to these? Read the Foundations pages linked above.

## In one sentence

A Sentinel incident is a case file of **alerts + entities + evidence**; you triage it (owner, status, severity), investigate it (timeline, entities, graph, logs, UEBA entity pages), act on it (playbook, tasks, comments) and **close it with a mandatory classification**.

## Why it exists

A building's CCTV raises hundreds of motion alarms a night. Nobody can chase each one. The guard desk groups the alarms that belong together ("same person, three doors, ten minutes") into one ticket, notes who is on it, and writes how it ended. Sentinel incidents are that ticket. The point is one record per real event, with an audit trail of who did what.

A first incident, start to finish. Say the rule "Multiple failed sign-ins followed by success" fires for user *alice*.

1. **Queue.** Filter **Owner** to yourself, or take an unassigned **New** incident. Set yourself as owner and Status **Active**, so nobody else picks it up.
2. **Why am I here?** Open **View full details**. Read the **Incident timeline**: which alerts, in what order, which MITRE tactics.
3. **Who is involved?** Check the **Entities**: alice's account, the source IP, the host. Open alice's **Timeline** for the last 7 days. Is there an alert from *outside* this incident? Add it.
4. **Is this normal for alice?** Look at **Top insights** and alice's **entity page**: UEBA anomalies, usual locations, peers.
5. **Dig.** Open the **Logs** panel from an alert to see the raw sign-in rows. Use the **investigation graph** to see what else the IP touched.
6. **Act.** **Run playbook** (for example, disable the user). Tick off the **tasks**. Write what you did in a **comment**.
7. **Close.** Status **Closed**, classification **True Positive – suspicious activity**, comment, **Apply**.

## What actually matters

**1. The vocabulary.** An **alert** is one detection. An **incident** groups one or more alerts. **Entities** are the "persons of interest" an analytics rule maps out of the data: user account, host, IP address, URL, file (hash), Azure resource, mailbox, and more. One user can be named several ways (Entra object GUID, UPN, or name + NT domain); Sentinel merges these into one entity only when the alert gives enough identifiers. A bare username with no domain becomes a *separate* entity. **Evidence** on the incident page is three things: **Events**, **Alerts** and **Bookmarks**. A **bookmark** is a row of hunting results you saved as evidence.

**2. Triage from the queue.** On the **Incidents** page, select one incident and use the details pane on the right: set **Owner** (a user or group), **Status** (**New → Active → Closed**; every incident starts as **New**), **Severity** (**Informational, Low, Medium, High** — first set by the rule, change it only if you disagree), add **tags** and **comments**. Escalating to tier 2 means changing the **Owner**, not the severity. The **Actions** button offers **Investigate**, **Run playbook**, **Create automation rule** (for incidents from the same analytics rule) and **Create team (Preview)** in Microsoft Teams. If the incident came from Defender XDR, **Investigate in Microsoft Defender XDR** opens the same incident there; status, owner and closing reason sync both ways. A Sentinel incident holds at most **150 alerts**; a bigger Defender XDR incident shows as "150+" with a link back. Default search covers **Incident ID, Title, Tags, Owner, Product name**; advanced search shows **50** results at a time and is case sensitive.

**3. The incident details page (Azure portal).** Left panel: the incident's details, **Evidence** (Events / Alerts / Bookmarks open a **Logs** panel without leaving the page) and the first **four** entities. Two tabs:

| Overview tab widget | What it tells you |
|---|---|
| **Incident timeline** | Alerts and bookmarks in order, with severity, provider and MITRE tactics |
| **Similar incidents** | Up to **20** look-alikes, with a **Similarity reason** (same entities, same analytics rule, or same alert details). Looks back **14 days** from the last alert |
| **Entities** | Every entity in the incident |
| **Top insights** | Prebuilt queries about the entities. Time frame: **24 hours before the first alert** to the last alert |

The **Entities** tab gives each entity **Info**, **Timeline** (last **7 days**, including alerts *not* in this incident — a **+** adds them) and **Insights**. From an entity you can **View full details** (entity page), **Add to TI** (IP, URL, domain, file hash) or **Run playbook (Preview)**. **View full details** exists only for user account, host, IP address, Azure resource and IoT device.

**4. The investigation graph.** **Investigate** opens a map of the incident's entities. Hover an entity for **exploration queries** (for example *Related alerts*), expand it to pull in more related entities, and use the **timeline** at the bottom to replay when each alert happened. Two limits: the graph needs **entity mappings** (no entities, no graph) and works only for incidents up to **30 days old**. In the Defender portal this view is replaced by the **attack story / incident graph** (D2.1.9).

**5. Document and hand off.** **Activity log** records every change, human or automated, and holds comments. Only a comment's author can edit it; only **Microsoft Sentinel Contributor** can delete one. Limits: **30,000 characters** per comment, **100 comments** per incident. **Incident tasks** are a checklist on the incident. An **automation rule** (*Add task* action) adds a fixed list; a **playbook** can add a task *and* mark it complete (for example, after it reset a password); an analyst can add one by hand. **Microsoft Sentinel Responder** is enough to add tasks and to create the automation rule; building the playbook needs **Logic App Contributor**. While in the **Logs** panel you can tick rows and choose **Add bookmark to the current incident**. Bookmarks join an incident through **Hunting > Bookmarks > Incident actions > Add to existing incident**. Bookmarks can only be **created** in the Azure portal; the Defender portal can view them but not add new ones.

**6. Close with a classification.** Status **Closed** forces a classification. The two portals use different words for the same idea:

| Azure portal (Sentinel) | Defender portal (incident) |
|---|---|
| **True Positive** – suspicious activity | **True positive** + determination (Multistage attack, Malicious user activity, Compromised account, Malware, Phishing, Unwanted software, Other) |
| **Benign Positive** – suspicious but expected | **Informational, expected activity** (Security test, Line-of-business application, Confirmed activity, Other) |
| **False Positive** – incorrect alert logic | **False positive** (Not malicious, Not enough data to validate, Other) |
| **False Positive** – incorrect data | |
| **Undetermined** | |

Add a **comment** before **Apply**. When a Defender XDR incident syncs, its classification is translated: Defender *True positive* → Sentinel *True Positive – suspicious activity*; *False positive* → *False Positive – incorrect data*; *Informational, expected activity* → *Benign Positive*; *Not set* → *Undetermined*. *Incorrect alert logic* has no Defender equivalent. Defender status **Active** shows in Sentinel as **New**.

> **Sources disagree.** The training module (unit 5) lists "False Positive – ==@Inaccurate data==" and says *every* Entra user who investigates must be in **Directory Readers**. The product docs say "incorrect data", and that only **guest** users need Directory Readers (members have it by default). The product docs win.

**7. UEBA and entity pages.** **User and Entity Behavior Analytics (UEBA)** learns what is normal for each user, host and IP, compared to **itself**, its **peers** and the **organization**, and flags what is not. It writes to tables: `BehaviorAnalytics` (enriched activity with deviations), `IdentityInfo` (user profiles from Entra ID, and AD through Defender for Identity), `UserPeerAnalytics` (top **20** peers) and `Anomalies`. **Entity pages** show one entity's info, timeline and insights over a time range you pick. In the Azure portal they live under **Entity behavior**. In the Defender portal they are the normal user, device, IP and Azure resource pages with a **Sentinel events** tab. UEBA gives two scores: `InvestigationPriority` in `BehaviorAnalytics` (**0–10**, one event, near real time) and `AnomalyScore` in `Anomalies` (**0–1**, a pattern over many events, batch ML). A first-ever Azure action scores high on the first and low on the second. Expect useful insights about **one week** after you turn UEBA on. Turning it on needs the Entra **Security Administrator** role plus (least privilege) **Microsoft Sentinel Contributor** on the workspace and **Log Analytics Contributor** on the resource group. UEBA has no extra licence or cost of its own, but its tables add storage charges. Entity pages exist for **user account, host, IP address (preview), Azure resource (preview)** and **IoT device (preview, Azure portal only)**.

## Where it lives

| Task | Azure portal (Sentinel) | Defender portal |
|---|---|---|
| Incident queue | **Microsoft Sentinel > Threat management > Incidents** | **Investigation & response > Incidents & alerts > Incidents** (case-management view: D2.1.10) |
| Full incident | **View full details** | Open the incident (attack story) |
| Hunting / bookmarks | **Threat management > Hunting > Bookmarks** | **Microsoft Sentinel > Threat management > Hunting** (view only) |
| Entity pages | **Threat management > Entity behavior** | **Assets > Identities** or **Assets > Devices** > *entity* > **Sentinel events** |
| Turn UEBA on | **Configuration > Settings > Settings** tab **> Set UEBA** (older flow; current docs show only the Defender path) | **System > Settings > Microsoft Sentinel > UEBA** tab > **Turn on UEBA feature** |
| Tasks via automation | **Configuration > Automation** > automation rule > **Add task** | **Microsoft Sentinel > Configuration > Automation** |

```kql
// Everything UEBA found unusual for one user in the last 7 days
BehaviorAnalytics
| where TimeGenerated > ago(7d)
| where UserName =~ "alice"
| where InvestigationPriority > 0
| project TimeGenerated, ActivityType, ActionType, SourceIPAddress, InvestigationPriority
| order by InvestigationPriority desc
```

```kql
// Your saved hunting evidence
HuntingBookmark
| where TimeGenerated > ago(30d)
| where SoftDeleted == false
| project TimeGenerated, BookmarkName, CreatedBy, Notes, QueryText
```

## Exam traps

- ==!Closing an incident without a classification== — impossible. ==+Classification is mandatory on Closed.==
- **Benign Positive** (Azure portal) = **Informational, expected activity** (Defender portal). Same meaning, different label. A pen test is ==+benign==, not false.
- Two flavours of false positive in the Azure portal: ==@incorrect alert logic== (fix the rule) vs ==@incorrect data== (fix the source).
- ==!Every investigator needs Directory Readers== (training module) — product docs: only ==+guest users== need it.
- ==!Microsoft Sentinel Reader can assign incidents== — no. You need ==+Microsoft Sentinel Responder==. Deleting a comment needs ==+Microsoft Sentinel Contributor==, even for your own.
- A **guest** user assigning incidents also needs the Entra **Directory Readers** role.
- The entity **Timeline** card on the incident is fixed at **7 days**; the full **entity page** lets you choose the range.
- ==!Bookmarks can be created in advanced hunting== — no. Only **Microsoft Sentinel > Hunting** in the **Azure portal**.
- ==!Incident tasks run themselves.== Tasks are a checklist. **Automation rules** only *add* them; a **playbook** can add one and mark it complete; otherwise an analyst ticks it.
- Escalate to the next tier = change the ==+Owner==, not ==!Severity== or Status.
- The investigation graph ==!works for any incident== — no: it needs ==+entity mappings== and incidents up to **30 days** old.
- The **investigation graph** is an Azure-portal view. In the Defender portal you get the ==@attack story / incident graph==.
- UEBA: no licence fee, but ==!not free storage==.
