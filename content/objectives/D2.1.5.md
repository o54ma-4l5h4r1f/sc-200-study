## Azure first

- **Microsoft Entra ID** is the identity service behind Azure and Microsoft 365. Every user sign-in goes through it and is written to the **sign-in logs**.
- **Conditional Access** is Entra's rule engine for sign-ins: *if* this user, app, location or **risk** *then* allow, require MFA, require a password change, or block.
- **Microsoft Entra ID Protection** (formerly *Identity Protection*) scores how likely a sign-in or an account is to be in an attacker's hands. Full features need **Entra ID P2** (or Entra Suite).
- Its pages live in the **Microsoft Entra admin center** (`entra.microsoft.com`), not the Azure portal or the Defender portal — though its alerts also appear in Defender.
- **Entra roles** (Security Reader, Security Operator, Security Administrator, User Administrator, Conditional Access Administrator) decide who can look, who can mark risk, who can reset passwords and who can write policy.

New to these? Read the Foundations pages linked above.

> **Licence-blocked, but trialable.** ID Protection needs Entra ID P2. Your Azure subscription's tenant is Entra ID Free, which shows only a limited risky-users view. Microsoft offers a 30-day **Entra ID P2 trial** that works in an Azure-only tenant; real risk detections still need real (or simulated, e.g. Tor-browser) risky sign-ins. Treat the screenshots as the lab unless you start a trial.

## In one sentence

ID Protection turns sign-in signals into **risk detections**, rolls them up into **sign-in risk** and **user risk** (low / medium / high), lets you investigate them in the **Risky users**, **Risky sign-ins** and **Risk detections** reports, and remediates either automatically through **risk-based Conditional Access** (MFA or a secure password change) or by an admin action — **reset password, confirm compromised, confirm safe, dismiss, block**.

## Why it exists

Stolen passwords do not set off malware alarms. The attacker simply signs in. The only clues are in *how* they sign in: from a Tor exit node, from Lagos ten minutes after a sign-in from Leeds, with a token that looks replayed, or with a password Microsoft found in a leaked dump.

Picture a bank card. The card works, the PIN is right, but the bank's fraud desk sees a cash withdrawal in another country an hour after you bought coffee at home. It does not decline every odd payment. It texts you to confirm (MFA). If the card details are on a criminal forum, it cancels the card and sends a new one (password change). ID Protection is that fraud desk for sign-ins.

## What actually matters

**1. Two kinds of risk.** **Sign-in risk** = the probability that *this sign-in* was not made by the account owner. **User risk** = the probability that *the account* is compromised. Both are **Low, Medium or High**. Detections are **real-time** (scored during sign-in, so a policy can act immediately) or **offline** (found later, so they raise risk after the fact). Un-remediated sign-in risk feeds user risk. Detections that matter:

| Detection | Risk | Note |
|---|---|---|
| Anonymous IP address | Sign-in | Tor, anonymiser VPNs |
| Atypical travel | Sign-in | Two places too far apart for the time between |
| Unfamiliar sign-in properties | Sign-in | New device, location, IP, user agent for this user |
| Malicious IP / Verified threat actor IP | Sign-in | Microsoft threat intelligence |
| Password spray | Sign-in | Fires only where the spray **succeeded** in your tenant |
| Anomalous token / Token issuer anomaly | Sign-in | Token replay or a compromised SAML issuer |
| Suspicious browser | Sign-in | Odd activity across tenants from one browser |
| **Leaked credentials** | User | Always **high**; the valid password is out |
| Microsoft Entra threat intelligence | Both | Known attack pattern |
| **Admin confirmed user compromised** | Listed as sign-in; raises user risk to High | Created when an admin clicks *Confirm user compromised* |
| Suspicious MFA authentication approval | Sign-in | Authenticator approval that looks like phishing; flagged **High** |
| Attacker in the Middle, Possible attempt to access PRT, Suspicious sending patterns | User | Signals from Defender for Cloud Apps, Defender for Endpoint, Defender for Office 365 |
| Anomalous user activity, Suspicious API traffic, Suspicious credential addition, User reported suspicious activity | User | Odd directory changes, Graph enumeration, a new MFA method added suspiciously, user denied an MFA prompt and reported it |
| New country, Activity from anonymous IP, Suspicious inbox forwarding | Sign-in | Come from **Defender for Cloud Apps** |

Without P2 you see **Additional risk detected** (`riskEventType` = `generic`) with no details. A few detections are *nonpremium* (work on Free/P1): Anonymous IP address, Leaked credentials, Entra threat intelligence, Admin confirmed user compromised. Free and P1 tenants get only a limited **Risky users** view (medium and high only, no details or history). New users start in **learning mode** (minimum five days) for *Unfamiliar sign-in properties*.

**2. The three reports and the dashboard.** In **ID Protection** you get **Risky users** (who is at risk, risk history, all their risky sign-ins), **Risky sign-ins** (up to **30 days**; risk level, detection types, Conditional Access result, MFA, device, app, location) and **Risk detections** (up to **90 days**; each detection with a link into Defender for Cloud Apps where relevant). The **Dashboard** shows attack volumes for the last 30 days, blocked vs not-yet-remediated, a map, and recommendations. Risk states you will see: **At risk**, **Remediated**, **Dismissed**, **Confirmed safe**, **Confirmed compromised**. Common risk details: *User passed multifactor authentication*, *User performed secured password reset*, *AI confirmed sign-in safe*.

**3. The analyst's verbs.** This is the most tested table on the page.

| Action | Use when | Effect |
|---|---|---|
| **Confirm user compromised** | True positive | User risk → **High**; new detection *Admin confirmed user compromised*; user-risk policy now forces remediation |
| **Confirm sign-in compromised** | That sign-in was the attacker | Sign-in and user aggregate risk → High |
| **Reset password** | Contain a compromised account | Revokes current sessions; closes the user's risk. **Generate a temporary password** (you tell the user; risk detail *Admin generated temporary password for user*) or **require the user to change it** (user must already be MFA-registered) |
| **Block user** | Attacker can pass MFA or reset the password | Stops sign-in |
| **Confirm user safe** / **Confirm sign-in safe** | False positive | Risk removed; the user goes into **learning mode** |
| **Dismiss user risk** / **Dismiss sign-in risk** | **Benign** true positive (pen test, approved app) | Risk closed; ==!password unchanged==, similar activity is still evaluated |
| **Investigate with Microsoft 365 Defender** | Wider attack? | Opens the user in the Defender portal |

**Sources disagree — product docs win.** The training unit (unit 6) says to *dismiss* user risk when a reset is impossible, "for example, the user has been deleted". The current docs say the opposite: ==!admins can't dismiss risk for deleted users==; a deleted user stays in the report until you open a Microsoft support case. The docs define *dismiss* as the benign-positive action. The same unit says "require the user to reset" needs MFA **and SSPR** registration; the docs now say the risk-driven secure password change is MFA + change, ==@not the SSPR flow== (an SSPR reset also remediates user risk, though).

**4. Self-remediation through Conditional Access.** Microsoft's recommended pair, built in **Entra ID > Conditional Access** (not in ID Protection):

| Policy | Condition | Grant | Session |
|---|---|---|---|
| **Sign-in risk** | Sign-in risk **Medium and High** | **Require authentication strength** → *Multifactor authentication* | **Sign-in frequency: Every time** |
| **User risk** | User risk **High** | **Require risk remediation** (auto-adds *Require authentication strength*) | **Sign-in frequency: Every time** (mandatory) |

User-risk policies can grant **Require risk remediation**, **Require password change** or **Block access**; sign-in-risk policies can **require MFA**, **require reauthentication** (sign-in frequency), allow or block. Rules: ==!never put sign-in risk and user risk in the same policy==; exclude **break-glass** accounts; start in **Report-only**; users must already be **MFA-registered** (hybrid users also need **password writeback**) or they are **blocked**. **Require risk remediation** handles password users (secure password change, then sessions revoked), passwordless users (sessions revoked, sign in again) and an **attacker-added device** (the Entra device object is disabled, sessions revoked). It remediates user risk only, and is not supported for guests. Precedence if a user hits several: **Block** > **Require risk remediation** > **Require password change**.

==!The legacy user-risk and sign-in-risk policies inside ID Protection were retired on 1 October 2026.== The training exercise still walks *ID Protection > User risk policy*. Today you build these as Conditional Access policies. The ID Protection **MFA registration policy** still exists; it makes sure users can self-remediate.

Two automatic behaviours to know. **Token-theft detections** (Entra threat intelligence, Anomalous token, Attacker in the Middle, Verified threat actor IP, Token issuer anomaly) are ==!no longer auto-remediated by MFA== — the user needs a secure password change. And ID Protection **blocks very-high-confidence risky sign-ins on its own** (often legacy authentication): the user gets error **50053**. ID Protection can also **dismiss** risk itself (risk detail *Microsoft Entra ID Protection assessed sign-in safe* / *AI confirmed sign-in safe*).

**5. Who can do what.**

| Task | Least-privileged role |
|---|---|
| View risk reports | **Global Reader** (Security Reader also works) |
| Dismiss user risk / confirm safe or compromised | **Security Operator** |
| Reset a user's password | **User Administrator** (from inside ID Protection: Security Operator **plus** User Administrator) |
| Create or edit Conditional Access (risk) policies | **Conditional Access Administrator** (the remediation article also names Security Administrator for "risk-based policies") |
| Everything in ID Protection | **Security Administrator** — but ==!it cannot reset passwords== |

If the action buttons are grey, your role is too low.

**6. Workload identities.** ID Protection also scores **service principals** (apps), not just people: **Risky workload identities** plus a *Workload identity detections* tab. Detections include leaked credentials (for example a secret pushed to GitHub), suspicious sign-ins (baseline learned over 2–60 days), Entra threat intelligence, malicious / suspicious application, anomalous service principal activity, suspicious API traffic and *Admin confirmed service principal compromised*. Admins can **confirm compromised**, **dismiss risk** or **Disable service principal**. Remediation = add a new credential (certificate), remove the old ones, rotate Key Vault secrets it could read. **Managed identities are out of scope.** Conditional Access for workload identities can block risky **single-tenant** service principals (not multitenant or SaaS apps). Graph: `riskyServicePrincipals`, `servicePrincipalRiskDetections`. Licence: the docs say full details and risk-based Conditional Access need **Workload Identities Premium** (without it you still get the detections, with limited detail); the training unit says *Entra ID P2* — the docs win.

**7. The same risk, elsewhere.** ID Protection alerts appear in the **Defender portal** alert queue (filter *Product name* = *AAD Identity Protection*; IDs start `ad`). For hunting, use `EntraIdSignInEvents` in Defender advanced hunting — it replaced `AADSignInEventsBeta` on **19 October 2026** and needs Entra ID P2 — or `SigninLogs` in Log Analytics / Sentinel. Graph exposes `riskDetections`, `riskyUsers` and `signIn`. Copilot can **summarise a risky user**, and the **Identity Risk Management Agent** (Security Copilot, SCUs) suggests **Dismiss risk** or **Reset password** in bulk — details in D2.1.8.

## Exam traps

- ==!Dismiss user risk resets the password.== ==+Dismiss closes the risk only. The password stays as it was — use Reset password to contain a real compromise.==
- **False positive** → ==+Confirm safe==. **Benign true positive** (pen test, known VPN) → ==+Dismiss==. **True positive** → ==+Confirm compromised== then reset / block.
- ==!Sign-in risk is fixed by a password change.== ==+Sign-in risk is self-remediated by MFA; user risk by a secure password change (Require risk remediation).==
- ==!Put user risk and sign-in risk in one Conditional Access policy.== ==+Two separate policies.==
- ==!Configure risk policies under ID Protection > User risk policy.== ==+Since 1 October 2026 risk policies are Conditional Access policies.==
- **Least privilege to dismiss user risk** → ==@Security Operator==. **To reset a password** → ==@User Administrator==. **To view reports** → ==@Global Reader==. **To write risk policies** → ==@Conditional Access Administrator==.
- Users not registered for MFA hit by a risk policy are ==!blocked==, not prompted. Turn on the MFA registration policy first.
- **Leaked credentials** is a **user** risk and always **high**; ==!MFA alone does not remediate it== — the password must change.
- ==!Managed identities get workload-identity risk.== ==+They are out of scope.==
- Report retention: **risky sign-ins 30 days**, **risk detections 90 days**.
- ==!Security Administrator can reset passwords.== ==+Security Administrator has full ID Protection access but cannot reset passwords — that is User Administrator.==
- ==!Dismiss the risk of a deleted user.== ==+You can't; deleted users with risk need a support case.==
- ==!MFA closes an Anomalous token detection.== ==+Token-theft detections are no longer auto-remediated by MFA; require a secure password change.==
