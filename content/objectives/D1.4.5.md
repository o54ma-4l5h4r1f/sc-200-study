## Azure first

- **Log Analytics workspace** — the database under Sentinel. Anomaly results are written into one of its tables, `Anomalies`, which you read with KQL.
- **Analytics rules** (D1.4.3) — Sentinel's detection rules. **Anomaly** is one of the rule types, with its own **Anomalies** tab on the Analytics page.
- **Baseline** — "what normal looks like", learned from past data. Machine learning (ML) here just means: learn normal, flag what's far from it.
- **UEBA** (User and Entity Behavior Analytics, D2.1.7) — a second Sentinel feature that also learns normal behaviour, per user and device. Turning UEBA on needs the Entra role **Security Administrator** plus an Azure role such as **Microsoft Sentinel Contributor** (least privilege: **Microsoft Sentinel Contributor** on the workspace + **Log Analytics Contributor** on the resource group; **Owner** also works). The workspace must have no Azure resource locks.
- **Licence:** fully lab-able with an Azure subscription; no extra licence, but the extra rows cost storage.

New to these? Read the Foundations pages linked above.

## In one sentence

**Anomaly rules** are Microsoft-built ML detections that learn a baseline from your data and write anything unusual into the `Anomalies` table — ==@they create no alerts and no incidents== — and you "configure" them by duplicating a rule, changing its threshold or parameters, testing it in **Flighting** mode and promoting it to **Production**.

## Why it exists

A smoke detector that rings for toast gets its battery pulled. Anomalies are softer signals: "this account logged in 40 times more than usual". One alone isn't a crime. Several at different stages of an attack tell a story. So Sentinel stores them quietly as evidence for hunters, investigators and other rules, instead of ringing the bell each time.

They are also notoriously noisy. Every company's "normal" is different. The **threshold** is the volume knob. The **Flighting** mode is a test bench, so you can try a new setting without losing the old one.

## What actually matters

### 1. Anomaly rules are different from every other rule type

- Built by Microsoft's data science team. You don't write KQL.
- Each rule has a **training period** (typically 7–21 days; many Windows ones train on 21 days). Nothing appears until it's over.
- Output goes to the `Anomalies` table, ==!not to alerts or incidents==. Use them as context in hunting and investigations, or write a scheduled rule (D1.4.3) that alerts when an anomaly lines up with something else.
- In the current product, anomaly rules are ==@enabled by default==.
- Some detections are retired: the two DGA (domain generation algorithm) DNS anomalies were discontinued on **8 March 2026**.

> **Training vs product.** The training unit (*Use Anomaly detection analytical rule templates*) says anomaly rules **must be activated** from the **Rule templates** tab, one rule per template. The current product article says they're **enabled by default** and listed on their own **Anomalies** tab. The product wins. Older screenshots and questions may still say "activate from templates".

![Rule templates in the Analytics page](https://learn.microsoft.com/en-us/training/wwl-sci/analyze-data-in-sentinel/media/03-rule-templates.png){Analytics rule templates — Anomaly is one of the rule types (training module view)}

### 2. Read the details pane

Select a rule on the **Anomalies** tab. The details pane shows:

| Field | Meaning |
|---|---|
| **Description** | How it works and what data it needs (and its training period) |
| **Tactics and techniques** | MITRE ATT&CK mapping |
| **Parameters** | Configurable attributes — vary per algorithm |
| **Threshold** | ==@How unusual an event must be before an anomaly is created== |
| **Rule frequency** | Time between processing jobs |
| **Rule status** | **Production** or **Flighting** (staging) |
| **Anomaly version** | Template version; to change it on an active rule you must ==!recreate the rule== |

Filter the tab with **Add filter**: Status, Tactics, Techniques, Data sources.

### 3. Tune by duplicating — the exact rules

1. Built-in rules ==!can't be edited or deleted==. The **Edit** button on them only switches **Production / Flighting** (and sends feedback).
2. Right-click the row (or **...**) → **Duplicate**. The copy is named "*original* - Customized", starts **Disabled**, and shows a **FLGT** badge.
3. Only ==@one customized copy per rule==. A second duplicate fails.
4. **Edit** the copy. Change **threshold** and **parameters**. Check the **Results preview** pane; select an **Anomaly ID** to see why the model flagged it.
5. **Enable** the copy. It runs in **Flighting**; the original keeps running in **Production**.
6. Compare both in Logs. They share the same `AnomalyTemplateId`.
7. Happy? Edit the copy → **General** tab → **Production**. The original ==@flips to Flighting automatically== — only one version can be in Production.

**Too many anomalies?** The usual cause is a threshold that's too low.

### 4. Query the Anomalies table

Check one rule over the last 24 hours, then open `AnomalyReasons` to see why each row fired:

```kql
Anomalies
| where RuleId contains "<RuleId>"
```

Compare original and customized copy:

```kql
Anomalies
| where AnomalyTemplateId contains "<RuleId>"
| summarize count() by RuleName, RuleStatus
```

Useful columns: `RuleName`, `RuleStatus` (Flighting/Production), `Score` (0–1; higher = further from baseline), `AnomalyReasons`, `Tactics`, `Techniques`, `UserName`, `SourceIpAddress`, `Entities`.

### 5. Anomaly rules versus UEBA anomalies

Both fill the same `Anomalies` table. They are switched on differently.

| | ML anomaly rules | UEBA anomalies |
|---|---|---|
| Question answered | *What* activity is unusual | *Who* is behaving unusually |
| Baseline | Training period on specific events | The entity's own history, peers, whole organisation |
| Tuning | Threshold and parameters in the analytics rule UI | On/off through UEBA settings only |
| Examples | Attempted brute force, excessive downloads, beaconing | Anomalous sign-in, account creation, privilege change |
| Prerequisite | Data source connected | UEBA turned on **and** **Detect Anomalies** on |

To get UEBA anomalies: turn on UEBA (`System > Settings > Microsoft Sentinel` → **UEBA** tab → **Turn on UEBA feature**), then on the workspace (`Settings > Microsoft Sentinel > SIEM workspaces` → workspace → **Anomalies**) toggle **Detect Anomalies**.

![UEBA tab in Microsoft Sentinel settings](https://learn.microsoft.com/en-us/azure/sentinel/media/enable-entity-behavior-analytics/entity-behavior-analytics-tab.png){Defender portal: System > Settings > Microsoft Sentinel > UEBA tab}

![UEBA configuration settings](https://learn.microsoft.com/en-us/azure/sentinel/media/enable-entity-behavior-analytics/entity-behavior-analytics-configuration.png){Entity behavior configuration: Turn on UEBA feature, directory sources, data sources}

## Exam traps

- ==!Anomaly rules raise alerts and incidents.== ==+They write to the Anomalies table only.==
- ==!Edit the built-in rule's threshold.== ==+Duplicate it and edit the copy.==
- ==!Make several tuned copies and compare.== ==+One customized copy per rule.==
- ==!The copy goes straight to Production.== ==+It starts Disabled, in Flighting.==
- ==!Promoting the copy deletes the original.== ==+The original switches to Flighting and keeps running.==
- ==!Too many anomalies → raise the training period.== ==+Raise the threshold.==
- ==!UEBA anomalies are tuned with thresholds.== ==+UEBA is on/off only; thresholds belong to ML anomaly rules.==
- ==!Change an active rule's anomaly version in place.== ==+Recreate the rule.==
