## Azure first

- **Syslog** is the standard way Linux machines and network devices write log messages. Every message carries a **facility** (which part of the system sent it: `auth`, `authpriv`, `daemon`, `local0`–`local7`…) and a **severity** (Debug up to Emergency).
- **CEF (Common Event Format)** is a Syslog message whose text follows a fixed security layout: `CEF:0|vendor|product|version|…` followed by `key=value` fields. Firewalls and proxies use it.
- A **Syslog daemon** (`rsyslog` or `syslog-ng`) is the Linux service that receives Syslog messages. It is already on most Linux machines.
- The **Azure Monitor Agent (AMA)** runs on a Linux machine and ships what the daemon hands it. A **data collection rule (DCR)** tells it which facilities and severities to keep. Non-Azure Linux machines need **Azure Arc** first.
- A **log forwarder** is a dedicated Linux VM that receives Syslog/CEF from appliances that can't run an agent.

New to these? Read the Foundations pages linked above.

## In one sentence

**Syslog via AMA** and **CEF via AMA** are two Sentinel connectors that put the Azure Monitor Agent on a Linux machine — either the source itself or a dedicated forwarder — and use a DCR to pick facilities and minimum severities; Syslog lands in the `Syslog` table, CEF in the already-parsed `CommonSecurityLog` table.

## Why it exists

You can't install an agent on a firewall, a switch or most security appliances. They can only *send* Syslog over the network. So you stand up one Linux box as a post office: appliances mail their logs to it on port 514, the local daemon sorts them, and AMA drives them to Azure.

CEF exists because plain Syslog is a free-text letter. Every vendor writes it differently, so you must write a parser for each. CEF is a printed form with labelled boxes — Sentinel can file each box into its own column.

## What actually matters

**1. Which connector, which table.**

| | Syslog via AMA | CEF via AMA |
|---|---|---|
| Messages | Plain Syslog (RFC 3164 / RFC 5424) | CEF over Syslog |
| Table | `Syslog` | `CommonSecurityLog` |
| Fields | Header columns; the message body is one string, `SyslogMessage` | Already parsed: `DeviceVendor`, `DeviceProduct`, source/destination IP… |
| DCR stream | `Microsoft-Syslog` | `Microsoft-CommonSecurityLog` |
| Querying | Write a **parser** (a KQL query saved as a function) | Query columns directly |

If a device offers both, the training is blunt: CEF is the better choice, because the data arrives parsed. Many vendor solutions in the Content hub (Palo Alto, Fortinet, Cisco ASA…) are thin wrappers over **CEF via AMA** or **Syslog via AMA**; installing them pulls the AMA connector in as a dependency.

**2. Two architectures.**

- **Single machine:** AMA installed directly on a Linux server that produces its own Syslog. No forwarder.
- **Log forwarder:** a **dedicated Linux VM** — in Azure, on-premises or in another cloud — receives logs from appliances. If it isn't an Azure VM, it needs the **Azure Arc Connected Machine agent**. Appliances must send to the forwarder's daemon, not their own.

**3. The ports and the hop inside the forwarder.**

- Appliances → forwarder daemon: **UDP or TCP 514** by default (another port is allowed if both sides match).
- Daemon → AMA: **TCP 28330** for AMA **1.28.11 and later**; older AMA used a **Unix domain socket**.
- AMA → workspace: HTTPS.
- If appliances send over the internet to a cloud forwarder, configure **TLS** in rsyslog or syslog-ng.

**4. Setup order (portal).**

1. Install the **Syslog** or **Common Event Format** solution from Content hub.
2. Connector page > **+Create data collection rule**: **Basic** (name, subscription, resource group) > **Resources** (pick the forwarder; AMA installs automatically) > **Collect** (a **minimum log level per facility**) > **Review + create**.
3. On a forwarder, run the **installation script** from the connector page. It configures the daemon to listen on 514 (UDP and TCP), opens the port and restarts the daemon:
   `sudo wget -O Forwarder_AMA_installer.py https://raw.githubusercontent.com/Azure/Azure-Sentinel/master/DataConnectors/Syslog/Forwarder_AMA_installer.py&&sudo python Forwarder_AMA_installer.py`
4. Point each appliance at the forwarder on port 514.
5. Test. Data can take **up to 20 minutes** to appear.

**5. Facilities and severities.** A **minimum log level** collects that level and everything worse: pick `LOG_ERR` and you also get `LOG_CRIT`, `LOG_ALERT`, `LOG_EMERG`. Choose **NONE** to skip a facility. In the plain Azure Monitor wizard the default is **LOG_DEBUG** for every facility (that is, everything). The portal only offers a *minimum* level; the **API** can list exact levels (`logLevels`) and facilities (`facilityNames`). Changes push to all associated machines automatically.

**6. Duplication — the most-tested planning issue.** If the same facility feeds both a Syslog DCR and a CEF DCR, each event is stored **twice** (in `Syslog` and `CommonSecurityLog`). Two fixes:

- Use **different facilities** for CEF and plain Syslog on the sources, and make each DCR collect only its own facilities.
- If you can't change the device, add an ingestion-time **transformation** to the Syslog stream that drops CEF:

```kql
source
| where ProcessName !contains "CEF" and SyslogMessage !contains "CEF:0"
```

**7. Forwarder prerequisites and roles.**

- Linux, **64-bit only**, a supported distro; **Python 2.7 or 3**; **rsyslog or syslog-ng**; `sudo` rights. Don't let the daemon store unneeded logs locally — a full disk stops AMA.
- Linux AMA as a forwarder should target about **10,000 events per second**. For more, use several forwarders behind a **round-robin load balancer** (for a VM Scale Set the docs strongly recommend it).
- Roles: **Virtual Machine Contributor** or **Azure Connected Machine Resource Administrator** to deploy the agent; `Microsoft.Resources/deployments/*` to deploy templates; **Monitoring Contributor** to create or edit DCRs.

**8. Two timestamp columns.** `TimeGenerated` is when the forwarder processed the message (UTC). `EventTime` comes from the Syslog header, which has no time zone, so it is converted using the forwarder's offset. Different time zones = the two disagree.

## Where it lives

**Defender portal:** **Microsoft Sentinel > Configuration > Data connectors** > search **Syslog** → **Syslog via AMA**, or **CEF** → **Common Event Format (CEF) via AMA** > **Open connector page** > **+Create data collection rule**. Azure portal: **Microsoft Sentinel > Configuration > Data connectors**, same steps.

Plain Azure Monitor route (Syslog only): **Azure portal > Monitor > Settings > Data Collection Rules > + Create**, platform **Linux**, data source **Linux Syslog**.

API: `PUT https://management.azure.com/subscriptions/{subscriptionId}/resourceGroups/{rg}/providers/Microsoft.Insights/dataCollectionRules/{name}?api-version=2022-06-01`, then a **DCR association (DCRA)** on the VM: `.../virtualMachines/{vm}/providers/Microsoft.Insights/dataCollectionRuleAssociations/{name}`. With the API route you must install AMA on the forwarder yourself first.

Daemon config files: `/etc/rsyslog.conf`, `/etc/syslog-ng/syslog-ng.conf`. AMA drops its own forwarding rule in `/etc/rsyslog.d/` (or `/etc/syslog-ng/conf.d/`).

Checks on the forwarder:

```bash
sudo systemctl status azuremonitoragent.service
sudo systemctl status rsyslog.service
netstat -lnptv                       # daemon listening on 514?
sudo tcpdump -i any port 514 or 28330 -A -vv &
logger -p local4.warn -P 514 -n 127.0.0.1 --rfc3164 -t CEF "0|Mock-test|MOCK|common=event-format-test|end|TRAFFIC|rt=$common=event-formatted-receive_time"
```

```kql
CommonSecurityLog
| where TimeGenerated > ago(1d)
| where DeviceProduct == "MOCK"
```

A Syslog parser (the training's Squid proxy example, saved as a function so later queries just call `MyParser`):

```kql
Syslog
| where ProcessName contains "squid"
| extend SourceIP = extract("([0-9]+ )(([0-9]{1,3})\\.([0-9]{1,3})\\.([0-9]{1,3})\\.([0-9]{1,3}))", 2, SyslogMessage)
```

A second contradiction worth knowing: the Syslog training unit says the daemon forwards to the agent "via a local Unix domain socket". That was true for older AMA. Current docs: AMA 1.28.11+ uses **TCP 28330**.

## Exam traps

- "Firewall sends CEF; analysts want parsed fields." ==+CEF via AMA → `CommonSecurityLog`.== ==!Syslog via AMA== would leave the payload in `SyslogMessage`.
- "Install AMA on the firewall." ==!Not possible== — use a ==+dedicated Linux forwarder==.
- "Forwarder is on-premises and doesn't show in the Resources list." ==+Install Azure Arc.==
- "Windows Server as the CEF forwarder." ==!No== — Linux, 64-bit.
- "Events appear in both Syslog and CommonSecurityLog." Same facility in both DCRs. Fix: ==+separate facilities== or a transformation.
- "Collect only Warning, not Error." Portal can't; it's minimum-level. ==+Use the API.==
- "Minimum level Error collects only Error." ==!False== — Error and everything more severe.
- Ports: appliances → **514**; daemon → AMA → **28330**. Don't swap them.
- "Creating the CEF DCR is all the forwarder needs." ==!Not per the docs== — the DCR installs AMA; ==+the installation script== opens 514 on the daemon.
