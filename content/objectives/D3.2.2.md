## Azure first

- The **Microsoft Sentinel data lake** is the cheap long-term storage tier behind your Sentinel workspaces (D1.2.2). Tables can live in the **Analytics tier** (hot, fast, expensive), in the **Data lake tier** (cold, cheap, slower), or in both. Analytics-tier data is mirrored to the lake.
- **Data lake exploration** is a section of Microsoft Sentinel in the **Defender portal** only. It has **KQL queries** (an editor for lake data) and **Jobs** (where scheduled work is listed).
- **Federated tables** are outside data (for example Microsoft Entra ID, Microsoft 365 and Microsoft Resource Graph tables) that you can query from the lake without ingesting it.
- A **managed identity** is an identity Azure creates for a service so it can be given roles. The data lake has one, named `msg-resources-{guid}`.
- **Microsoft Entra roles** (Security Operator, Security Administrator…) govern the whole tenant. **Azure RBAC roles** (Log Analytics Contributor…) govern one Azure resource, such as one workspace.

New to these? Read the Foundations pages linked above.

## In one sentence

A **KQL job** is a KQL query you run against the data lake **once or on a schedule**, which writes its results into a table, usually a new `_KQL_CL` table in the **Analytics tier**, so cheap cold data becomes fast, hunt-ready hot data.

## Why it exists

Think of the basement archive from D1.2.2. Years of firewall boxes sit there cheaply. Walking down to search them is slow, and you pay per search. A KQL job is a clerk you send downstairs with written instructions: "Every morning, pull yesterday's connections to these 50 bad IPs and put a one-page summary on my desk." The summary on your desk is the Analytics-tier table. Detection rules, Advanced hunting and workbooks can read it at full speed.

Microsoft lists four uses. Long one-time incident-response queries. Aggregating low-value logs for enrichment. Matching new threat intelligence against **historical** logs. Anomaly scans across several tables. Jobs are strongest when the query **joins or unions** several datasets. Since livestream was retired, KQL jobs are also one of Microsoft's suggested replacements for watching attacker behaviour on a schedule (see D3.2.1).

## What actually matters

**1. Prerequisites and roles.** You must be onboarded to the **Sentinel data lake**. Onboarding needs Sentinel connected to the Defender portal and an Azure subscription + resource group for lake billing. ==+No Defender XDR or E5 licence is required== — lake usage is pay-as-you-go on that subscription. To **create scheduled jobs or manage jobs** you need one of these **Microsoft Entra** roles: ==@Security Operator==, ==@Security Administrator== or ==@Global Administrator==. The same three let you write to Analytics-tier or lake tables. Defender unified RBAC has a matching custom permission: **Analytics Jobs Schedule (Read / Manage)**. To create **new custom tables in the Analytics tier**, also give the data lake's managed identity (`msg-resources-{guid}`) ==@Log Analytics Contributor== on that workspace. ==!That role goes to the managed identity, not to you.==

**2. Creating a job (the wizard).** Start from the KQL query editor (**Create job**) or from the **Jobs** page (**Create job**). Then:

| Step | What you set | Rules worth knowing |
|---|---|---|
| Details | **Job name**, **Job Description** | Name unique in the **tenant**, up to **256** characters, ==!no `#` and no `-`== |
| Destination | **Select workspace** (a Sentinel workspace, or **System tables** for the lake), new table or **Add to an existing table** | New Analytics table gets the ==@_KQL_CL== suffix; new lake table via System tables gets ==@_KQL==. Appending needs a **matching schema** or the run fails |
| Query | **Prepare the query**, **Selected workspaces** (sources), time picker | Several workspaces → `union()` is applied automatically to same-name tables; pick one with `workspace("Name").Table` |
| Schedule | **One time** or **Scheduled job**: **Repeat frequency** (By minute, Hourly, Daily, Weekly, Monthly), **Repeat every**, **From**, **To** or **Set job to run indefinitely** | **From** must be at least ==@30 minutes== after creation. Times are in your locale |
| Review | **Submit** | A one-time job runs straight away |

**3. Templates.** **Create job > Create from template** opens Microsoft's built-in templates. Each has a query, destination table and schedule. Examples: *Network log IOC matching* (hourly, writes `NetworkLogIOCMatches`), *New processes observed in last 24 hours* and *Daily sign-in location trend per user and app*. Categories are **Hunting**, **Anomaly detection** and **Baseline**. You only choose the destination workspace.

**4. Managing jobs.** **Microsoft Sentinel > Data lake exploration > Jobs** lists **every** job type: **KQL**, **Notebook** and **Graph** (the **Job type** column). For **KQL** jobs you can create, **Edit**, **Enable/Disable**, **View history** and **Delete**. ==!Notebook and graph jobs are view-only here==; you edit them in the VS Code extension (D3.2.4). Key behaviours:

- **Edit** can change description, query and schedule, but the query ==!must return the same output schema==.
- ==!Editing a one-time job runs it immediately.==
- **Disable** or **Delete** does not stop a run already in progress or queued.
- You **can't delete a running job**. Deletion is permanent.
- A job whose source workspace is deleted is automatically set to **Disabled**.
- **View history** shows run times, status and the row count written. **Recent health issues** flags failing jobs.

**5. Limits (per tenant).**

| Limit | Value |
|---|---|
| Concurrent job runs | **5**. Extra runs are **rejected, not queued** |
| Enabled jobs | **100** |
| Job query timeout | **1 hour** (partial results may be promoted) |
| Output tables per job | **1** |
| Query time range | up to **12 years** |
| Lake ingestion latency | up to **15 minutes** |

KQL jobs have their own quota, separate from interactive lake queries (30 per minute, 10 concurrent).

**6. KQL rules inside a job.** Everything works except ==!`adx()`, `arg()`, `externaldata()` and `ingestion_time()`==. **User-defined functions are not supported.** With `stored_query_results`, put the time range in the query. Column names must start with a letter. Standard columns such as `TenantId`, `Type`, `_ResourceId` and `_IsBillable` are overwritten on write. ==!`TimeGenerated` is overwritten if older than 2 days==, so copy the original time into another column.

```kql
// Scheduled every 15 minutes: only read data that has surely arrived in the lake
let lookback = 15m;
let delay = 15m;
let endTime = now() - delay;
let startTime = endTime - lookback;
CommonSecurityLog
| where TimeGenerated between (startTime .. endTime)
| where DeviceAction in ("deny", "drop")
| summarize Hits = count(), FirstSeen = min(TimeGenerated) by SourceIP, DestinationIP, DestinationPort
| extend OriginalTime = FirstSeen   // survives the TimeGenerated overwrite
```

```kql
// One-time IR job across a year: promote only what you need (filter + project = lower cost)
SigninLogs
| where TimeGenerated between (ago(365d) .. now())
| where UserPrincipalName =~ "compromised.user@contoso.com"
| project EventTime = TimeGenerated, UserPrincipalName, IPAddress, AppDisplayName, ResultType, Location
```

**7. Cost logic.** KQL jobs are billed by **GB of data analyzed**. Storage in the Analytics tier costs more than in the lake. ==+Filter and `project` before you promote.==

**8. KQL job vs summary rule vs search job.** These three get confused. Microsoft's own comparison:

| | ==@KQL job== | ==@Summary rule== (D3.2.3) | ==@Search job== (D1.2.2) |
|---|---|---|---|
| Reads | data lake tier (+ federated) | Analytics, Basic, Auxiliary, data lake | one table: Analytics, data lake (Basic/Auxiliary/Archive if no lake) |
| Tables per query | many, joins OK | many (Basic: `lookup` to 5 Analytics tables) | **one**, no joins |
| Schedule | on demand or scheduled | every **20 min – 24 h** | on demand only |
| Lookback | up to **12 years** | up to **1 day** (one bin) | up to 12 years, span up to **1 year** |
| Timeout | **1 hour** | **10 minutes** | **24 hours** |
| Needs data lake onboarding | ==!yes== | no | no |

Choose a **KQL job** for long history, complex joins, or scheduled or ad-hoc investigation. Choose a **search job** for data older than your lake onboarding date (the Archive tier) or one big table.

**Two Microsoft pages contradict each other.** The comparison page says KQL jobs schedule *daily, weekly, monthly* with *no template support*. The KQL jobs how-to shows **By minute** and **Hourly** frequencies and a **Job templates** gallery. ==+The how-to describes the shipping wizard; trust it.==

## Where it lives

Everything is in the **Defender portal** only. There is no Azure portal equivalent.

| Task | Path |
|---|---|
| Write / test a lake query | **Microsoft Sentinel > Data lake exploration > KQL queries** |
| Create a job from a query | KQL queries > **Create job** (upper right) |
| Create / manage jobs | **Microsoft Sentinel > Data lake exploration > Jobs** |
| Job templates | **Create job > Create from template** |
| Grant the managed identity | Azure portal > **Log Analytics workspace > Access control (IAM) > Add role assignment** > Log Analytics Contributor > **Managed identity** `msg-resources-{guid}` |

Azure Data Explorer can also query the lake at `https://api.securityplatform.microsoft.com/lake/kql` with `external_table("TableName")`.

## Exam traps

- "Run a lake query every day and make the output usable by analytics rules." ==+Scheduled KQL job writing to an Analytics-tier `_KQL_CL` table.== ==!Not a search job== (on demand, one table).
- "The job can't create its destination table in the Analytics tier." ==+Give the data lake managed identity Log Analytics Contributor on the workspace.==
- "Which role lets an analyst schedule KQL jobs?" ==+Security Operator== (or Security Administrator / Global Administrator). ==!Microsoft Sentinel Contributor alone is not listed== for managing lake jobs.
- "Job name `ioc-scan#1` rejected." ==+No `-` or `#`.==
- "Job scheduled to start in 10 minutes rejected." ==+Start must be at least 30 minutes after creation or editing.==
- "Sixth job submitted while five run." ==!Rejected, not queued.==
- "Job query uses `externaldata()` / a saved function." ==!Unsupported.==
- "Results show today's date in TimeGenerated for old events." ==+Expected: TimeGenerated is overwritten if older than 2 days.== Keep the source time in another column.
- "Write job output to a federated table." ==!Not allowed.==
- "Edit a notebook job's schedule on the Jobs page." ==!View-only== — use the VS Code extension.
- "Query data from before you onboarded to the lake." ==+Search job==, not a KQL job.

## Skip

- **Skip:** the full template catalogue (18 templates with destination tables and lookbacks). Know that templates exist, their three categories and that you only choose the destination workspace.
- **Skip:** the KQL control commands the lake supports (`.show version`, `.show databases`…) and the per-query row and MB limits of interactive lake queries. Interactive querying isn't this bullet.
- **Skip:** row-level RBAC scoping (preview) and the Microsoft 365 audit-log operation names for jobs (`JobCreated`, `JobRunScheduled`…). Admin detail.
- **Skip:** Azure Data Explorer connection details beyond knowing the lake can be queried from ADX with `external_table()`.
- **Skip:** data lake billing meters. Know only "jobs are charged per GB analyzed; Analytics storage costs more than lake storage".
- **No training unit covers this bullet.** The SC-200 learning paths only name KQL jobs in passing (D1.2.2's *Configure logs* unit, and the livestream-retirement note in *Hunt for threats with Microsoft Sentinel* unit 5). This page is written entirely from product docs.
