## Azure first

- A **Log Analytics workspace** is the database under Microsoft Sentinel. Data sits in **tables** (`SigninLogs`, `SecurityEvent`, `CommonSecurityLog`…). Retention is set **per table**.
- **Defender XDR** (Defender for Endpoint, Office 365, Identity, Cloud Apps) keeps its own hunting tables (`DeviceEvents`, `EmailEvents`, `IdentityInfo`…). They live in Defender, **not** in your workspace, unless you extend them.
- **Advanced hunting** is the KQL query page in the Defender portal. It reads both Defender XDR and Sentinel tables.
- **Retention** = how long data is kept before deletion. **Ingestion** = data arriving (billed per GB). Both cost money, and they are billed separately.

New to these? Read the Foundations pages linked above.

## In one sentence

Every table has a **tier** (Analytics, Data lake, or the XDR default) and one or two retention numbers; you set them per table to balance "can I detect and hunt on it right now?" against "what does it cost to keep for years?".

## Why it exists

Think of a filing cabinet with three drawers. The **top drawer** (Analytics tier) is at your fingertips. Detection rules, hunting and workbooks read it constantly, and it is expensive. The **basement archive** (Data lake tier) is cheap and holds years of boxes. You can still search it, but slowly and on purpose. The **third drawer belongs to another department** (the XDR default tier). Defender keeps 30 days there for you, free with the licence. If you want it longer, you copy it into your own cabinet.

Security data piles up fast. Firewall and proxy logs alone can be terabytes a month. Keeping everything in the top drawer for a year is unaffordable. Throwing it away breaks compliance and forensics.

Two numbers matter for an Analytics-tier table. **Analytics retention** is how long it stays hot. **Total retention** is how long it exists at all. The gap between them is long-term storage in the lake. By default total = analytics, so there is no long-term part until you raise total retention.

## What actually matters

**1. The three tiers, with the numbers.**

| | ==@Analytics tier== | ==@Data lake tier== | ==@XDR default tier== |
|---|---|---|---|
| What it's for | Real-time detection, hunting, workbooks, every Sentinel feature | Compliance, forensics, trends, high-volume low-value logs | Defender XDR hunting data |
| Retention setting | **Analytics retention 30 days – 2 years**; **Total retention up to 12 years** | **Retention 30 days – 12 years** | **30 days**, fixed, included in the XDR licence |
| Default | Total = analytics (mirrored to lake, no extra lake time) | — | Not in your workspace at all |
| Analytics rules / advanced hunting | ✓ | ✗ | ✓ (hunting) |
| How you query old data | Full KQL; search jobs; restore | KQL queries/jobs, Spark notebooks, search jobs, summary rules | Advanced hunting |
| Restore | ✓ | ✗ (KQL and notebook jobs can promote data to Analytics instead) | — |
| Cost shape | Standard ingestion, queries included | Minimal ingestion; pay for storage, processing and per-GB query scan | Free for 30 days |

**Choosing a tier — three questions.** Does a detection rule or analyst hunt need this table in real time? Then it belongs in **Analytics**. Is it high-volume, low-value data kept for audit or the odd forensic look-back, such as NetFlow, proxy or storage-access logs? Then use the **Data lake** tier. Is it Defender XDR data you need for longer than 30 days? Then extend it into the workspace, either Analytics (to keep hunting on it) or lake only (cheapest). Tier and retention are separate dials. Pick the tier first, then set the days.

**2. The default-retention numbers disagree between docs.** One doc says Sentinel and Defender XDR keep Analytics data **30 days** by default, and Sentinel solution tables can go to **90 days free**. The billing doc and *Log retention tiers* say a Sentinel-enabled workspace keeps data **90 days** at no charge. Both describe the same deal from two angles: **retention up to 90 days costs nothing extra on a Sentinel workspace**. Beyond 90 days, retention is charged. ==+For the exam: 90 days included for Sentinel; 30 days for Defender XDR; 2 years max hot; 12 years max total.==

**3. Extending XDR data.** Defender XDR tables (for example `DeviceEvents`, `AlertInfo`) start with 30 days in advanced hunting. To keep them longer, raise their retention above 30 days in the Defender portal. The table is then **created in your Sentinel workspace**:

| XDR setting | What you pay |
|---|---|
| 30 days (default) | Nothing extra |
| Analytics 31–90 days | Sentinel **ingestion**; storage free; mirrored to lake |
| Analytics beyond 90 days | Ingestion + Analytics storage |
| Total beyond analytics | + Data lake storage for the extra time |
| Data lake tier only | Lake ingestion, processing and storage. Advanced hunting still shows **30 days** free. |

Turning on the Sentinel XDR connector in the Azure portal does the same for the tables you tick. ==!Resetting both retentions back to 30 days disables that connector.== Some tables (for example `IdentityInfo`) are XDR-type: you can **view** them in the Defender portal but **not manage** them.

**4. What happens when you change settings.**

- **Analytics → Data lake:** alerting, advanced hunting, analytics rules and custom detection rules **stop working** on that table.
- **Not every table can move.** Some XDR and Sentinel solution tables must stay in Analytics because Microsoft services need them in near-real time.
- **Shorten total retention:** Microsoft waits **30 days** before deleting, so you can undo a mistake.
- **Lengthen total retention:** applies to data already ingested and not yet removed.
- **Change analytics retention:** takes effect immediately. Data past the new hot window stays in the lake until total retention ends.

**5. Getting old data back (Log Analytics side, mapped training units).**

| Tool | What it does | Result table | Limits worth knowing |
|---|---|---|---|
| ==@Search job== | Asynchronous search of one table over long periods, including long-term retention, Basic and Auxiliary tables | `YourName_SRCH` | One table; 24-hour timeout. Other limits: see the note below — the docs disagree |
| ==@Restore== | Brings a time slice of long-term data back to hot for full, fast KQL | `TableName_RST` | Minimum 2 days; up to 60 TB; 1 active restore per table; ==@4 restores per table per week==; 2 concurrent per workspace. Analytics and Basic tables only — ==!not Auxiliary==. Delete when done — it costs while it exists (deleting `_RST` never touches the source data). |

**Search-job limits: two Microsoft sources disagree.** The training unit (*Hunt with a Search Job*) says: date range up to 1 year, 1 million records, 5 concurrent jobs, 100 result tables and 100 runs per day per workspace. The current Azure Monitor product doc says: any date range within total retention, **100 million** records, **10** concurrent jobs, **200** result tables and **200** runs per day per workspace. ==+The product doc wins== — it is the newer, maintained source. Both agree on the 24-hour timeout and one table per job.

**6. Table plans in Log Analytics.** Log Analytics has three **table plans**: **Analytics** (full features), **Basic** (cheaper, 30 days of limited single-table KQL) and **Auxiliary** (cheapest, slow queries, queryable for its whole total retention). In the Sentinel world the **Data lake tier** is the recommended home for secondary data. A **Basic** table shows in the Defender portal but can be managed **only in Log Analytics**. Change it to Analytics first to manage it from Defender.

**Who can change it.** Viewing needs **Security data basics (read)** in URBAC, or **Log Analytics Reader**. Changing tier or retention needs **Data (manage)** in URBAC, or **Log Analytics Contributor** (`workspaces/write` + `workspaces/tables/write`). Table insights also lists **Sentinel Contributor + Log Analytics Contributor** for tier changes.

## Where it lives

| Task | Path |
|---|---|
| Table tier and retention (Defender portal) | **Microsoft Sentinel > Configuration > Tables** > select table > **Manage table** |
| Same, new preview hub | **Setup & configuration > Data & connectors > Tables** tab |
| Table plan and retention (Azure portal) | **Log Analytics workspaces > (workspace) > Tables** > table's **...** > **Manage table** |
| Workspace default retention | **Log Analytics workspace > Usage and estimated costs > Data Retention** |
| Search job / restore (Defender) | **Microsoft Sentinel > Data lake exploration > Search & restore** (training unit). The Sentinel *search jobs* doc shortens it to **Microsoft Sentinel > Search**. ==+Use the product-doc path== (Microsoft Sentinel > Search); current docs list only **KQL queries** and **Jobs** under Data lake exploration. |
| Search job / restore (Azure portal) | **Microsoft Sentinel > General > Search** (Saved searches, Restore) |

```bash
# Analytics retention 90 days, total retention 2 years (730 days)
az monitor log-analytics workspace table update \
  --resource-group <rg> --workspace-name <ws> --name SecurityEvent \
  --retention-time 90 --total-retention-time 730
```

The CLI's `--total-retention-time` accepts up to **2,556 days (7 years)**. For the full **4,383 days (12 years)**, use the portal, REST API or PowerShell (`Update-AzOperationalInsightsTable`).

## Exam traps

- "Keep firewall logs 7 years for audit at lowest cost; no detections needed." ==+Data lake tier, retention 7 years.== ==!Analytics retention of 7 years is impossible== — Analytics tops out at ==@2 years==.
- "Keep data hot 90 days and searchable for a year." ==+Analytics retention 90, Total retention 365.== Not two tables, not a restore.
- "Moved `CommonSecurityLog` to the Data lake tier; detections stopped." ==+Expected== — analytics rules and advanced hunting need the Analytics tier.
- "Keep `DeviceEvents` 180 days." ==+Raise its retention in Microsoft Sentinel > Configuration > Tables== (the table is created in the workspace). ==!Defender XDR's own 30 days cannot be extended in place.==
- "Defender XDR data default retention?" ==+30 days.== "Sentinel free retention?" ==+90 days.==
- "Full KQL with joins over 3-month-old long-term data, fast." ==+Restore== (`_RST`). "Find one username across a year." ==+Search job== (`_SRCH`). ==!Restore doesn't work on Auxiliary tables== — use a search job there.
- "Restore the same table a fifth time this week." ==!Fails== — limit is 4 restores per table per week, and only one active restore per table.
- "Shortened retention by mistake yesterday — is the data gone?" ==+No, Microsoft waits 30 days before removal.==
- "Manage a Basic-plan table from the Defender portal." ==!Can't== — change it to Analytics first, or manage it in Log Analytics.
