## Azure first

- The **Windows Security log** is where Windows records logons, privilege use, account changes and process starts. Each record has an **event ID** (4624 = successful logon, 4625 = failed logon, 4688 = new process).
- The **Azure Monitor Agent (AMA)** reads that log on the machine and sends records to Azure.
- A **data collection rule (DCR)** is an Azure resource that says *which* events to collect and *which workspace* gets them. A **DCR association** links a DCR to a machine. One machine can have several DCRs; one DCR can cover many machines.
- **Azure VMs** can take AMA directly. **Any other Windows server** (on-premises, AWS, VMware) must first be connected with **Azure Arc**, which gives it an Azure resource ID.
- The events land in the **`SecurityEvent`** table of the Log Analytics workspace that Microsoft Sentinel uses.

New to these? Read the Foundations pages linked above.

## In one sentence

The **Windows Security Events via AMA** connector is a wizard in Microsoft Sentinel that creates a DCR, installs the Azure Monitor Agent on the Windows machines you pick, and streams the Security (and AppLocker) events you choose — All, Common, Minimal or your own XPath filter — into the `SecurityEvent` table.

## Why it exists

A busy domain controller writes thousands of Security events a minute. Ship them all and the bill explodes. Ship too few and you miss the attack.

Think of a mailroom with a written instruction sheet: "send logon slips and new-employee forms to cabinet B, shred the rest". The agent is the mail clerk on every floor. The DCR is the instruction sheet. Change the sheet once, in Azure, and every clerk follows it — no visit to each server.

This replaced the old **Log Analytics agent** (also called MMA), which was ==!deprecated on 31 August 2024==. The old agent kept its settings in the workspace and could only collect preset sets. The DCR model filters ==@at the source==, so unwanted events never leave the machine and are never billed.

## What actually matters

**1. The four event sets.** On the **Collect** tab you pick one:

| Set | What it contains | Typical use |
|---|---|---|
| **All Security Events** | Every event in the Security log **and** the AppLocker logs. ==!Not== Application, System or Setup. | Maximum visibility, highest cost |
| **Common** | A full **user audit trail**: logon and logoff (4624, 4634), group changes, key Kerberos events on domain controllers | Auditing / compliance |
| **Minimal** | Only events that may signal a breach, plus rare important ones: 4624, 4625, 4688, 1102 … but ==!no logoff (4634)== — so no full audit trail | Detection at low volume |
| **Custom** | Your own XPath queries; can also pull **other logs** | Exact control |

Most of Minimal's volume is logons and process creation (4688). Exam questions describe a requirement ("full audit trail", "lowest cost but breach detection") and expect you to pick the set.

**2. XPath filters (Custom).** XPath is a small query language for picking XML nodes. Each Windows event is XML, so XPath picks events. The format is `LogName!XPathQuery`:

- `Security!*[System[(EventID=4624 or EventID=4625)]]` — only logons, successful and failed.
- Limits: ==@up to 20 expressions in one box, up to 100 boxes in a rule==. **XPath 1.0 only.** Functions such as `position`, `band` and `timediff` work. ==!`starts-with` and `contains` do not.==
- Test locally first with PowerShell: `Get-WinEvent -LogName 'Security' -FilterXPath '*[System[EventID=4624]]'`. Events back = valid. "No events were found" = probably valid but nothing matched. "The specified query is invalid" = syntax error. (`Get-WinEvent` accepts up to 23 expressions; DCRs only 20.)
- **Analytic and Debug channels can't be collected** (Windows won't let AMA subscribe to them). Event logs stored on network shares or UNC paths aren't supported either.

**3. Where the DCR lives doesn't matter much.** The **Basics** tab asks for a rule name, subscription and resource group. They ==+do not have to match the machines==, as long as everything is in the **same tenant**. On **Resources** you tick subscriptions, resource groups or single machines; you see Azure VMs and Azure Arc-enabled servers. AMA is installed automatically on any selected machine that doesn't have it.

**4. Azure VM vs Arc.** An Azure VM needs nothing extra. A physical server, an on-premises VM or a VM in another cloud must have **Azure Arc installed and enabled ==!before==** you enable the connector — otherwise it won't appear in the Resources list.

**5. Permissions.** You need **read and write permissions on the Sentinel workspace**, plus permission to create DCR objects (the exact built-in roles — **Monitoring Contributor** for DCRs, **Virtual Machine Contributor** or **Azure Connected Machine Resource Administrator** to push the agent — are listed on the Syslog/CEF page, D1.3.4).

**6. DCRs outside the wizard, and transformations.**

- **API / code:** a DCR is just an Azure resource, so you can create it with REST, ARM, Bicep, CLI or PowerShell. Microsoft suggests this for MSSPs who create many rules. The key parts: `dataSources.windowsEventLogs` with stream **`Microsoft-SecurityEvent`** and `xPathQueries`; a `destinations.logAnalytics` workspace; a `dataFlows` entry linking them. DCRs created by API still appear on the connector page.
- **Two DCR types to know.** A **standard DCR** is used by AMA and the Logs Ingestion API. A **workspace transformation DCR** applies to data that arrives some other way. `SecurityEvent` supports workspace transformations.
- **Transformation** = a KQL query run on each incoming record before it's stored. The incoming data is a virtual table called `source`. Example: `source | where EventID != 4634`. Filter with XPath first (cheaper, at the agent); use a transformation for what XPath can't do.

**7. Scale.** On Windows, AMA targets about **5,000 events per second** — the Windows Event service limit.

**8. Not the same as a plain Azure Monitor DCR.** If you build a DCR under **Monitor > Data Collection Rules** and pick "Windows Event Logs" with the Security log, the same agent collects the same events — but they go to the ==!`Event` table==, not `SecurityEvent`. Sentinel's Windows content reads `SecurityEvent`. Use the Sentinel connector.

**Migration.** Still on the legacy agent? The **AMA migration tracker workbook** in Sentinel shows which machines still run it.

## Where it lives

**Defender portal (current):** **Microsoft Sentinel > Configuration > Data connectors** > **Windows Security Events via AMA** > **Open connector page** > **+Add data collection rule**. Install the **Windows Security Events** solution from **Content hub** first.

**Azure portal (until 31 March 2027):** **Microsoft Sentinel > Configuration > Data connectors** > same steps.

Edit or delete existing rules under **Configuration** on the same connector page.

Arc onboarding for non-Azure servers: **Azure portal > Azure Arc > Machines > Add/Create**.

Command line (create a DCR from a JSON file, then associate):

```powershell
New-AzDataCollectionRule -Name "dcr-win-sec" -ResourceGroupName "rg-sentinel" -JsonFilePath ".\dcr.json"
```

```bash
az monitor data-collection rule create --resource-group rg-sentinel --name dcr-win-sec --rule-file dcr.json
```

REST: `PUT https://management.azure.com/subscriptions/{subscriptionId}/resourceGroups/{rg}/providers/Microsoft.Insights/dataCollectionRules/{name}?api-version=...`

Check the data arrived (allow ==@up to 5 minutes== after creating the DCR; a healthy agent writes one `Heartbeat` row a minute):

```kql
SecurityEvent
| where TimeGenerated > ago(1h)
| summarize count() by EventID, Computer
```

```kql
Heartbeat
| where TimeGenerated > ago(15m)
| distinct Computer
```

## Exam traps

- "Collect only failed and successful logons from domain controllers." ==+Custom with an XPath query== — not Minimal (Minimal also brings 4688 process creation and more).
- "Full audit trail including sign-outs, lowest volume." ==+Common.== ==!Minimal has no 4634 logoff.==
- "All Security Events includes the System log." ==!False== — Security plus AppLocker only.
- "On-prem server not shown on the Resources tab." ==+Install Azure Arc first.==
- "DCR must be in the same resource group as the VMs." ==!False== — same tenant is enough.
- "Use `contains` in the XPath." ==!Unsupported== — XPath 1.0 subset only.
- "Plain Azure Monitor DCR collecting the Security log feeds Sentinel's Windows rules." ==!No — it lands in Event.==
- "Legacy agent connector is equivalent." ==!Deprecated 31 August 2024 and has no XPath filtering.==
- Distractor names: "Windows Event Collector connector", "Security Events via AMA (Legacy)" — the real names are **Windows Security Events via AMA**, **Windows Forwarded Events**, **Security Events via Legacy Agent**.

## Skip

- **Skip** the full event-ID lists for Common (a long list) and Minimal (39 IDs). Remember the anchors: 4624/4625 in Minimal, 4634 only in Common, 4688 process creation, 1102 log cleared.
- **Skip** the DCR JSON body line by line. Know the three sections — data sources (stream `Microsoft-SecurityEvent` + XPath), destinations, data flows — and that DCRs can be created by API.
- **Skip** the training unit "Connect using the Security Events via Legacy Agent Connector" (`connect-windows-hosts-to-azure-sentinel`, unit 4) — off-blueprint, agent retired.
- **Skip** the XPath `band(Keywords, …)` bitmask example. Know XPath exists, its 20/100 limits and the 1.0 restriction.
- **Skip** the data-normalization module's ASIM parser units (`data-normalization-microsoft-sentinel`, unit 5 "Create an ASIM Parser") — off-blueprint; only its DCR unit 6 matters here.
- **Skip** the Agent Settings DCR, AMA disk-cache size and the performance benchmark tables. One number is enough: ~5,000 events per second on Windows.
