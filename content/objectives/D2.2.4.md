## Azure first

- **Defender XDR** joins signals from Defender for Endpoint (devices), Defender for Identity (on-premises Active Directory), Defender for Office 365 (email) and Defender for Cloud Apps (SaaS) into one **incident** in the Defender portal.
- A **contained** device or user is not deleted or wiped. Other onboarded devices simply refuse to talk to it, or the account is blocked from signing in.
- The **Action center** (`security.microsoft.com/action-center`) records every automatic and manual action, and is where many of them are undone.
- **Device groups** in Defender for Endpoint carry an **automation level** (Full, Semi, No automated response). Attack disruption respects it.
- There is **no training unit** for this bullet. Everything here comes from product documentation.

New to these? Read the Foundations pages linked above.

## In one sentence

**Automatic attack disruption** is Defender XDR acting on its own during a high-confidence attack (for example human-operated ransomware or business email compromise): it **contains devices, IPs and users or disables accounts** in real time, tags the incident **Attack Disruption**, and leaves you to investigate and then **release** the assets once it's safe.

## Why it exists

Human-operated ransomware spreads from machine to machine faster than a person can triage an alert. Attack disruption is a **sprinkler system**: it fires on its own when it is very sure there is a fire, it contains the spread, and then the fire brigade (you) investigates, cleans up and turns the water off. Microsoft states a precision target of **99% or higher** for containment detectors, and every action can be undone.

## What actually matters

**1. The actions it can take.**

| Action | Product that executes it |
|---|---|
| ==@Contain device== (block comms with an unmanaged/compromised device) | Defender for Endpoint |
| Contain IP (undiscovered / not onboarded device) | Defender for Endpoint |
| Isolate device (Preview — workstations only, time-limited) | Defender for Endpoint |
| ==@Contain user== (block the account's network logons, RPC, SMB, RDP on onboarded devices) | Defender for Endpoint |
| ==@Disable user== (AD account: via DCs running the Defender for Identity sensor; AD synced to Entra: disabled in both; cloud-only Entra account: via the Microsoft-managed *Microsoft Defender for Identity* enterprise app) | Defender for Identity |
| Revoke user session / Suspend user in Entra | Microsoft Entra ID |
| OAuth app compromise measures | Defender for Cloud Apps |
| AWS deny policy / Okta suspend (Preview) | Microsoft Sentinel connectors |

*Contain user* does **not** disable the account in the identity provider. It blocks the account at the endpoint layer. *Disable user* does. There is **no manual Contain user button**: Microsoft states containing users is currently only available automatically, through attack disruption.

**2. How you recognise a disrupted incident.**

- Tag **Attack Disruption** plus the threat type (for example *ransomware*) in the incident queue — and in incident email notifications.
- A **yellow banner** under the incident title.
- Contained or disabled assets carry a status **label** in the incident graph.
- An **attack disruption summary card** on the incident page with **View activities** and **View related assets**.
- The incident **Activities** tab: filter **Performed by** = *AttackDisruption* (the results article), plus **Activity status** = *Completed*. The overview article words the same filter as **Provider: Attack disruption** — two docs, two labels; use whichever the UI shows. The filter also returns **predictive shielding** actions. The **Policy status** column (Preview) shows **Active** (still enforced), **Inactive** (released), **Not applicable** (an undo action) or **No status** (still in progress or not retrievable).
- Through the API, likely-disrupted incident titles end in **(attack disruption)**.

**3. Investigating.** Read the attack story, then hunt. Advanced hunting logs the **blocks** containment caused, not the containment action itself:

```kql
DeviceEvents
| where ActionType contains "ContainedUser"
```

Use `"ContainedDevice"` for device-derived blocks. Blocked attempts also appear on the **device timeline**.

For an organisation-wide view, query the advanced hunting table `DisruptionAndResponseEvents`. ==!Two Microsoft pages disagree about it.== The results article calls it "a unified view of the same automatic actions" and shows queries filtering on `IncidentId`, `AccountUpn`, `RemoteIP` and `AttackDisruptionCategory`. The table's own schema reference lists **none** of those columns. It says the table holds only the **outcomes** of Defender for Endpoint controls (blocked logons, ended SMB/RDP sessions, policy applied/removed) and **not** the execution of Contain user or Disable user — those live in the **Action center**. The schema reference wins. Query it with columns that exist:

```kql
DisruptionAndResponseEvents
| where Timestamp > ago(30d)
| project Timestamp, ActionType, ReportType, DeviceName, SourceUserName, SourceIpAddress, TargetDeviceName, IsPolicyOn
| order by Timestamp desc
```

Typical `ActionType` values: `ContainedUserLogonBlocked`, `ContainedUserSmbFileOpenBlocked`, `ContainedUserRemoteDesktopSessionDisconnected`, `ContainedUserRpcAccessBlocked`. `ReportType` is **Prevented** (blocked before it ran), **Blocked** (live session killed) or **PolicyUpdated**.

**4. Remediating and releasing.** Investigate and clean first — releasing early lets the attacker resume.

- **Device:** select it in the incident > **Release from containment** (or **Release from isolation**), or from the device page.
- **User:** select it > **Enable user**; or Action center > **History** > the *Contain user* action > **Undo**.
- **IP:** Action center > the *Contain IP* action > **Undo**.
- Undoing *Contain user* needs **Global Administrator** (per the device-response article).
- Automatic releases also happen: a contained user is released within **five days**, and automatic isolation is undone after a defined window.

**5. Prerequisites that make it work.** Licence (any one): Microsoft 365 E5/A5, E3 + Defender Suite, E3 + EMS E5, Defender for Endpoint Plan 2, Defender for Identity, Defender for Cloud Apps, Defender for Office 365 Plan 2 or Defender for Business, among others. Each product must be deployed to perform its own actions. Defender for Endpoint **device discovery** must be **Standard** for *Contain device*. Sense agent **v10.8470+** for *Contain user*. Device-group **remediation level**: **Full** recommended; **Semi** still allows disruption; **No automated response** excludes the group. Defender for Identity needs domain-controller **auditing** and a working **action account** (LocalSystem by default). Disruption acts whatever the Defender Antivirus mode (Active, Passive or EDR block mode). Defender for Cloud Apps needs the **Microsoft 365 connector** with every box ticked. Defender for Office 365 needs mailboxes in **Exchange Online** and mailbox auditing of `MailItemsAccessed`, `UpdateInboxRules`, `MoveToDeletedItems`, `SoftDelete`, `HardDelete`. Okta and AWS actions (Preview) need a Sentinel workspace connected to the Defender portal with that provider's connector.

**6. Exclusions instead of opting out.** **Settings** > **Microsoft Defender XDR** > **Automated response**: **Identities** (exclude user accounts), **Devices** > **Device groups** (automation level), **IPs**, and **Policy application** (Preview — disable specific controls for tagged devices). Excluded isolation shows **Skipped** in the Action center. Full opt-out needs a support case titled *Attack disruption opt-out*; you still get the alerts, but no automatic actions. Setting a device group to **No automated response** also switches off automated investigation and response (AIR) for it.

## Where it lives

All in the **Microsoft Defender portal** (`security.microsoft.com`).

| Task | Path |
|---|---|
| Find disrupted incidents | **Incidents & alerts** > **Incidents** > filter/tag **Attack Disruption** |
| Per-incident actions | incident > summary card > **View activities** / **Activities** tab |
| Release / undo | incident graph > asset > **Release from containment** / **Enable user**; or **Actions & submissions** > **Action center** > **History** > action > **Undo** |
| Exclusions | **Settings** > **Microsoft Defender XDR** > **Automated response** |
| Device-group remediation level | **System** > **Settings** > **Endpoints** > **Device groups** |

Permissions: configuring needs Global Administrator, **Security Administrator**, **Security Operator** (or several identity admin roles). Managing exclusions: **Security Administrator** or **Global Administrator** when unified RBAC is off; **Security Operator** (or higher) or the **Core security settings (manage)** permission when unified RBAC is on. A **Security Reader** can view exclusions but not edit them.

## Exam traps

- ==!You approve disruption actions in the Action center before they run.== ==+They run automatically; you review and undo afterwards.==
- ==!Contain user disables the account in Entra ID.== ==+Contain user blocks it on onboarded endpoints; Disable user (Defender for Identity) disables the account.==
- ==!To stop disruption on a critical server, turn the feature off.== ==+Use an exclusion (identity, device group, IP or policy application).== Opt-out is a support case.
- ==!Release assets as soon as the incident appears.== Investigate and remediate first.
- "Hunt the blocks caused by containment across the tenant" → `DisruptionAndResponseEvents` (or `DeviceEvents`). ==!It logs the Contain user / Disable user action itself.== ==+It logs only the outcomes; the action is in the Action center.==
- ==!An analyst can manually Contain user from the user page.== ==+Contain user is automatic-only (attack disruption).==
- "Show logons blocked because the user was contained" → `DeviceEvents` with ActionType containing `ContainedUser`.
- Policy status **Inactive** = the asset is **no longer** contained.
- **Semi** automation still allows disruption; only **No automated response** excludes a device group.

## Skip

- **Skip:** the AI paragraph (graph models, boosted trees, small language models). Know "high-confidence, 99%+ precision, incident-level".
- **Skip:** the Okta and AWS setup pages. Know that Sentinel connectors extend disruption to them (Preview).
- **Skip:** predictive shielding (Safeboot hardening, GPO hardening, proactive contain user). It shows under the same *AttackDisruption* filter but is a separate, preventive feature.
- **Skip:** the long Defender for Identity domain-controller hunting query. Know `IdentityDirectoryEvents` and "Account disabled".
- **Skip:** the `MsSenseDllVersion` registry commands. Know "Sense v10.8470+ for Contain user".
- **Skip:** the domain-controller GPO update that Contain user triggers (and reverts on Undo). Operational noise, not exam material.
